## 1. 交付范围与设计结论

新增插件 `bmc_ikvm`，通过 [插件宿主](V0.2.1_PLUGIN_HOST.md) 的清单注册，在已有工作区中打开独立 KVM 页签。页面拥有自己的会话、连接状态、远程帧缓冲与输入焦点，和终端页签同级；画面及控件均由 zenit 原生渲染。配置包括连接名称、BMC IP/主机名、HTTPS 端口、BMC 用户名/密码，以及可选的已保存 SSH 跳板配置引用和本次认证。打开连接时由 ZeroWork 建立、维持和释放本会话独立转发，不要求 Netcatty 或 Chrome 正在运行。本文不要求为 KVM 修改向导、设置页、AI 工具枚举、页签图标分支或会话创建分支。本文件是 V0.2.2，不是 V0.2.1 的子版本。V0.2.1 只交付插件宿主、三个内置插件迁移和假插件验收；v0.2.1.2 通过之前不开始本版实现，生产注册清单也不加入 `bmc_ikvm`。

首版采用 **HTTPS/Redfish 管理通道 + OEM KVM 会话 + WSS 上的厂商扩展 RFB + zenit RGBA 流纹理**。实机前端已经显示其修改了 noVNC 握手，不能把 `/kvm/0` 交给任意标准 VNC 客户端即宣称兼容。可复用标准协议实现与开源测试方法，但 OEM 登录、控制权、握手和消息必须单独实现并由实机证据约束。

包括：远程画面、键盘/鼠标、必要组合键、适应窗口/原始比例/全屏、只读与可控制状态、断线重连、开机/正常关机/重启/强制断电等实机允许动作、一次性/持续启动覆盖、实机支持的启动模式与只读启动顺序。启动能力按实际返回值展示，不保证每个固件提供全部字段。

不包括：虚拟媒体/镜像挂载、文件传输、SOL、传感器/告警中心、BMC 用户管理、固件更新、BMC 自身重启、录屏、终端广播、把电源/启动写入或键鼠交给 AI，以及动态插件市场。只读的电源状态、启动项和画面尺寸/文字描述可以写进插件清单，由插件宿主接线，不在本文件里改 AI 枚举。启动项中的 CD/USB 仅代表目标机已有设备，不能让用户误以为可以在本版上传 ISO。

## 2. 证据分级与目标机协议

### 2.1 事实来源

本节严格区分四类信息：**源码事实**来自当前仓库；**实机读取**来自目标 BMC 的 HTTPS/WS 响应；**前端事实**来自目标机公开交付的 JavaScript；**设计约定**为本插件拟实现行为。前端包含某条分支并不证明当前账户、固件或硬件支持它；请求返回成功也不等于已经验证真实重启或键鼠效果。

目标拓扑为本机 → 用户指定 SSH 跳板的 22 端口 → 内网 BMC 的 443 端口。连接名称、地址和账户均由用户配置，实际密码、令牌、认证头、登录返回中的会话 ID 不进入文档、截图、测试夹具、日志或版本库。现有 Chrome 页面与 Netcatty 转发只作为研究参考，产品不读取浏览器 Cookie、扩展配置或复用其不稳定端口。

### 2.3 OEM 握手与控制权

从实机与前端共同确认的最小状态机为：`WebSocket101 → SendBinary("KVM ") → ProtocolVersion → OemMagic → Security → Authentication → SecurityResult → ClientInit → ServerInit → Normal`。传输是字节流，不能假设一条 WebSocket 消息恰好等于一条 RFB/OEM 消息；每个状态先检查所需长度，再消费，支持拆包和粘包。

前端四字节消息的行为如下，命名是本设计用于解释的名称，不冒充供应商正式协议文档：

| 首字节 | 前端处理 | 原生适配要求 |
| --- | --- | --- |
| `105` | 根据后续字节处理 major/minor 控制权；将首字节改为 `106`，剩余字节原样回发 | 完整保留原包，校验长度和状态；等待控制权结果，不先开放输入 |
| `104`，第二字节 `0` | 允许进入标准 Security 阶段 | 此前不能把 OEM 字节解释成 security type count |
| `104`，第二字节 `1` | 提示有用户独占 | 显示占用原因，允许退出或稍后重试，不自动抢占 |
| `104`，第二字节 `2` | 提示共享连接已达到限制 | 不循环创建新 KVM 会话 |
| 其他值 | 前端失败 | 返回结构化 `UnsupportedOemHandshake`，保存脱敏阶段/消息类型，不降级绕过 |

前端中 `105` 的第二字节 `1` 对应 major，其他情况对应 minor；第二字节 `0`、第三字节 `1` 有约 30 秒授权等待；拒绝分支出现第二字节 `127`。这些均属于前端证据，必须用只读实测或可控夹具补齐顺序、运行期消息与拒绝语义。首版不自动批准其他会话获取控制权，也不自动从只读抢控制权。若服务端已授予控制权，再开放普通键鼠；尚未确认则只读。

`SecurityType=None`（本机实测选择type1）只表示 RFB 层不再重复认证，不代表匿名访问：其前面必须有受信任 TLS、Redfish 登录、OEM token 和服务器授权。所有安全类型以真实协商为准；未知类型失败并显示具体原因，不退回不加密连接。

运行期除了标准FramebufferUpdate等消息，还必须处理下表前端已识别的OEM消息。下列长度包含type字节；它们是该固件profile的明确解析规则，不能在收到第一个心跳时以“非标准RFB”断开。

| 类型 | 长度/方向 | 处理契约 |
| --- | --- | --- |
| 102 `CMD_KEEP_ALIVE` | server→client 1字节 | 立即回binary `[102]`；这是OEM应用层保活，WS ping/pong不能替代 |
| 105/106 | server105共4字节；client106共4字节 | 重新计算major/minor和等待状态；回复保留本次收到的3字节上下文，撤权先release_all；不要拿初始化时旧包回复 |
| 107 | server→client 4字节 | 新控制权请求，按本次context提示现主控；弹窗最多保留约30秒，超时等待服务器最终裁决 |
| 109 | client→server 1字节 | 用户明确点击申请控制权才发送，不自动抢占 |
| 108 | client→server 4字节 | 对107作显式答复；第二字节1=全部控制、0=只看视频、127=拒绝，其余字段使用本次request上下文；未知context不猜包 |
| 125 | server→client 2字节 | 更新主机显示状态；只影响画面状态，不自行改变电源 |
| 122 | server→client 2字节 | 更新键盘LED：bit0 Num、bit1 Caps、bit2 Scroll；不能为同步灯状态而反向发送按键 |
| 123 | server→client 8字节 | status、媒体状态、保留字节、u16分辨率上限宽/高；status2触发无信号/电源状态只读复核，媒体状态忽略；它不是普通FramebufferUpdate，不能误当帧矩形或未知消息断开 |
| 121 | 一般4字节：type/service/operation/value | 消费并转成只读提示；service=4且value≠127时后随value字节UTF-8文本，需等全长且禁止日志输出序列号；value=127无追加文本 |
| 113 | server→client 8字节 | 启动顺序通知（operation/status/5项），可消费后触发Redfish刷新，不把其固定5项数组覆盖实际20项BootOrder |
| 126 | server→client 1444字节 | 前端宏数据（3字节头+1440字节），本版不启用宏；若收到按固定长度有界消费并忽略 |

本版允许按profile发送OEM120且operation=0的只读查询，以及113的只读顺序查询；禁止operation=1等OEM电源/启动写命令，写操作统一使用§8–9的Redfish事务，以免出现双通道重复写。121中的只读电源/启动值可按§2.2与Redfish交叉验证，不能独自冒充Redfish写操作成功回执。真正未知且无法确定长度的消息必须停止解析并报告协议版本不支持，不能盲目跳过导致后续帧错位；所有上述已知运行期消息需先有fixture覆盖，副控授权真实效果仍待受控验证。

### 2.4 兼容边界

`BmcProfile` 通过服务根信息、固件标识、OEM 字段、KVM 登录资源及握手特征匹配，不用 IP 段或网页标题猜厂家。实机服务根版权信息确认中科曙光（Sugon），产品SuperPod/Hygon，BMC芯片AST2600-A3，固件1.80，BIOS 0TC1001011。首个 profile 命名 `sugon_1_80_oem_rfb`，只声明本实机固件族已观察的兼容行为，不外推所有曙光机器。匹配失败可保留已发现的只读管理信息，但不能宣称 KVM 可用。

配置中的“自动识别”只尝试已实现的 profile，不能执行从 BMC 返回的 JavaScript。 profile 定义登录过程、WS 子协议/路径、OEM 协商、像素编码集合、输入差异、控制权、注销和错误映射。协议扩展不侵入工作区或控件代码。

## 3. 插件接入与自主配置

### 3.2 KvmConnectionEditor 的信息与操作

插件决定以下信息和交互，不强制其他协议采用这些字段或步骤。普通字段可选 schema 辅助，有序跳板编辑、认证、发现和连接状态机由插件实现，复用宿主控件、主题、焦点及挑战 UI。

| 信息 | 来源与规则 |
| --- | --- |
| 名称、分组 | 公共 ConnectionEnvelope，沿宿主资产规范保存 |
| BMC endpoint | 主机/IP、HTTPS 端口，默认 443 可修改；BMC 是最终 TCP 目标 |
| BMC 认证 | 用户名、当次密码；与 SSH 认证域独立，不从浏览器或已有会话取 token/密码 |
| 访问方式 | 直连或按已保存 SSH 配置独立建链；没有选择活跃会话/运行转发的入口 |
| SSH 配置引用 | 保存显式有序 `route[]`，每项引用已保存SSH资产；复用SSH路径编辑器，支持添加、删除、调序及本机→各跳板→BMC预览。只读取每项地址、端口、认证/凭据引用与host key策略，不继承该主机自身route |
| 缺少 SSH 资产 | 调用同一宿主承载内的 SSH 编辑能力创建/选择，返回时保留 KVM 非秘密草稿；取消不产生半成品 KVM 资产 |
| 转发 | 插件从 BMC endpoint 确定内部转发目标；不要求手填本地端口、常驻 SOCKS 或另开 SSH 终端 |
| TLS/profile | 目标信任使用公共信任仓；运行期只尝试已实现的 profile，不增加普通用户必填 profile 字段 |
| 显示偏好 | fit/逻辑 100%/只读请求为本 KVM 偏好，不混入 SSH 配置 |

保存只校验结构和可解析引用，可离线、可暂不提供密码；保存并连接先原子保存，再启动独立 attempt；临时连接不入资产。probe 用自己的临时连接，只验证 SSH/TLS、管理登录、资源发现/能力并注销，不占用 OEM 视频会话、不发送输入，不把“管理认证成功”称为“画面已验证”。打开控制台才进行视频验证。probe 结束释放的秘密引用不能继续使用；同一仍存活草稿可在既有授权范围保留 lease，否则再次提示。

### 3.3 用户操作与宿主接线

| 用户操作 | 宿主调用和所有权 | 插件/状态结果 |
| --- | --- | --- |
| 侧栏“新建主机”→协议选择BMC iKVM | 注册表取ConnectionContribution，挂载editor到既有创建槽 | 同一页组织名称/分组、BMC地址/端口/认证、直连或SSH配置引用；不要求所有插件相同步数 |
| 选择SSH跳板 | 公共SSH路径编辑器逐项选择已保存SSH记录，返回有序route[]及非秘密摘要 | 不查看活跃Tab，不绑定原转发；直连隐藏该字段 |
| 没有跳板→新建SSH主机 | 以parent_editor/draft_revision调用已有SSH编辑能力 | 取消返回原KVM草稿；成功返回新asset_id后由KVM重新校验，秘密不复制进payload |
| 测试连接 | `editor.probe(draft_revision, cancel)`分配独立临时owner，申请本次凭据 | 显示测试进行中/成功/失败，取消只回收测试资源；成功只证明SSH/TLS/BMC管理登录与发现，不开视频 |
| 仅保存 | editor.validate/encode→AssetStore原子提交 | 侧栏公共投影更新；不建立网络连接。原型停在已保存、未连接状态，可再次连接/编辑 |
| 保存并连接 | 先完成保存；同一SessionHost.open分配handle/operation→session_factory.create→一个controller | 使用仍有效且已授权的草稿secret lease，否则挑战；保存失败不建链，连接失败不删除资产 |
| 已保存主机的连接动作 | AssetStore取版本化信封→同一SessionHost.open→controller解析/冻结配置 | 不依赖原SSH在线；显示路由、身份、管理登录、视频协商与首帧阶段 |
| 首次证书或认证失败 | controller发宿主trust/auth challenge | 信任与密码输入只交本attempt；重新认证保留非秘密配置，不自动重放管理写入 |
| 取消/关闭/重连 | SessionHost的同一cancel/close/release_stale链 | 只清理本owner；自动重试冻结配置，手动重连重新解析，旧完成不得挂回 |

编辑已保存KVM调用同一editor并带原envelope/revision，保存后提示下次连接生效；运行中的独立KVM保持旧冻结值。配置输入、错误和测试结果属于editor草稿，只有宿主保存成功才发布新资产revision。测试结果绑定draft_revision；地址/账号/路由变更即失效，不能拿上次“成功”跳过新目标信任。测试失败保留字段并定位实际失败阶段，字段错误行内显示；全局业务反馈走统一通知，不重复弹两个成功提示。

Figma创建表单的连接路径入口直接复用SSH三主题的有序路径卡片：本机→各跳板→BMC预览、已保存主机选择、防重复、添加、删除、调序，确认回同一KVM草稿。表单底部明确提供取消、测试连接、仅保存、保存并连接。管理测试由该按钮触发，完成回同一表单的结果状态；内容页没有另造测试按钮。已有SSH编辑器分支沿其现有设计，返回由宿主parent context协调，不要求KVM实现SSH配置或凭据流程。

保存并连接、已保存主机的连接和手动重连共用SessionHost.open(envelope, intent)→session_factory.create→单个KvmConnectionController；创建表单仅负责校验、编码及可选保存，不另写会话启动流程。测试复用配置校验/冻结与独立transport，但在probe范围完成后清理，不进入视频。配置复用与会话独立并不排斥复用同一实现。该open为0.2.1的目标入口，扩展现有SessionHost.create；editor不调用controller启动、不预建运行连接。保存成功回调与连接按钮共用request key，避免一次“保存并连接”创建两个会话；重连沿原Tab建立新attempt。

## 4. 数据模型与服务边界

以下为目标类型形状；持久配置、当次快照、运行资源和显示状态分开：

```text
BmcConnectionPayload {
  endpoint { host, https_port = 443 }, username,
  access = direct | ssh_route { hops[] { asset_id } },
  display { scale = fit, read_only_requested = false }
}
BmcCreateSpec {
  envelope_id?, envelope_revision?, payload,
  frozen_route { resolved_hops[], asset_revisions[] },
  credential_references[], secret_leases[], target_window, target_workspace
}
BmcSession { handle, create_operation, owned_transport, auth_generation,
             web_session, kvm_session, capability_revision, frame_generation }
CapabilitySnapshot { video, input, control_owner, reset_types[],
                     boot_targets[], boot_modes[], override_modes[],
                     boot_order_kind?, boot_options[], secondary_auth }
FrameSnapshot { session_handle, frame_generation, sequence, width, height,
                stride, format=rgba8, pixels_lease, received_monotonic_ns }
InputCommand { session_handle, binding_generation, input_sequence,
               key_down | key_up | pointer | wheel | release_all }
ManagementOperation { operation_key, target_system_uri, capability_revision,
                      requested_action, phase, result, verify_deadline }
```

公共 ConnectionEnvelope 存 ID/名称/分组/revision/payload_version；payload 不存秘密、展开后的 SSH 配置、冻结 revision、动态本地端口或 token。目标 TLS 信任由 trust 仓管理，profile 是运行期匹配结果。密码只在本次 secret lease 中，末次释放清零。未接系统凭据库前不提供“已安全保存密码”的提示；已有 SSH 凭据配置沿现状真实提示，不在本版顺带改造。

已运行 session 使用冻结配置；自动重试保持本次目标，手动重连重新解析当前资产。修改/删除引用不会打断现有 KVM，新建时引用失效则报错，不从活跃会话兜底。临时连接同样有 SessionHandle，但不自动保存。

独立维护 route、web_auth、video、input、management 五个状态。它们是插件服务状态，与宿主SessionHost生命周期正交：宿主attached不等于已收到视频首帧；管理在线不等于视频在线，视频可看不等于允许键鼠，释放未知不等于资源已释放。标题/状态、菜单和AI使用同一快照投影，不维护互相矛盾的“已连接”布尔值。阶段为 validation→route/SSH trust/auth→TLS trust→profile/web_auth→discovery→KVM negotiation→first_frame→viewing，各阶段可取消并准确归因。断线保留旧帧并标停止更新；无信号需 OEM 显示状态等证据，黑色像素可正常在线。只读、申请控制权、等待、允许、拒绝分开；取消等待不冒充服务端撤销，控制权变化先 release_all。

FramebufferService 提供完整帧，RemoteInputService 接收代际命令，Power/BootService 接收从本会话能力构造的请求。UI 不拼 Redfish 路径，不取得 raw token 或 libssh2 指针。

### 4.1 可实施的服务函数与结果

以下为Zig接口伪签名；`binding`含SessionHandle和binding_generation，所有调用先验证live，内部队列入队不代表已发远端：

```text
FramebufferService.acquireLatest(binding, after_sequence) ->
  frame(FrameLease) | unchanged | unavailable(Reason) | stale_binding
FrameLease.release() -> void
RemoteInputService.submit(binding, InputCommand) ->
  accepted(input_sequence) | read_only | not_focused | queue_full | stale_binding
RemoteInputService.releaseAll(binding, cause) ->
  accepted | locally_cleared_remote_unconfirmed | stale_binding
PowerService.snapshot(binding) -> Snapshot(PowerState, AllowedResetTypes, freshness)
PowerService.request(binding, PowerExecutionRequest) -> accepted(OperationKey) | rejected(Reason)
BootService.snapshot(binding) -> Snapshot(BootState, AllowedValues, freshness)
BootService.apply(binding, BootExecutionPatch, expected_revision, etag?) ->
  accepted(OperationKey) | conflict(CurrentSnapshot) | rejected(Reason)
ManagementService.cancel(OperationKey) ->
  cancelled_unsent | observation_stopped_remote_may_continue | already_terminal | stale_operation
ManagementService.result(OperationKey) ->
  queued | awaiting_auth | sending | accepted_remote | verifying |
  succeeded(VerifiedResult) | failed(StructuredError) | outcome_unknown(LastObservation)
```

`Snapshot`携带来源URI、采集单调时钟、capability_revision、fresh/partial/stale标记；未连接不返回伪造Off或空BootOrder。管理写请求还须携带用户点击执行时冻结的目标摘要和 execution nonce，入队后 UI 不能替换 target。`StructuredError`含阶段、稳定错误码、可显示原因、HTTP/OEM code、retryable，绝不含原始认证payload。

### 4.2 队列、帧lease与取消

帧缓冲由FramebufferService持有，worker写入时独占可写buffer，发布后变为不可变lease；UI acquire增加引用，上传完成即release，不保存裸pixels指针。默认两块CPU buffer：一块工作帧、一块最近完整帧；UI仍持有完整帧时worker不得覆盖它，也不得再无界分配第3块。可以继续累积工作帧或施加读端背压，release后再发布最新一致帧。交换工作/发布buffer前复制或同步必要基底，使下一次增量始终基于上一完整帧；不能只交换指针就让工作buffer回到更早的画面。显示mailbox只有1个“最新快照”槽；替换已未被UI借用的快照时释放旧lease。generation过期直接release，纹理只属于UI线程。

设计上限：输入mailbox256条；鼠标move合并，按键/button down/up不得静默丢弃。队列满时返回queue_full并暂停捕获，专用release-all控制槽（1个可合并标志）不受普通队列堵塞影响。管理写入同时仅1个，读请求队列最多8项并按资源URI合并；状态事件最多64项，重复进度可覆盖，终态通过持久operation结果槽保留直到controller确认，不能丢掉完成回执。传输缓冲与解码工作区另受§6.3总预算限制。

取消未发送请求：从queue撤出、清零本操作认证密码，返回cancelled_unsent且明确未作用远端。发送开始后不能确认服务器是否执行时，取消仅停止本地等待/后续轮询，标记observation_stopped_remote_may_continue或outcome_unknown，绝不展示“操作已撤销”。用户关闭tab同理；不发送反向电源/恢复Boot PATCH作为补偿。读请求可中止transport或丢弃过期completion；写请求不能因为通道中断就自动重试。所有缓冲、任务和lease在owner结束时有唯一释放路径。

## 5. 配置复用与独立跳板传输

### 5.1 建链与所有权

```text
宿主 SessionHost.open → session_factory.create（一次）
  → KvmConnectionController / 新 owner
  → 只读配置解析与冻结 → TransportFactory.openOwned
  → 本 KVM 专用 SSH IO owner / 全新 SSH Session 与 direct-tcpip
  → 本次 HTTPS + WSS/OEM-RFB → typed 服务 → 内容 renderer
```

直连同样新建本会话 TCP/TLS 资源。经跳板只复用保存配置与连接器实现，不复用任何活跃 SSH/SFTP/KVM Session、socket、channel、监听器或运行转发。一个 KVM 内的 HTTPS/WSS 可共享自己这条 SSH 传输，不能跨会话共享。原 SSH 终端或原转发关闭/重连不影响 KVM，KVM 取消/关闭也不改变它们。

空route直连BMC；非空route沿0.2.1已验收的有序路径逐跳新建无shell SSH，再从末个SSH节点打开最终BMC TCP通道，不把 BMC 作为需 SSH 登录的末跳。HTTPS 保活和长期 WSS 至少需要两个并发 direct-tcpip stream，由同一 IO owner 公平调度；通过有界 mailbox/socketpair 暴露，不能多线程直接访问同一 libssh2 Session。

默认内部流转发，不公开本地端口。库确实需要本地 TCP 入口时，单独绑定 `127.0.0.1:0`，动态端口不持久化，只属于本 KVM；不得占用/接管用户原转发端口。绑定失败明确报错，不停止占用者。本版不提供固定本地端口设置或外部 SOCKS 配置入口。

以下是用户提出的设计场景，**不是新增实测目标**：BMC `172.16.13.10`，SSH 配置地址 `10.2.209.21`。443/22 仅为设计默认，实际端口、账号、认证、有序跳板列表由输入与资产决定；不能假定它与原 Sugon 测试机同一 profile。

1. 插件编辑器保存 BMC endpoint/用户名、有序SSH route[]引用等非秘密配置，宿主原子保存公共信封。
2. 连接分配新 owner/attempt，逐项解析显式route中的SSH资产，不继承资产自身route，检查类型/缺失/重复/环/8跳上限和版本，冻结 revisions；缺凭据时走本次挑战。
3. 独立连接 `10.2.209.21:<配置端口>`，逐跳信任/认证，不开 PTY、不执行资产启动命令；新建到 `172.16.13.10:<HTTPS端口>` 的本次通道。
4. 保留原 BMC authority 完成 TLS、管理认证、profile/资源发现、OEM/WSS/RFB 握手；首帧后发布视频，控制权确认后才允许输入。
5. 电源/启动使用本 KVM 管理通道，执行后区分接受/验证/失败/未知，不随转发重连重发写请求。probe 另建临时资源，失败/取消只回收对应 owner。

原调查目标为 SSH `10.2.209.201` → BMC `192.0.2.40`；既有证据见§2。新例子没有连接测试，不把示例地址写进运行默认值。

### 5.2 目标身份不能被本地转发覆盖

TCP 实际连 socketpair/loopback，TLS 验证名、HTTP Host、Origin、WS authority 仍使用原 BMC host/port。不可把验证对象改成 `localhost`，也不可为解决自签名证书而全局关闭 TLS 验证。对 IP 地址验证 SAN 中的 IP；DNS 名按主机名验证并以其为 SNI（IP 目标是否发送 SNI按TLS库约定）。通过跳板连接 DNS 名时优先由跳板侧解析，避免将内网 DNS 请求错误发往公网。

首次不受信任证书显示 subject/issuer/有效期/SHA-256 指纹与确切目标，经用户明确接受后按连接记录 pin；后续改变阻断并提示。SSH host key 使用现有 known_hosts 处理，其信任与 BMC TLS 信任分开。临时连接的接受只作用本次 owner，明确选择持久信任后才写仓；浏览器曾访问不等同产品已信任。证书过期、身份不匹配与自签名分别表示，不统一吞成“连接失败”。

### 5.3 有界 IO 与恢复

设计默认：单阶段网络连接超时 15 秒（用户信任/认证挑战暂停该计时；OEM 授权等待按§2.3）；读操作有取消令牌；WS辅助心跳15秒、连续2次无响应视为失联；视频静止不能视为断线。实际固件是否支持 WS ping/pong需验证；若不可用以 TCP/SSH保活与可控健康请求组合判断，不能每秒重新登录。

失败状态保留envelope/route引用、顺序和失败阶段，而非保存“最后一个跳板”作为新目标。手动重试进入同一SessionHost.open，由当前资产重新解析全部route引用；配置未改时路径完全相同，已改动则按最新revision验证并准确展示，不能静默丢跳或改直连。只有用户确认编辑才改变route；取消、关闭或旧attempt完成不覆盖新attempt的路径。

网络恢复可重试 1/2/4/8 秒（上限 30 秒并带轻微抖动），每次以本次冻结配置建立新 attempt 和新 native 资源；认证错误、证书改变、控制权占用不自动高频重试。断线立即禁止输入，保留最后画面并明确遮罩“连接已中断，画面停止更新”。重连完成先拿完整帧并确认控制权，再允许输入；旧队列中的按键、鼠标、电源和启动修改绝不补发。

错误区分配置引用、跳板不可达、SSH 信任/认证、目标端口拒绝、监听失败、BMC TLS/认证、profile 不支持、KVM 占用及视频无信号。保留非秘密草稿和具体阶段，不统一报密码错误或自动换资产。手动重连重新解析当前配置；目标/跳板改变重新走对应信任/认证。


## 6. 登录、协议解析与开源复用

### 6.1 连接顺序

1. 宿主先分配 SessionHandle/OperationKey；控制器校验 payload、解析并冻结 BMC/跳板配置，申请本次 secret lease。
2. 按访问方式新建直连或专用 SSH 路由并验证 SSH host key，向配置的 BMC host/port 打开本次通道。
3. TLS 验证；GET Redfish root，发现 Systems/Managers/SessionService URI，拒绝跨 origin 的资源链接。集合多成员时通过 manager→Links/ManagedBy 等关系唯一定位 `/kvm/0` 对应 system；无法证明映射则禁管理写入，不能默认第一项。需要用户选择时使用 choice challenge，不增加永久必填字段。
4. 按`sugon_1_80_oem_rfb` AuthProfile使用已验证RSA2048公钥/PKCS#1 v1.5/base64封装Password，并附`From: WebUI`和`X-Requested-With: XMLHttpRequest`，POST Redfish Session。令牌、会话资源位置与Id分开保存；Location必须校验同origin与合法资源路径。固定厂商公钥封装不替代TLS；普通明文Redfish登录不得当成WEB会话继续交换。
5. 读取目标 system、manager、允许动作、boot 字段、权限及必要 SecurityService。只读测试连接到此报告认证与能力，不以副作用操作测试权限。
6. POST OEM KvmSessions，保存单独的 KVM token/id；按实机 profile 打开 WSS `/kvm/0`，子协议使用 KVM token，HTTP Upgrade 必须验证状态、accept 与协议响应。
7. WS升级成功后先发binary `KVM `，解析RFB版本、OEM magic/控制权、Security、ServerInit；主动设置32bpp/24depth像素格式与Tight/Raw/LastRect等已实现编码，申请全帧。
8. 首帧校验/解码完成交主线程上传，视图从“正在打开画面”进入控制/只读；管理服务可独立标记可用。

Redfish发现失败、KVM token失败、OEM占用、无视频信号等必须分别归因。管理通道暂不可用时不必立刻杀掉仍有效的画面；显示管理动作禁用原因。反过来视频失败时可保留已认证管理状态，但用户必须明确看到 KVM 不在线。

Web token 失效仅暂停管理并重认证；仍有效的视频流继续显示。KVM token 失效先释放输入，再建立新视频 attempt。认证失败停止自动重试，提供新凭据后再继续。相同 endpoint/账号的多个 Tab 仍有独立会话，达到容量上限提示关闭本应用相应 Tab 或稍后重试，不自动抢占或循环开会话。

### 6.2 编码与库选择

noVNC 是浏览器 JavaScript VNC 客户端，其协议处理与测试可参考，但 canvas/DOM 渲染不直接成为 zenit 原生窗口。OpenBMC 的 bmcweb/webui-vue 展示了 HTTPS 鉴权、WSS RFB 与控制 UI 的分层；它只能作为架构参考，不能证明本实机使用标准 OpenBMC 握手。[noVNC](https://github.com/novnc/noVNC)、[OpenBMC bmcweb](https://github.com/openbmc/bmcweb)、[OpenBMC KvmConsole](https://github.com/openbmc/webui-vue/blob/master/src/views/Operations/Kvm/KvmConsole.vue)。

首版主路径确定为 **Zig 0.17有界RFB解析器与OEM profile + 现有vendored mbedTLS提供TLS/RSA + 系统zlib提供Tight持续解压 + macOS ImageIO/CoreGraphics提供Tight JPEG解码**。noVNC与RFB规范用于协议、行为和测试向量参考，不携带其DOM/canvas运行时；LibVNCClient作为对照实现参考，不作为首版链接依赖，因此不让其连接状态机限制OEM前导与运行期消息。[LibVNCServer/LibVNCClient](https://github.com/LibVNC/libvncserver)。

具体集成点：

- `build.zig`当前core已经链接`mbedcrypto`与`z`；`scripts/build_ssh_deps.sh`当前只生成`libmbedcrypto.a`，并没有可直接使用的完整TLS客户端。实现时在同一固定版本vendored mbedTLS构建中增加`libmbedtls.a`、`libmbedx509.a`，复用mbedcrypto，显式加入core和BMC测试target依赖；不可悄悄链接Homebrew随机版本。
- `src/plugins/bmc_ikvm/protocol/tls_shim.{h,c}`封装TLS context、socketpair非阻塞read/write、证书链/主机名或pin策略、取消、RSA公钥加密和清理；沿现有`b.addTranslateC`/`addCSourceFiles`模式暴露稳定C接口，Zig不依赖mbedTLS内部结构布局。开启实际用到的client TLS、X.509、RSA PKCS#1 v1.5配置并做握手fixture，不能把已有crypto静态库等同于TLS已接线。
- `src/plugins/bmc_ikvm/protocol/http.zig`与`websocket.zig`实现本任务所需有界HTTP/1.1、chunked/Content-Length响应、Upgrade、masked客户端WS帧/控制帧与分片。拒绝跨origin重定向、冲突长度头、超限headers/body；REST默认body上限4MiB、header64KiB，视频WS按帧上限及流式解析，不把整段无界聚合。JSON使用项目Zig版本std.json解析，schema/字段错误和HTTP状态分别报告。
- `src/plugins/bmc_ikvm/protocol/rfb_{parser,tight,raw,input}.zig`拥有状态机；小型`zlib_shim`或受控C导入复用系统`z`，每会话4个inflate状态，按Tight reset位重置。JPEG通过`src/plugins/bmc_ikvm/platform/jpeg.m`（函数式C ABI）使用ImageIO解码内存data，检查源宽高、目标格式和输出预算后转RGBA8；在网络/解码worker创建并释放局部CG对象，不访问AppKit/Cx/GPU。构建显式链接ImageIO/CoreGraphics。若以后移植其他平台，再替换同一JpegDecoder接口，不为本次增加跨平台框架。
- 新依赖构建与TLS/压缩夹具先在v0.2.2.1验收，生产app和相关测试使用同一依赖配置；不向纯UI mockup target引入SSH/TLS。任何基础库版本改变记录在`vendor/DEPENDENCIES.md`，不自动升级无关库。

这个实现只覆盖目标机实际协议和声明支持的标准子集。未知固件由profile匹配阻断，不从网页下载并执行协议代码，也不引入远端代理服务。

本机已实测Raw(0)、Tight(7)、LastRect(-224)，首版选择Tight为主、Raw为回退；暂不引入H.264解码，因为没有协商或流证据。Tight必须实现4个持续zlib stream、control字节低位reset、compact length、copy/palette/gradient过滤及fill/JPEG路径，协商质量伪编码只在对应解码路径完整时发出。当前帧已测fill/palette，其余路径须由合成夹具和动态实机覆盖。RFB子集还必须覆盖实机接受的DesktopSize/光标等实际使用的伪编码。仅声明客户端确实实现的编码；初期可用 Raw 做可行性验证，但最终带宽/延迟验收必须采用实机实际可用的压缩编码，不能用“能出一帧”代替图形可用。实现前锁定依赖 commit、构建选项和源码许可证；现仓库 LICENSE 为 GPLv3 文本，noVNC 为混合文件许可，LibVNC 项目标示 GPL-2.0，具体导入文件的授权条款须逐个核对，不能只凭仓库徽章推定可组合。[noVNC 许可](https://github.com/novnc/noVNC/blob/master/LICENSE.txt)。

### 6.3 解析器防护与帧发布

设计上限：初始最大 4096×2160 RGBA8（约 33.75 MiB/帧）；宽高乘法、stride、矩形边界、压缩输出长度均用检查算术；异常超限返回明确错误，不允许整型溢出或无界分配。默认两个完整 CPU 帧缓冲加一个 GPU纹理，1080p约 23.7 MiB，4096×2160约 101.25 MiB，不含解压工作区；这些是设计预算，须测量实际开销后冻结。

增量矩形必须顺序解码并应用到工作帧，完成一个一致的更新才发布 sequence。UI可丢弃旧的完整显示快照，但不能跳过协议 delta 后仍沿用旧底图。重连/分辨率改变增加 frame_generation 并请求非增量完整帧；不把旧大小矩形贴到新帧。WebSocket fragmentation、ping/pong/close、RFB消息长度、未知encoding都要有明确处理，不把未识别消息“略过几个字节继续”。

### 6.4 持续更新与运行预算补充

首帧使用非增量FramebufferUpdateRequest；完成一个FBU（含LastRect）后才请求下一次增量，基础模式最多一个未完成请求。静态画面可长期无更新，不作为超时证据。ContinuousUpdates仅协商确认后使用；后台通过减少后续请求节流，不停止整条WSS读取，以免阻塞保活/撤权。恢复前台、分辨率变化和重连重新获取一致完整帧。

初始实施上限：每会话传输暂存8MiB、解码临时工作区64MiB，矩形输出不得超过目标区域预算；JPEG先检查尺寸再解码。帧存储沿§6.3，分辨率切换额外纹理计入峰值；应用KVM资源预算初值512MiB，分配前预留，超限拒绝新会话/新尺寸并显示原因，不无限加缓冲。这些为待测工程上限，不能写成性能实测。连续矩形处理按有界批次让出调度，控制/取消消息不得被渲染上传饿死。

协议交付还须保留非秘密RSA公钥材料或确定的获取/指纹核验规则、OEM注销方法与脱敏路径模板、合成拆包/粘包/动态Tight向量。目前只有公钥散列和注销状态码，不足以独立复现；补证前不得标协议交付完成。

## 7. zenit 原生画面与输入

### 7.1 纹理和线程

公开 `ui.image(cx, texture_id, style)` 创建单个画面节点；宿主注入 `FrameTextureSink{create,update,release}`，实现连接实际 `render.ImageTextureStore.createStreamTexture()` / `updateStreamTexture()` / `unloadTexture()`。当前 ImageRenderer facade 没有同名 stream 包装，接入时由宿主封装纹理 store；这一通用 facade 必须在 0.2.1 的合成帧夹具中验收；0.2.2 不再临时修改 workspace 业务接线。插件视图不 import `ui.core`、不私自创建 Metal device。

现有 stream texture 是单 mip RGBA8，`updateStreamTexture` 更新整张纹理；首版接受完整帧上传，先验证 1080p基本交互，再按数据决定是否增加 dirty-region 上传。禁止为每帧 load/unload 普通图片、生成 PNG、重建整棵节点树或把每个像素画成 box。分辨率变化时先创建新纹理，上传成功后原子切换 node，再按渲染生命周期释放旧纹理；失败保留明确错误，不能挂无效 texture_id。

网络/解码线程只持不可变配置、CPU帧和队列，不触碰 Cx、Node、Signal 或 GPU。主线程在现有安全 tick/drain位置取最新完整帧，校验 SessionHandle 与 frame_generation，上传并 `markRenderDirty`/`requestRedraw`。不在回调执行中销毁当前节点。后台 tab 降低显示上传频率，协议仍正确解码或请求暂停更新；重新激活必须拿到一致帧，不能只解码最后一个 delta。

### 7.2 显示几何

`fit` 采用 `scale=min(viewport_width/frame_width, viewport_height/frame_height)`，画面保持比例并居中；黑边属于本地viewport。内容槽沿现有r11卡片，原型基准1194×794，上方44，下面viewport1194×750，无视频内距/内框。1920×1200的fit图像为1194×746.25，上下各1.875px比例黑边，scale≈62.19%。参数随宿主分配的内容槽变化，不固定整窗大小。100%模式一个远端像素对应一个zenit逻辑显示单位，菜单文案“100% · 逻辑原尺寸”，超出时可滚动；Retina 2×时一远端像素占2×2物理显示像素，这不是物理点对点模式。首版不另加物理像素模式。Retina backing scale仅用于GPU呈现，不能让鼠标坐标乘两次。全屏复用所在窗口的原生能力，退出后恢复此前布局与tab焦点。

远端坐标为 `floor((local_pointer - displayed_image_origin)/scale)` 并约束到 `[0,width-1]×[0,height-1]`。黑边点击不发送远端pointer；拖拽开始于画面内时允许捕获到边界并 clamp，直到 mouse_up。尺寸变化、缩放、滚动、窗口移动均更新变换，测试角点/中心和高DPI，不能靠截图猜坐标。

### 7.3 键盘与鼠标

使用 zenit 的 `key_down/key_up/mouse_down/mouse_up/mouse_move/scroll/focus/blur` 事件。为远程输入维护 pressed_keys、pressed_buttons、control_generation。键码映射到 RFB keysym（或实机扩展所要求的scancode）；修饰键分别down/up，自动重复遵循远端语义。区分物理键事件与 `text_input/ime_commit`，不能发送两遍文字。首版保障英文键盘、数字、符号、功能键、方向键、编辑导航键及远端OS自身输入法；不承诺把macOS中文预编辑文字直接变成BIOS按键。未知键显示不支持且不猜测映射。

鼠标优先采用实际已协商的绝对指针模式；实机需要相对模式时单独profile能力并提供鼠标同步，不能把缩放后的绝对坐标错发为相对位移。移动事件可合并到最新位置（设计上限60次/秒），down/up、滚轮步骤和组合键不可合并丢失；保持按钮mask与顺序。

点击画面取得远程输入焦点，工具栏/弹窗/切tab/窗口失焦/断线先发送可达的 release_all 并本地清空按下状态。释放失败不在新连接补发旧down；新的连接从无按键开始。应用提供“释放键盘鼠标”按钮和稳定释放快捷键（原型显示 `⌃⌥Esc`）；该组合由本地截获，不发给远端。仅画面焦点且已获控制权时路由远端输入；配置输入框、弹窗与tab切换保留本地键盘语义。

组合键菜单支持 Ctrl+Alt+Delete、Ctrl+Alt+F1…F12、F1/F2/F10/F11/F12、Esc等实机常用操作，按明确顺序发送down、反序up，失败立即release。不可直接把macOS Command视为远端Control；提供清楚的映射说明。Ctrl+Alt+Delete具有远端效果，用户激活才发送，不在连接测试中自动执行。剪贴板同步、粘贴脚本与密码自动填写不在本版默认能力中。

### 7.4 输入释放屏障

输入命令带input_epoch/control_generation。释放、撤权、关闭、接管时先递增epoch、废弃旧待发输入，再对已实际发送的pressed_keys/buttons尽力发送up。发送端在写入前再次核对epoch与权限，release_all优先槽不能执行后又发送旧down。组合键失败反序释放；文字输入返回已发送范围，不能盲目重发全文。人工输入租约与未来AI输入租约由宿主协调，同一会话只有一个本地写入者。

## 8. 电源管理

从已选定 ComputerSystem 的 `Actions.#ComputerSystem.Reset.target` 及 `ResetType@Redfish.AllowableValues`/ActionInfo发现动作；缺少允许值时按profile已证实映射且标记能力证据，不从UI猜。主机电源动作和BMC自身Manager.Reset分离，后者不提供。[DMTF ComputerSystem schema](https://redfish.dmtf.org/schemas/DSP2046_2021.1.html)。

本实机独立ResetActionInfo已返回`On/ForceOff/ForceOn/ForceRestart/GracefulRestart/GracefulShutdown/PowerCycle/Nmi`，大小写按原值保留。动作下拉仅提供下表动作；ForceOn与Nmi不因服务端存在就自动增加到用户范围，尤其Nmi不是普通重启。

| 用户动作 | 标准候选 ResetType | UI与执行规则 |
| --- | --- | --- |
| 开机 | On | 仅设备允许且当前适用时可选 |
| 正常关机 | GracefulShutdown | 明确由操作系统配合；未完成不能自动升级强制断电 |
| 正常重启 | GracefulRestart | 失败/无响应显示真实状态 |
| 强制断电 | ForceOff | 在动作气泡显示风险与目标，点击执行提交冻结动作 |
| 强制重启 | ForceRestart | 独立动作选项，不能与正常重启混为一项 |
| 断电后开机 | PowerCycle | 仅真实允许值存在时展示，不自行用ForceOff+On拼成无事务操作 |

请求为 `POST <discovered reset target> {"ResetType":"..."}`。点击执行时冻结 session owner、system URI、动作与capability revision；发送前复核当前 binding仍live和权限未变。二次点击禁用；同一会话 power/boot 共用写锁，宿主 tasks 再以规范 endpoint+system URI 协调跨 Tab 的本应用写入，拒绝重叠操作，权限仍逐会话验证。这只协调任务，不共享任何运行连接；外部网页竞争仍靠 ETag/读回发现。由controller更新宿主统一通知与操作记录：“请求中/已接受，等待状态/已核实/失败/结果待确认”，UI不自建通知。

点击执行冻结目标、动作、草稿差异及 capability_revision。前置状态超过 5 秒先重读；字段须为干净结果或本 profile 逐字段 corroborated（§2.2），变化时提示重新选择/执行，不增加常规确认弹窗。Task/TaskMonitor 只追踪同 origin 的已发现 URI，资源消失或超时不能解释成成功。

仅当body没有error/失败ExtendedInfo时，HTTP 200/204才表示请求被接受，不证明电源状态已变化；202读取TaskMonitor/Task资源，遵循Retry-After并限制轮询。之后GET PowerState并观察预期状态；重启不一定捕获瞬时Off，因此不能仅看到On就声称重启已完成，须结合task/厂商响应或明确“请求已接受，当前开机”。超时或连接断开后请求可能已执行，标记结果待确认，读回状态，**不自动重发**电源请求。只允许用户再次明确操作。

电源状态轻量轮询建议可见时5秒、后台30秒，结合已有请求合并，页面关闭取消；按固件负载/会话限制调整。SSH失联、BMC认证失败、权限不足、二次认证未确认均禁止发送。日志只记录操作类型、目标安全标识、状态码和结果，不记录认证头。

## 9. 启动项管理

“启动项”气泡包含：当前启动覆盖、目标、持续生效开关、可选启动模式；BootOrder/AliasBootOrder 在本版仅展示；顺序写入尚未完成目标固件验证，不因字段存在或拖动可实现就开放。当前正在从哪个设备运行与下次启动覆盖必须分开标注。本实机返回的20项BootOrder只读，覆盖选项可按§2.2交叉验证规则准备编辑；实际写入仍待维护窗口验收。

实机GET已返回目标`None/Pxe/Hdd/Cd/Diags/BiosSetup/Usb`、模式`Legacy/UEFI`，当前`Disabled/None/UEFI`，当前启动源Hdd、当前类型UEFI；BootOrder包含20项且BootOptions集合确实存在。前端支持有效期`Once/Continuous`。上述读取不证明写入权限或实际生效，本版不开放启动顺序写入。以实时AllowableValues、ActionInfo、schema及profile证据裁剪列表；未知OEM值保留原文只读，不映射成最相近选项。`Disabled`用于关闭覆盖，与目标`None`不是同一个字段。[DMTF Boot字段定义](https://redfish.dmtf.org/schemas/DSP2046_2021.1.html)。

示例请求仅表示标准语义（URI与值必须来自真实发现）：

```json
{"Boot":{"BootSourceOverrideTarget":"Pxe","BootSourceOverrideEnabled":"Once"}}
```

设置模式时仅在设备支持且用户改变时加入 `BootSourceOverrideMode`。只PATCH改变的字段，不把整份System GET结果原样PUT/PATCH。用户点击执行前在同一气泡显示所选动作摘要；保存不自动重启，成功按读回结果提示“仅下次启动生效”或“将持续生效”，需要重启时由用户另外执行电源动作。

官方语义依据目标返回的 [DMTF ComputerSystem v1.22](https://redfish.dmtf.org/schemas/v1/ComputerSystem.v1_22_0.json)：Once仅下次启动使用目标，完成后回Disabled；Continuous每次启动使用该目标直到关闭覆盖。这不修改BIOS永久BootOrder，不是“是否保存当前设置”。[OpenBMC BootSettingsStore](https://raw.githubusercontent.com/openbmc/webui-vue/master/src/store/modules/Operations/BootSettingsStore.js)也以布尔的一次性选择映射Once/Continuous，并单独处理Disabled；本插件采用更直白的“持续生效”开关。不能把示例UI当成目标固件写入成功证据。

| 草稿 | Redfish值 | 界面 |
| --- | --- | --- |
| 按正常启动顺序 | Enabled=Disabled | 隐藏持续开关；不把Target=None等同关闭 |
| 有效目标，持续生效关闭 | Enabled=Once | 仅下次启动，使用后恢复正常 |
| 有效目标，持续生效开启 | Enabled=Continuous | 每次启动，直到关闭覆盖 |

开关只修改草稿，点击执行才提交；不直接PATCH或重启。若设备/profile不支持Continuous则禁用该开关并给原因，不能默默改成Once；v1.22明确UefiBootNext不支持Continuous，不将早期schema对UEFI的泛化限制套到所有UEFI目标。首版不开放手写UEFI路径/BootNext。Once用完UI刷新真实Disabled，不把它“纠正”回Once；关闭覆盖保留其他字段实际读回。设备返回@Redfish.Settings时识别当前值/pending值和Settings URI；只在确认该字段的写入目标后提交，不能盲目尝试两个URI并重复写。

BootOrder/BootOptions 按集合 pagination、有界数量和 BootOptionReference 去重读取，未知项保留 ID 和原文；20 项 BootOrder 与 5 类 AliasBootOrder 不互相覆盖或证明。不提供拖动、提交顺序、通用 BIOS 属性、手写 UEFI 设备路径或新建启动条目。

启动草稿由当前session binding与System URI持有，包含target、enabled、mode及各字段的修改标记；菜单只投影该草稿。修改启动设备只改变target，持续开关只在Once/Continuous间切换，模式选择只改变mode，不能重置其余字段。关闭下拉、关闭气泡及切换到电源/显示/按键/控制菜单均保留草稿；同值重选不产生修改。选择关闭覆盖时隐藏持续和模式控件，暂存的编辑选择保留在本地草稿，再选有效目标时恢复；提交关闭覆盖只写Enabled=Disabled，不能把隐藏草稿冒充服务端当前值。执行读回成功后以该值更新基线；关闭再打开仍保留Once/Continuous/Disabled及设备和模式，无修改时禁用执行，不能回到默认Disabled或重复提交。打开气泡保留实际当前值；当前 Disabled 显示“未覆盖”，无修改时执行禁用，不预填待执行的 PXE。用户选择有效目标后才形成覆盖草稿，通过“持续生效”开关选择仅下一次或持续；模式仅支持且需要时显示。目标下拉中的“恢复默认（关闭覆盖）”只写 Enabled=Disabled，不把 Target=None 当作 Disabled，也不伪造服务端已清空的目标/模式。下次启动模式不等于当前 BIOS 模式。写入沿§8的同会话/跨 Tab 互斥、5 秒前置与能力门控。

后台刷新只更新未修改字段；与已修改字段或其能力条件冲突时保留草稿并提示重审。会话结束销毁草稿；重连产生新binding后先读回并重新校验，旧草稿只能作为待审输入，不自动提交。写入前使用ETag/If-Match（若支持）防止覆盖另一用户的变化；412/409刷新并显示差异，保留草稿待用户重审，不能自动覆盖。无 ETag 时发送前重读并比较草稿基线，变化则拒绝本次提交、保留草稿；该方式不能消除外部竞争，不承诺原子防覆盖。完成后读回期望字段并区分已应用、pending、部分不匹配。请求中断时标记结果待确认，先读回再由用户决定是否重试，不自动重复PATCH。权限不足或厂商二次认证失败不降级绕过。

## 10. 二次认证、安全与清理

实机`EnableAuthConfirm=false`，前端启用分支读取`<manager>/SecurityService`后输入确认密码并生成`AUTHKEY`。网页登录所用固定RSA2048公钥、PKCS#1 v1.5/base64已实测有效，二次确认复用FP函数属于前端证据，尚未以真实危险动作验证。实现profile时记录§2.2公钥指纹、算法与编码；启用二次认证的固件仍须补可控成功/失败测试，不能把不同固件统一绑定未经验证的key。

本插件在二次认证信息读取失败时停止写操作并提示“无法确认操作认证要求”，不复制网页catch后继续执行的行为。确认输入仅用于当前冻结的operation，取消立即清零；确认成功不扩大为全局免确认。授权/角色依据服务器响应，403/401立即失效相应能力。需要重新登录时重新验证目标身份，旧管理请求不重放。

关闭顺序：停止接收新输入/写操作 → 尽力释放远端按键 → 取消读与排队任务 → 关闭WS → 注销本插件创建的KVM会话（仅在profile已验证的接口）→ DELETE本插件自己的Redfish session Location → 释放HTTPS/转发通道 → 停止并join route IO owner → 逆序释放SSH hop → 主线程释放帧纹理和CPU lease → 清零凭据/token。整个链只处理当前 KVM owner 的资源，不释放其他 Tab 的传输或正在运行的转发。

不能DELETE用户Chrome的会话，也不能注销账户下所有会话。若OEM KVM注销路径尚未验证，不猜测DELETE资源，关闭WS并让服务端过期，同时在诊断回执中准确标记远端会话状态未确认。本地资源释放与远端注销结果分开：网络不可达不应永久保留CPU帧/密码，但仍不得把远端注销标为成功。`awaiting/unknown/released`沿用SessionHost语义，旧generation完成消息由release_stale回收，不能重新挂回tab。

日志/诊断脱敏覆盖Password、Authorization、X-Auth-Token、Cookie、Sec-WebSocket-Protocol、AUTHKEY、session id及登录响应正文。禁止自动记录KVM画面和键入内容；调试协议使用合成图案与脱敏字节向量。测试凭据经交互内存或安全测试注入传递，不写脚本常量、命令行参数、环境转储或git。

### 11.3 通知只由宿主呈现

创建稿与旧异常入口均使用按route区分的测试、保存后及统一启动状态；直连使用空route，单跳是多跳列表的一种有效取值，不再维护单独的单跳创建流程。启动覆盖气泡的标题栏开关/关闭保留读回基线。新建跳板出口引用现有SSH编辑器的原生组件/副本，不重画SSH外壳。Figma仍是有限状态原型，输入值为脱敏预置；不连接真实服务器，不实际保存资产、认证或执行电源/启动写入，不替代zenit运行验证。启动设备×Once/Continuous×UEFI/Legacy的三主题组合，以及关闭/跨菜单返回、执行读回已接线；多跳失败夹具按0/1/2跳与反向顺序保留原路径。原型使用显式状态和覆盖层表达草稿保留，产品实现应使用一个动态草稿对象，不照搬帧数量或在菜单内各存一份值。任意输入、并发服务端变化和全部历史基线的撤改组合仍须运行实现验收。Figma的定时跳转只便于演示网络进度，产品只能按真实事件前进。

多跳板、两种连接入口、控制权申请/移交、电源与启动项已在云端Present实际点击验证。三主题两跳/反向路径失败后的重试均进入对应完整路径的统一启动，Dark另验证返回编辑保留反向路径；Light、Sauber已复验模式/持续生效/设备互不重置、关闭重开、跨菜单返回及执行读回。[本轮定向验证](../DEVELOPMENT/V0.2.1_STATUS.md)记录实际点击与边界。最新导出、布局诊断、交互读回和验证范围见[Present完成记录](../DEVELOPMENT/V0.2.1_STATUS.md)。此前视觉评审见[原记录](../DEVELOPMENT/V0.2.1_STATUS.md)，旧截图不再作为本轮UI执行依据。

路径原型采用两台预置SSH主机，覆盖0/1/2跳、更换身份和反向顺序；产品仍支持最多8跳。SSH示例地址203.0.113.10、10.20.0.5不构成到目标BMC可达的实机证据。原型不能穷举任意配置、凭据和跨菜单组合；实际输入/保存/网络/管理写入仍须在实现阶段验证。

## 13. 有针对性的验证与验收标准

### 13.1 自动验证

- 清单：`bmc_ikvm` 通过插件宿主里校验假插件的同一套结构检查；不在向导、设置、AI 枚举或会话创建里为它增加分支。保存/临时配置、旧 SSH/SFTP 配置不变、未声明服务不报 ready。
- 协议：拆包/粘包、WS continuation/control frames、OEM 104/105/106、只读/独占/共享上限、未知security/encoding、异常尺寸/压缩数据、分辨率变化和旧generation消息。
- 隔离：同一 SSH 资产同时存在原终端、原转发和两个 KVM，native Session/channel/取消源/监听器分别独立；原会话关闭/转发停止与 KVM 关闭/重连互不影响；无原会话也能从配置建立。
- 配置：离线保存、测试临时资源、引用修改/删除/错协议、重复资产/规范端点、长度超限和一致快照冲突、自动重试冻结和手动重连重解析，缺凭据挑战；配置中不持久化展开路由或动态端口。
- 路由：0/1/2/8跳及9跳拒绝的本地可控替身，增删/调序后按新顺序认证，末端BMC不作SSH登录；HTTPS+WS并发，SSH断开、BMC端口关闭、host key变化、取消与逆序释放；验证同一libssh2 Session没有并发owner。
- 输入/几何：Retina、fit/100%、黑边、中心/四角、拖出边界、按钮mask、功能键/修饰键、弹窗/切tab/失焦/重连release_all，无按键重复发送。
- 通知：所有结果从controller进入NotificationHost；同operation阶段更新不重复弹出，unknown只查询，关闭不取消，多窗口/后台/Popover避让及权限拒绝。
- 管理：默认无更改不发送、恢复默认只关闭覆盖、AllowableValues过滤、403、二次认证必需/查询失败、200/204/202/task、ETag412、响应丢失、重复点击、同会话/跨 Tab 写锁、前置过期、旧owner、超时后仅查询且不自动重发。
- 生命周期/内存：连续打开关闭10次、失败中取消、重连时关闭、释放状态未知、不同tab独立、secret/token清理、CPU/GPU占用回落；文档复核不视为这些运行验证已通过。

### 13.2 真机验收

读操作可在用户提供的连接上验证；电源/启动写操作会影响实机，必须在明确维护窗口且用户授权的具体动作下进行，文档研究不自动重启服务器。必须记录每项是“实测”“前端可见”“未验证”，不能把模拟成功贴成实机完成。

| 范围 | 必须实际观察的结果 |
| --- | --- |
| 经跳板连接 | 无Chrome/Netcatty依赖，应用连接SSH并到达BMC，画面持续工作 |
| 图形操作 | 用户可控制远端GUI/BIOS中安全页面；鼠标定位与键盘功能键正确，工具栏有独立本地焦点 |
| 画面 | 真实首帧/后续帧、文本清晰、分辨率改变正常；无信号不误报鉴权失败 |
| 控制权 | 只读无法注入；占用显示准确；不抢占既有用户；授权变化撤回输入 |
| 电源 | 选定一个允许动作在维护窗口执行；HTTP与真实状态分别记录；正常动作失败不升级强制 |
| 启动 | 备份原值，应用一次受控更改并读回，在约定时恢复；Once语义在真实启动后验证或明确未验证 |
| 恢复 | 人为中断本应用专用路由后恢复；旧输入不重放、WS重新认证、完整帧恢复 |
| 关闭 | 应用自己创建的会话注销结果、通道/线程/纹理释放，无孤儿端口，无影响其他SSH/BMC会话 |
| UI对照 | 同尺寸导出Figma与实际zenit窗口，检查布局/字号/颜色/图标/焦点；不能只凭编译成功 |

性能作为工程验收目标而非已测数值：在可控本地链路与1080p图形测试中，持续交互目标20–30fps（受BMC实际输出限制），端到端输入显示延迟目标p95≤200ms；用户内网实机同时记录链路RTT、BMC出帧与应用解码/上传耗时，不能将链路瓶颈掩盖成达标。UI线程不做网络等待；帧队列有界、内存不随运行时间增长、静态画面无无谓60fps整帧上传。
