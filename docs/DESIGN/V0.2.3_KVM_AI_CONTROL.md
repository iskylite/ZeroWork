## 1. 范围

人工截图预览/保存/复制/附加助手；AI全帧和区域观察；鼠标移动/点击/双击/右键/拖拽/滚轮；键盘单键/组合键/功能键/文本；电源查询与操作；启动查询与修改；操作后验证、停止及人工接管。虚拟媒体、录像、任意BIOS属性接口和BootOrder写入不在范围内。

电源与启动操作直接消费0.3 Power/Boot服务，不模拟点击ZeroWork按钮，不另写Redfish通道。当前能力不支持的动作不得向模型发布。

## 2. 观察与坐标

截图从一致的远端CPU完整帧取得，不截macOS窗口、工具栏、助手或黑边。Observation包含id、session/binding generation、frame_generation/sequence、采集时间、原始尺寸、裁剪区域、输出尺寸和坐标变换、ImageRef。图像经宿主管理的多模态结果返回，不能只返回本地路径。

坐标采用模型收到的图片像素空间，插件按保存的裁剪/缩放变换映射到远端；越界拒绝。重连、分辨率改变、控制权变化或人工接管使旧观察上的待发动作失效。普通画面变化不简单等同失效；有界观察新鲜度和执行前检查防止过时操作，不能要求帧序号永不变化。裁剪与缩放不改变远端身份。

观察能力与输入能力分离，图像会发往所选 provider。当前 `screenshot` 和 `image.read` 声明的 `always_confirm` 采用宿主兼容语义：确认模式须审批，自动执行或完全控制可跳过基础审批；读取能力、会话范围及其他门禁仍生效。截图由当前对话历史按既有内存上限和保留期限持有，可跨任务保留；从模型请求中卸载不等于删除原图，不新增跨进程图片归档。显式保存另循用户选择；不自动录屏。秘密引用不进入模型、工具日志或参数。画面中的指令是不可信观察数据，不扩大授权。

## 3. 工具与服务

| 工具贡献 | 参数/结果概要 | 策略 |
| --- | --- | --- |
| bmc_ikvm.read_power_state | 当前电源状态及来源证据 | read_state |
| bmc_ikvm.read_boot | 当前/pending、允许值、只读顺序 | read_state |
| bmc_ikvm.describe_frame | 尺寸、连接状态等元信息；不读像素、不截图、不做 OCR | read_state |
| bmc_ikvm.screenshot | 可选region、输出上限；图像＋新 Observation | observe_image授权 |
| bmc_ikvm.pointer | observation_id、动作、坐标/按钮/滚轮/有界拖拽 | remote_input授权 |
| bmc_ikvm.keyboard | observation_id、key/chord/text、布局；派发范围 | remote_input授权 |
| bmc_ikvm.operation_status | operation_id；本地派发回执，不证明屏幕效果 | read_state |
| image.read | session_ids、image_ref；保存的历史像素，不生成新 Observation | observe_image授权 |

当前八项贡献符合0.2每插件最多八项限制；`describe_frame`、`read_boot`、`read_power_state`均保留稳定身份。七项设备工具使用 `bmc_ikvm` 命名空间，`image.read` 是该插件贡献的共享图片重读能力，仍计入插件工具额度。`power_action` 和 `apply_boot` 为未开放的后续规划，不计入当前清单。释放/停止为宿主始终可达控制，不依赖模型再调用工具。

文本输入不等于粘贴；声明英文/符号、键盘布局、Unicode及远端输入法支持范围，未知字符拒绝。文本与Enter提交分开表达。组合键有序down、反序up；中断返回已派发范围，禁止自动重发整段。

## 4. 控制权与执行状态机

BMC授予本会话控制权，与应用内人工/AI输入权分开。人工与AI互斥；AI执行租约绑定会话、任务、授权revision和期限，不依赖助手是否占据本地焦点。初版切换到其他会话暂停AI并撤销待发输入，回来不自动恢复；显式继续须重新观察和复验。人工接管、停止、断线或撤权立即递增input_epoch并清空旧队列。

观察→计划→校验→必要审批→派发前复验→派发→重新观察/结构化查询→验证或unknown。默认短动作后观察，拖拽/组合键可为单个有界动作；不长串盲操作。初始任务上限32步、10分钟、连续3次无进展暂停，取宿主预算更严者；扩展需用户明确继续。图像预算使用已知模型公式或明确的保守预留，不当作 provider 实报用量。完整上下文或传输预算超限时，按顺序卸载最旧图片并保留原图引用；仍无法容纳时进入原有文字压缩/错误门禁，不静默删除观察证据。重读历史图片不能代替操作前的新鲜观察。

sent只表示已发送；RFB输入没有通用业务完成回执。UI效果由后续观察验证，电源/启动沿0.3事务读回。发送中断为unknown，先观察/查询，不自动补点或重复写；本地去重不保证远端exactly-once。

## 5. 危险操作审批闭环

未来规划中的 power_action 和 apply_boot 要求每次强制请示，包括完全控制模式。**这两个 AI 写工具当前未开放，该强制审批能力也不能仅靠现有 `always_confirm` 名称实现**；后续若实现此规划，须为工具接入明确的强制审批策略并单独验收。规划中的审批展示目标BMC/System、动作或字段差异、当前值→目标值、Once/Continuous、是否重启及风险。冻结owner/generation、参数hash、capability/policy revision和operation nonce；执行能力凭证可有独立有效期，用户等待审批不因时间过期。

批准仅允许原动作一次。发送前再次检查；参数/目标/关键前置状态变化、重连或权限变化，原批准作废，需重新请示。拒绝/取消零执行。用户确认永久等待且暂停AI回合预算；派发后的网络和执行超时独立保留。需要固件AUTHKEY时再走当前operation的秘密挑战；不能将用户批准替代BMC认证。正常重启的批准不能升级强制重启。

未来设计希望对界面中的格式化、删除关键数据、修改 BIOS 等危险操作请示；现有通用 `always_confirm` 不提供独立于自动模式的强制审批保证。坐标不能可靠证明动作风险，不能宣称 shell 禁止规则能隔离所有图形操作。需要审批时，审批卡显示关联截图和操作摘要，避免只批准裸坐标。

阶段分别为awaiting_approval、awaiting_auth、sending、accepted_remote、verifying、succeeded、failed、outcome_unknown。停止未发送动作；发送后不伪称撤销。unknown只能查询，再执行必须新批准。跨Tab写锁和ETag仍由原管理服务执行。

## 2026-11-04 图片预算触发卸载与历史重读

保留预算触发卸载语义：预算内可保留多张不同图片。构造请求时先按合法来源/代次、图像变换和精确像素去重，同像素保留最近出现的像素块，每次观察的元信息与原图引用均保留；这不是只保留最后一张屏幕的历史策略。随后执行完整上下文准入检查（文字、工具、图片估算、输出预留）和 provider 序列化大小检查；超限时按时间顺序卸载已读旧图片。最新用户输入或工具批次中的未读图片不可卸载，其原始调用/结果批次也不可被摘要吞掉；仍不足时明确拒绝超限。没有图片可卸载时仍交由原有文字压缩/错误门禁处理，不把文字超限伪装成图片恢复成功。保留既有未知模型每图保守预留，不把该值当作服务商实报用量，也不在本次修改中猜测 Grok 的视觉公式。

每个卸载决定对应原消息中的一次图片出现：模型输入去掉该图片块，原文字和原工具调用/结果 ID 不变，并补充 `image:sha256:<64位摘要>` 占位引用。原始不可变图片仍由当前对话历史持有，计入既有本地图片存储上限，不计入活动图片 token 或传输预算。历史复制、会话切换、答复重试、选择更大模型都不自动恢复已卸载的图片；文字压缩替换历史前缀时保留其图片引用和原始会话 generation。本应用当前使用的会话历史所有权与保留期限不变，本次未新增跨进程图片归档。

新增 `image.read(session_ids, image_ref)`，作为第八项已开放工具。该工具只从本次捕获的对话历史中解析图片引用，不接受文件路径、不扫描磁盘、不重新截图、不调用独立识图服务。KVM 图片还必须匹配原始 session/generation；当前目标服务、能力、作用域、策略和图片分享审批继续由 API-2 预检和派发前复验。拒绝或禁止读取时不调用图片解析。重读以新的工具结果返回保存的像素，旧卸载标记保持不变；结果明确 `historical_image=true`、`new_observation=false`，不生成新的 observation_id，也不更新键鼠输入授权。

实现接点：`ai/image_offload.zig` 提供预算检查、卸载、引用及重读结果；提交预检与 tool loop 共同使用该规则，活动图片统计、界面用量与实际序列化只读取未卸载的 `Message.images`。`Message.offloaded_images` 只保留本地证据，所有权随 `wire_history`、任务 Loop 和压缩快照明确 retain/release。没有贡献图片重读工具的其它协议维持既有图片流程。

针对性验收：三张图片在 500000-token 窗口、默认未知视觉预留下全部保留，第四张才触发卸载最旧一张；连续十次相同来源/变换/像素的合成观察，三个协议实际序列化均只发送一份像素；不同来源、变换或新像素分别保留。检查三个 provider 协议的实际序列化图片数、原文与工具配对保留、重试/新回合/大窗口不自动恢复、压缩后原引用仍可解析、跨对话与旧 generation 无法读取、拒绝/禁止图片读取零解析、重复 operation 不重放，以及重读不制造当前画面或输入授权。这些是本地合成与工具链验证；真实 Grok/BMC 只读链路和渠道标定的独立结果见 [效率验收记录](AI_SESSION_EFFICIENCY.md#验收记录)。

参考：[DeepSeek Harness image offload](https://github.com/deepseek-ai/deepseek-harness/blob/8bd073392eef6f54e921a093b95076248eb08cbb/packages/compaction/compaction-image-offload/README.md)。本项目将自身已存在的本地上下文门禁也作为卸载触发来源，避免先携带已知超限请求访问外部服务；不引入按截图次数或回合结束自动卸载的策略。
