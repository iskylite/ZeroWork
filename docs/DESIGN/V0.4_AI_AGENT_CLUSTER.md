## 1. 角色与不可变边界

| 类型 | 产生方式 | 归属与职责 | 子 Agent |
| --- | --- | --- | --- |
| 独立 Agent | 从 AI Agent 连接入口新建，每次创建一个独立实例 | 不绑定连接会话；独立内容页；在用户授权后可选择任意会话/组并直接使用工具 | 可以派生 |
| 集群 Agent | 独立 Agent 经显式操作转换；可以有多个互不混同的集群 | 独立内容页；自身仍具备普通 Agent 能力；仅纳管会话 Agent，负责协作调度 | 可作为直接父 Agent 派生自己的子 Agent |
| 会话 Agent | 支持附着能力的连接会话/会话组建立时登记，使用时按需启动 | 一个逻辑会话或组对应一个 Agent；单会话严格限本会话，组严格限组内成员 | 可以派生，权限限父任务范围 |
| 子 Agent | 上述父 Agent 为明确任务派生 | 独立任务上下文，唯一直接父 Agent；不能作为集群成员、不能独立迁移 | 不可再派生 |

四类角色不是强制四层调用链。集群结构为“集群 Agent → 会话 Agent → 各自子 Agent”，集群 Agent 也可以有自己的直接子 Agent。普通独立 Agent 及其子 Agent 存在于集群之外。

硬边界：

- 新建 AI Agent 连接只创建独立 Agent；不提供绕过转换的新建集群入口。恢复既有集群是恢复记录，不是新建独立 Agent。
- 集群不纳入独立 Agent、其他集群或子 Agent。会话 Agent 同时最多加入一个集群。
- 独立 Agent 转换成功后永久终结，不存在退回、撤销为独立或恢复旧独立实例的操作。
- 会话 Agent 不能跨绑定范围；用户授权、加入集群、消息转发都不能扩大这一硬边界。只有绑定会话组的 Agent 能直接操作多个组内会话。
- 子 Agent 只与直接父 Agent 通信。集群 Agent 不得直接查看成员子 Agent 的私有对话、发送消息、委派、打断或控制它；控制请求必须交给该成员执行。
- 选择执行目标与纳管 Agent 相互独立。独立 Agent 无需建立集群即可在授权后操作任意会话/组；选择目标本身不建立成员关系。
- 所有主体共享基础 Agent 实现、Provider、附件、审批与工具结果组件；权限和生命周期由宿主检查，不以提示词代替。

### 1.1 按工作选择执行路径

先按用户目标、已有绑定、授权及局部上下文选择路径，在计划中记录负责人和选择理由；纳管不意味着每项工作都要经过完整层级。选择路径不改变角色、成员关系或授权，后续改派仍受§6.5约束。

| 工作 | 默认适合的路径 | 必须保留的约束 |
| --- | --- | --- |
| 单个连接内查询/执行 | 会话 Agent | 不增加无必要的协调回合 |
| 已有组内执行相同检查 | 组 Agent，必要时派生自己的子任务 | 逐目标能力/授权、部分失败和统一结果；不能把绑定外目标先拼进组 |
| 多个成员独立调查并交叉验证 | 集群分工，会话 Agent 保留局部上下文 | 已纳管成员优先承担其工作；证据交换不共享私有对话 |
| 多目标变更且步骤有依赖 | 集群维护计划，各负责人受控执行 | 明确前置条件、停止条件和验收，不承诺跨目标回滚 |
| 长时间等用户或依赖 | 持久任务与事件等待 | 不要求页面保持可见，不等于应用退出后持续执行 |

独立/集群的直接执行仍按§4、§6.5使用既有授权；不为减少协调成本静默绕过成员或改写工作项负责人。是否派生孩子以可独立交付、可验证及并行收益为依据，不为形成层级而拆任务。

## 2. 创建入口、转换与成员管理

### 2.1 从 AI Agent 连接开始

新建菜单/连接入口提供“AI Agent”，经标准插件创建入口建立独立内容页，不要求主机资产、SSH 或本地终端。模型未配置时仍可进入页面并配置，发送前提示准确缺项。

页面提供“启用集群”动作，以及自然语言路径，例如：“把生产 SSH 和测试组的助手加入，协同检查故障。”模型先解析实际对象、查询归属，再调用结构化工具。明确请求已构成相应授权时不重复确认；对象重名、范围不清或需超出授权时才要求补充。用户所选权限策略要求审批的操作仍经过统一审批。

两条入口调用同一宿主命令，不在按钮和模型工具中维护两套转换逻辑。UI 文案使用“启用集群”，避免用“启用 AI Agent 模式”描述一个本来已经是 Agent 的页面。

建议工具契约：

| 工具 | 关键输入与行为 |
| --- | --- |
| `agents.list_session_agents` | 按名称/状态/所属会话/组查询，返回稳定 Agent ID、绑定与当前集群归属；可见不等于可纳管 |
| `cluster.enable` | 当前独立 Agent、预期 revision、请求幂等键、初始会话 Agent ID 集合、明确授权范围；原子转换并纳管；返回新的集群 Agent ID 与交接回执 |
| `cluster.add_members` | 已存在集群、成员 ID、预期归属/权限 revision、幂等键；仅接受会话 Agent |
| `cluster.remove_members` | 集群、成员 ID、任务处理方案与预期 revision；撤销该成员协作授权并移除 |
| `cluster.get` / `cluster.list_members` | 返回允许公开的集群/成员状态、数量和任务摘要，不泄露私有对话 |

显式“启用集群”可不选择成员，创建空集群；自然语言要求加入指定成员时，转换和首次纳管为同一事务，不能失败后留下意外空集群。成员增减可以通过按钮或模型工具完成。成员数量变为零时仍为集群，显示“尚无成员”，不自动退回。

### 2.2 转换是单向交接，不是可逆标记

建议使用独立的旧、新 Agent ID，使“旧独立 Agent 已终结”具备可审计事实：

1. 校验当前独立实例、权限、初始成员、单集群归属及插件能力。转换前置失败不改变旧 Agent。
2. 进入 `converting`，冻结旧 Agent 新任务。旧 Agent 其他运行回合、待批操作和自己的子任务须按§6.6、§7.1完成控制生命周期收尾；控制/资源清理未知时阻塞转换，不以模型回复完成或远端结果未知的标签替代清理证据，不重挂仍运行的子 Agent。
3. 准备新集群记录、权限快照与 AI 对话续接记录。转换工具返回内部 `handoff_pending` 后将本回合停在宿主交接点；等待集合排除这个调用本身，不能在 controller/UI 线程等待自己结束。释放事务锁后等待其他任务清理，回到提交点重新校验 revision。
4. 按§11.2的单一持久化提交点提交：旧 Agent 标为 `converted`，记录 `successor_agent_id`；建立新集群 Agent；登记初始成员独占归属；建立新的对话续接记录和 Tab→Agent 引用；按§2.2.1交接当前转换任务的执行归属及同一预算。持久化成功后，当前及其他窗口更新投影。
5. 宿主将成功回执写入旧对话结束事件及新对话交接事件，只由新 Agent 继续后续工作。旧运行 generation、待批令牌、回调和执行入口全部失效。

旧独立 Agent 从活动列表和可恢复列表消失；历史审计记录只读保留并可跳转后继集群，不具备恢复旧 Agent 的入口。当前内容页位置保持，Tab 标题、图标和状态随事务一起切换。历史上下文通过不可变引用续接；仅当前转换调用对应的逻辑任务按§2.2.1交接，不复制其他运行任务、旧请求现场或执行权限。

事务提交前失败可撤销准备状态并保留原实例；提交后失败只能恢复集群记录，不能复活旧独立 Agent。崩溃恢复、重试和多个窗口重复点击用同一幂等键及唯一后继约束，保证只有一个后继实例。

#### 2.2.1 当前转换任务与预算交接

自然语言转换调用所在任务保留同一 TaskId、root_task_id、创建来源和交付物；任务记录区分初始执行者/对话与当前执行者/对话，并维护 executor_revision。最终转换提交原子地将当前执行者改为新集群 Agent、当前对话改为续接对话、递增 executor_revision，关联转换 operation；同一任务及预算始终只有一个活动执行归属。按钮仅要求启用集群时，其宿主控制任务遵循同一预算结算和幂等原则；未请求后续工作就不自动启动新模型任务。

模型请求/token/工具次数的上限、累计消费、未使用预留、已保守计入的未知 usage，以及现有时间预算、deadline 和已记录的人工等待暂停/恢复状态，均在同一任务账本中保留，不给新 Agent 再初始化一份额度。旧子任务先收尾并只向原账本结算一次；准备和清理沿用原计时规则，不借转换额外暂停或重置预算。提交前若任务已取消或有效 deadline 已到，取消转换意图并按真实清理回执解除冻结；已提交后预算不足则阻止后续模型/工具派发，不能回滚角色或按新页面/Provider 默认值补满预算。

旧调用、执行尝试、审批及回执保留原 Agent/ConversationId，不能改挂新主体。新主体使用原用户授权范围与目标当前能力重新签发 scope，不继承旧批准或因纳管自动扩权；宿主将后续执行的来源登记为新 ClusterId，保留转换前来源供审计。迟到回调须校验 executor_revision，只能补原请求事实或按原请求去重结算 usage，不能关闭当前任务、启动旧执行者或增加预算上限。转换重试及提交后崩溃恢复均定位同一 TaskId、后继与账本；进程重启仍遵守§11.3、§11.4的明确恢复和预算门禁。

#### 2.2.2 转换调用与工具批次边界

第一版要求 `cluster.enable` 是所在 Provider 响应中唯一的工具调用。Loop/Manager 在本批任何调用派发前预检完整批次；只要其中包含转换调用且调用数大于一，就按原顺序为每个 call 写入一次 `ExclusiveToolCallRequired` 未派发结果，整批不执行查询、副作用、审批或转换准备，也不冻结旧 Agent。不能执行转换前的调用后才发现冲突，不能挑出转换单独执行或将其他调用自动转移到新 Agent；本次模型/token 及工具循环额度仍按原规则记账。全部工具对闭合后，模型可在下一轮按原授权和剩余预算单独请求转换。

合法的单调用转换按§2.2返回内部 handoff_pending 并挂起旧循环，不向 Provider 提前发送成功或发起下一轮。成功时，旧 call 的最终交接结果及完整工具对按§11.2随最终 state/outbox 发布；新对话只引用已闭合的历史并使用新主体请求表续行。提交前失败/取消只在旧对话闭合失败/取消结果；提交结果未知时保持门禁并按原 operation 对账，不让旧循环自行重试。批次重试沿原 turn/call 账本返回既有结果，不重复补结果或绕过派发预检。session→group 沿 PATCH 的旧批次屏障收尾规则处理；其他挂起工具遵守§6.4.1。

### 2.3 成员归属

纳管时绑定具体 `AgentId`，不能按名称或当前活动页签定位。已在另一集群的成员返回明确冲突，不能静默抢占。转移必须先处理原集群任务、撤销协作授权并移除，再加入新集群。

成员退出仅停止/撤销原集群来源的任务权限，不删除 Agent、AI 对话、连接配置或底层连接。执行控制或本地资源清理未知时保持“退出中/阻塞”，不能把同一成员交给另一个集群继续执行；仅远端业务结果未知但控制资源已安全释放时，按§7.1保留原任务证据及禁止重放约束，不阻塞成员接受新的独立授权工作。

单会话 Agent 和包含该会话的组 Agent 是不同主体，可以分别加入不同集群；这不会产生双重 Agent 归属，但会产生资源重叠，须经过§8的统一目标仲裁。

### 2.4 与 PATCH 的 session→group 交接明确区分

| 项目 | 已有附着对话建组 | 本版启用集群 |
| --- | --- | --- |
| 触发 | 附着助手经 host.create_group 受控建组 | 独立 Agent 经 cluster.enable 启用集群 |
| 对话 | **保留同一 ConversationId**，initial_owner 不变，owner=session→group，binding_revision 递增 | 旧对话关闭；**新的 ConversationId** 通过 continued_from 续接 |
| Agent | 源 session Agent 留存；为新组登记 group 会话 Agent，当前对话归给它 | 新建集群 AgentId，旧独立 Agent 永久 converted |
| 集群关系 | 源 session Agent 的既有成员关系不动，新组 Agent 默认未加入；必须单独显式纳管 | 初始成员与角色转换同一元数据事务提交 |
| 历史与授权 | origin_agent_id/origin_binding 保留；旧批准与旧 binding 回调作废，组内目标重新冻结 | 旧 generation/批准/回调作废；历史引用不携带权限 |

会话 Agent 的绑定身份自身不改为另一个对象；变化的是当前对话及其当前任务的承接 Agent。源 session Agent 之后仍可新建自己的对话，不复制或抢回已交接对话。session→group 不可逆，不提供把该对话再改回 session 的操作。不得把它实现成 cluster.enable，也不得随着对话移动自动迁移集群归属。用户来源任务可在原建组授权覆盖的范围内以新 binding revision 续行，但须重新签发执行 scope。若被交接的是集群来源任务，对话移动不把该任务的协作授权带给未纳管的新组 Agent；交接后将该任务置为 blocked 并关闭派发门禁，需明确纳管及重新委派。这里重新委派是对原 Task 的明确续行授权和 scope/revision 更新，不另建同一工作项的副本，仍须通过§6.5的原尝试及改派门禁。

第一版不交接运行中的子 Agent。派发实际建组操作前，先持久登记交接意图，冻结本 Task 的新工作及子任务创建；由源 session Agent 收齐该 Task 所属孩子及受影响执行的控制/资源收尾证据，并只结算一次预算。触发建组 call 不进入等待自己的集合，无关用户任务不被取消。未收尾的孩子仍归原父级，不能让新 group Agent 接收其控制权或假装成为直接父级；清理未知时不派发建组。已安全关闭但结果未知的事实按§7.1保留，不因交接转成成功或重放。宿主已建组后的恢复只依据交接前已保存的收尾证据推进，不补造证据。

组建立仍由现有 lifecycle controller 完成。V0.4 对 `prepareHandoff/commitHandoff` 增加 Agent/Task 关联投影，交接意图保存 group、原/新 Agent、同一 ConversationId、受影响的当前 TaskId/预期 executor_revision 及 HostOperationId。核实宿主组提交回执、沿 PATCH 的屏障闭合旧批次全部工具对后，在同一次 Agent state 提交中发布对话的当前承接 Agent/绑定关联，以及该 Task 的当前执行者、同一当前 ConversationId、递增的 executor_revision 和交接回执；assistant_store/视图据稳定 ConversationId 刷新投影，未对齐时不能派发新一轮。任务的初始执行者/对话、TaskId/root_task_id/parent_task_id、initiator/创建来源、集群来源和工作项关联不改写，同一预算的消费、预留及暂停账本不重置。旧请求/审批/执行尝试保留原归属，旧 executor_revision 回调只补原事实或去重结算 usage，不能续行或终结交接后的任务。

宿主组已建立而 Agent 元数据未发布时保持交接冻结，恢复按原 HostOperationId、TaskId 和预期 executor_revision 补齐一次投影，不再次创建组、不重复递增执行归属版本；宿主结果未知时保持待核实并禁止旧绑定继续执行。该 Agent 元数据提交不包含宿主组日志或其他存储文件，不得宣称跨文件原子提交；明确恢复、预算不足及授权复验门禁仍然适用。

## 3. Tab 名称与 AI 对话属性

### 3.1 Tab 命名

- 默认标题分别为“独立 Agent”“集群 Agent”；同类多实例由宿主提供稳定序号消歧，不因关闭其他 Tab 重新编号。
- 支持别名，采用“独立 Agent · 排障”“集群 Agent · 排障”等类型前缀形式。自动生成标题只更新别名；类型标识不能被覆盖。
- 转换提交时同一 Tab 更新类型前缀与图标，保留别名/位置/用户设置；其他窗口的导航、切换器、任务链接同步。准备中可显示“转换中”，不能提前显示成功。
- 会话 Agent 附着面板不修改其底层连接 Tab 名称。AI 对话标题、Agent 内容页标题、连接 Tab 标题分别存储。

### 3.2 对话来源与当前归属

AI 对话至少记录：

| 字段 | 契约 |
| --- | --- |
| `ConversationId` | 独立于 AgentId、连接 SessionId、TabId |
| `origin_agent_kind`、`origin_agent_id` | 创建时来自集群/独立/会话/子 Agent，创建后不可改写 |
| `owner_agent_id` | 当前承接 Agent；session→group 交接可改变，创建来源不变 |
| `origin_binding` | 创建时的会话/组绑定快照；独立与集群为空，不伪造连接绑定 |
| `cluster_at_creation` | 可选创建时集群来源；成员后续退出不篡改历史 |
| `initiator`、`task_id` | 用户直接发起或某个父级/集群委派；不与 Agent 类型混用 |
| `continued_from` | 转换时续接的旧对话 ID，可空；不是迁移旧权限的通道 |
| `state` | active/closing/closed/archived；关闭不等于删除 |

列表/属性浮窗显示“来源：独立 Agent / 集群 Agent / 会话 Agent”；子 Agent 显示自身类型及直接父 Agent 来源。当前所属集群单独显示，不覆盖创建来源。

独立→集群转换时旧对话关闭，新对话来源为集群，使用 `continued_from` 续接必要历史。session→group 则按§2.4保留同一对话，不创建伪续接记录。用户可连续阅读，但不能把转换前的消息伪标为集群产生。子 Agent 记录明确父主体，不将成员子 Agent 直接标成集群的子 Agent。

### 3.3 会话助手的 ×

会话 Agent 面板的 × 是“关闭当前 AI 对话”，不是销毁 Agent、退出集群、断开连接或删除历史。

关闭过程先将当前对话置为 closing，禁止新回合，取消当前对话尚未派发的步骤，并停止其运行回合与子任务；收集真实清理状态后关闭/收起当前对话。存在不确定清理时保留状态提示，不声称操作已全部停止。其他对话或独立委派任务不因本次 × 被取消。

再次打开助手默认新建对话；用户可以从历史查看/显式继续旧对话，但旧审批不会恢复。后台获准的集群委派使用该 Agent 的任务对话，不自动弹出或重新打开用户刚关闭的对话。Agent 身份、会话绑定、集群成员关系始终保留。

AI 内容页的 Tab × 是关闭该内容页运行实例；其内部对话的关闭动作另行定义并标注。关闭集群内容页停用该集群协调，不将它变成独立 Agent；允许之后恢复集群本身。

### 3.4 多窗口与内容页关闭

同一 Agent 的活动内容页运行实例及其容器关联由进程级宿主唯一登记；其他窗口的导航或视图投影不产生另一个协调域。恢复一个已打开的集群时定位现有实例；已关闭的集群则经明确恢复动作建立新实例及协调代次。

| 动作 | 宿主语义 |
| --- | --- |
| 切 Tab、最小化、renderer unmount、跨窗口移动/重挂 | 只改变视图，不调用关闭命令、不撤销协调代次；不能用视图引用数降为零推断用户关闭 |
| 显式关闭 AI 内容页 Tab | 按容器身份、预期 revision 和幂等键提交关闭命令；关闭共享运行实例，所有窗口同步 closing/closed 状态 |
| 关闭包含 AI 内容页的窗口 | 对实际归属该窗口的内容页执行同一关闭流程；其他窗口的导航/只读投影不改变页面归属 |
| 窗口/应用异常退出 | 按§11.3恢复为待核实状态，不自动启动模型或重放工具 |
| 正常退出应用、系统睡眠/唤醒、网络中断 | 按§7.2分别处理，不以 renderer 卸载、进程重启或统一重试替代 |

集群关闭命令先持久化停用意图、撤销协作代次并禁止新派发，再异步收集清理回执；页面可解除挂载，清理状态继续由 AgentRuntime 持有并可从历史/导航查看。持久化失败不能报告关闭成功。重复关闭返回同一回执；旧窗口迟到的更新、挂载或恢复回调不能重新开启协调域。会话助手的 × 仍仅走§3.3的对话关闭命令。

## 4. 目标、工具与附件范围

| 主体 | 可直接操作的范围 | 扩展规则 |
| --- | --- | --- |
| 独立/集群 Agent | 用户授权的任意现存会话/组及明确授权的本机能力 | 选择并冻结本次目标；不以集群成员名单代替授权 |
| 单会话 Agent | 仅绑定会话提供的能力 | 不能发现/操作绑定外既有会话；可按 PATCH 受控建组交接，跨范围任务可交给所属集群 |
| 组会话 Agent | 仅绑定组内冻结成员 | 可选择组内一项/多项；组变化重验，不自动扩入新增成员 |
| 子 Agent | 直接父任务授予的目标和能力子集 | 父为单会话则单会话；父为组则限定组内；不能借消息或转交扩权 |

“会话 Agent 不跨会话”覆盖执行、终端上下文、远程附件浏览、会话管理和模型工具，不只是命令执行。通用用户本地附件不自动提供额外连接能力；会话 Agent 不因运行在本机而获得操作宿主 shell 的兜底通道。

独立/集群 Composer 的目标选择器支持授权会话/组及具体成员。会话 Agent 的选择器固定本会话，组 Agent 仅列组内成员。目标选择和参考上下文分别记录；选择不意味着自动读取全部日志。

工具参数必须明确目标，宿主捕获会话 handle/generation、组 revision、权限 revision、调用来源与完整参数。多目标先预检后派发；前置不满足给出逐项原因，不擅自跳过目标。批准后的组成员或连接代次变化使批准失效。执行中失败允许部分结果，不能谎称分布式原子回滚。

远程文件 UI：选择允许范围内的会话/组 → 具体成员 → 目录/文件 → 捕获附件。单会话自动填入来源但仍可见身份；不同主机同名文件不能混淆。附件保留来源、路径、时间、截断信息和内容快照。切换当前 Tab、目标选择或连接重连不会重定向已附加内容。

已关闭 Agent 面板不影响在线连接选择；连接断开时可查询/引用快照，实时能力不可用；关闭的连接会话作为历史来源选择，重新执行须通过显式打开/重连取得新运行身份。保存配置与运行会话在选择器中分组，不把离线配置伪装成在线目标。

### 4.1 独立授权入口与执行适配

新增宿主私有的 `AgentAuthority`，包含 AgentId/kind/generation、ConversationId、TaskId/executor_revision、initiator、grant_revision、可选 parent/membership/coordinator revision。`ExecutionScope` 保存本任务实际授权的 SessionHandle 集合、group revision、能力集合、权限/执行模式与来源；scope 是宿主签发的不可变引用，不接受模型自报角色、成员或授权值。子任务只能取父 scope 的子集；附着主体还必须与其实时绑定求交。

保留 `host_tools.Context` 的 session/group 非零校验，以及 `host_queries`、旧 inventory、附着 UI 的原有拒绝路径。独立/集群通过新的 agent 工具网关验证 AgentAuthority，不能制造 session=0、AI 页面容器 SessionHandle 或临时全局组来满足旧 Context。AI 页面本身不是执行目标。

落地时增加内部 `ExecutionAuthority = attached(Context) | agent(AgentAuthority, scope_ref)`，由 `agent_host_adapter.zig` 连接执行服务；现有附着工具入口仍只接受原 Context。`host_execution` / lifecycle controller 的内部授权钩子和操作日志按该显式判别类型演进，旧分支调用原校验，新分支通过 AgentRuntime 再验。只扩展授权载荷、索引和回调，不复制其命令提交、等待、取消、输入、记录逻辑。旧日志 schema 迁移映射为 attached；不允许反向推导成 agent 授权。

实际派发链为：角色工具入口 → 任务/成员/目标/审批复验 → 现有宿主 controller → typed service → 原 exec 或 PTY driver。每次输入/租约续期/读取执行记录都重验 task、scope 和目标 generation；不得只在第一次 run 时检查。审批新增 AgentId/generation/scope revision 的绑定，保留现有命令规范化哈希及精确目标校验。集群来源任务使用该成员自己的执行身份，不能借集群 authority 越过成员绑定。

独立/集群的目标发现使用单独的授权目录投影；附着 Agent 没有该入口。成员目录只向已获协调授权的独立/集群列出候选，会话 Agent 仅能读取已加入集群公开的成员摘要；摘要不提供对方会话的实时工具引用。

#### 4.1.1 贯通请求、调用与回执

以下是同一条调用链的必需改动，不能仅在执行服务末端增加 adapter。名称为内部契约示意，实施时沿用项目实际类型及内存所有权规则。

| 层次/落点 | 必须满足的契约 |
| --- | --- |
| `assistant_store` 与请求准备 | 独立/集群/子 Agent 对话可按 ConversationId/AgentId 索引且无连接 owner；附着对话保留 session/group 索引和交接语义。AgentId 不编码进旧 Owner，后台结果按原对话定位 |
| `plugin_tools.RequestTable` | 请求授权捕获为 `attached { scope, context? } \| agent { authority, scope_ref }` 的显式分支；旧 init/initWithHost 只构造 attached 并保留原校验，agent 构造不经过要求附着 Scope 的旧 init。旧 host_context 仅作为 attached 分支的兼容访问，不另存一份可漂移的权限 |
| `tool_loop` 的调用封装与去重 | Loop 当前必填的 Scope 随请求捕获一并分支化，共享解析、工具循环和 wire history；附着调用保留原 key，agent 调用键绑定 ConversationId、TaskId、turn/call 及 authority revision。内部调用封装携带授权分支，模型参数不能选择分支或写入 authority；派发前执行§2.2.2/§6.4.1批次预检，拒绝结果也按原 call 成对记录，挂起时保留所有 slot |
| 宿主网关与现有 controller | 附着分支仍调用原 Context 入口；agent 分支经 AgentRuntime 验证后形成§4.1的 ExecutionAuthority，再进入同一 controller/typed service。插件目标工具按冻结 SessionHandle 解析真实服务，不伪造调用 owner |
| 调用回执与结果接收 | 内部回执分支匹配原调用、主体代次、对话、任务、scope/权限 revision 和目标；复用原工具输出及执行证据。迟到结果可补原任务的事实记录，但不得成为当前/后继任务的新授权 |
| `turn_manager`、挂起与权限刷新 | 按§6.4.1支持内部 suspend/resume，不将等待当作普通工具返回后立即进入下一模型请求；在完整 tool_call/tool_result 配对边界刷新下一轮 RequestTable。attached/agent 分支不能因刷新互换；目标、组或权限变化时重签 scope、使旧审批失效，已派发调用身份不改写 |

独立对话 → 捕获 agent 请求表 → Provider tool call → agent 调用/审批复验 → 现有执行服务 → 原调用回执 → 下一轮权限刷新，必须先通过一个真实目标的定向闭环；随后复验附着越界、无效 Context、旧审批和旧回调等拒绝路径。新增分支不得复制一套 Provider/工具执行循环。

### 4.2 工具目录与上下文预算

§2/§5/§6中的名称是逻辑命令集合，不要求每回合全部暴露。Agent 管理命令由可信宿主贡献，不塞入 AI 插件的 8 个插件工具配额；宿主配额仍是 32。按角色、授权、当前任务阶段选择注册表中的工具集，并固定到本请求的 RequestTable；目录中不存在的调用返回明确不可用，不在执行时临时放大目录。

需要切换“成员管理/任务协作/执行”等目录时，由宿主在下一模型请求边界重建目录并保留授权 revision，既有 tool_call 仍按原表解析。预先计算插件工具数、宿主工具数和序列化字节数；超过 16/32/96 KiB 即在发送前拒绝并提示缩小本次能力集，不静默截断、不直接提高常量。新增 API 与回归用例必须覆盖混合 Local/SSH/SFTP/KVM/网页连接插件目录的最坏组合；目录可见性从不等于操作批准。

### 4.3 交付范围、上下文读取与数据来源

执行/读取目标的授权与向接收者交付数据的授权分别校验。Task 登记原请求/授权依据引用、允许的交付对象及内容范围；成员关系、依赖或一条引用都不授予原对话、完整日志或其他目标的数据权限。跨成员、父子汇报及向所选 Provider 构造请求均使用获准投影；已获授权的相同范围不重复确认，超出范围先取得对应授权。凭据和安全输入继续只走宿主服务，不写普通汇报或模型上下文。

默认上下文只放当前任务/计划摘要、目标身份、最近必要结果、阻塞与证据索引；通过有界读取入口沿 Task→工作项→attempt→ExecutionId/HostOperationId/记录按需展开。每次读取校验调用者、当前读取授权、来源、目标代次及长度/分页限制；引用只提供定位，不携带实时执行权限。历史读取与实时观察分别标记，原记录不因摘要更新而改写；过期、缺失、截断或无权读取均明确返回，不以空成功替代。

日志、网页、文件和其他 Agent 消息保留来源及数据类别，不作为宿主通知、用户指令或授权依据。模型可提出判断/计划修订，但不能据这些内容修改权限、任务来源或执行模式。接收端仅得到原获准内容的子集，不自动获得成员子 Agent 私有历史；宿主负责引用/交付范围校验，父级负责审查自己形成的摘要，不能承诺自动识别任意自由文本中的全部敏感信息。本版复用已有记录和内容引用，不新增全局共享记忆或向量数据库。

## 5. 会话管理与 Agent 管理工具

本版目标是覆盖连接会话查询、创建/打开、修改、断开、重连、关闭，以及连接配置/历史记录的显式删除；组覆盖查询、创建、改名、成员增减、解散。当前 `host_catalog` 只有 list_hosts/get_host/create_host，不能把目标列表写成已具备修改/删除 API。逐项复用现有宿主命令；没有命令或精确影响审批的动作不发布给模型，在§12阶段补齐后才开放。关闭连接、删除配置、删除记录是独立操作，不提供含混的“删除会话”包办动作。

独立/集群 Agent 可在用户授权范围使用这些工具。单会话 Agent 只查询/控制当前绑定的既有运行会话，但可读取静态主机目录，并按现有 create_host 精确审批创建保存配置；保存配置不等于打开连接。它可按 PATCH 明确请求建组、保持同 ConversationId 交接，然后在组内新建获准工作终端；这不是枚举或接管其他既有运行会话的入口。组 Agent 可在授权后通过宿主在当前组内新建工作终端，提交成员变更后重取范围快照，旧批准不自动覆盖新增目标。将绑定外既有会话加入组，仍须由用户或具有独立授权的独立/集群 Agent 发起，附着 Agent 不能先靠 inventory 发现对象再请求扩权。子 Agent 默认无生命周期管理，确需时只授予父范围内具体动作，不能自己扩大父任务范围。

Agent 管理工具与连接管理分开：新建独立 Agent、转换集群、成员增减、查询状态、委派/消息/等待/停止、派生自己的子 Agent、关闭 AI 对话。集群不能用通用 `stop_agent` 等工具绕过子 Agent 边界；所有查询和动作均按直接父级/成员关系校验。

所有副作用操作沿原有宿主命令、影响预检、审批及资源清理回执执行。认证和秘密由宿主受控服务处理，模型不读取凭据明文。工具返回结构化成功/失败/取消/清理未知，保存成功不等于连接成功。

## 6. 消息与任务协作

### 6.1 允许关系

| 关系 | 消息 | 调度与管理 |
| --- | --- | --- |
| 集群 ↔ 本集群会话 Agent | 协调运行域启动且授权有效时允许 | 集群可委派/停止自己发起的成员任务；不能停止成员所有用户任务 |
| 同集群会话 Agent ↔ 会话 Agent | 经集群消息路由与授权允许 | 信息可互通；启动协助工作经§6.4请求集群形成委派，接收方仍限自身范围 |
| 任意父 Agent ↔ 自己的直接子 Agent | 允许 | 父负责创建、继续、停止、收集结果 |
| 集群 ↔ 成员的子 Agent | 禁止直接通信 | 禁止直接控制；只能请求成员处理其子任务 |
| 会话 Agent ↔ 其他父级的子 Agent | 禁止 | 禁止 |
| 子 Agent ↔ 子 Agent | 全部禁止，包括同父兄弟 | 禁止 |
| 子 Agent ↔ 非直接父 Agent | 全部禁止 | 禁止 |

跨父任务需求必须“子 Agent → 自己父 Agent → 获准的其他父 Agent → 对方自己的子 Agent”，返回也沿父级。父级须审查并形成自己的消息/任务，不提供把子消息直接透传的代理 API。父级重新委派不迁移子 Agent 身份、不授予跨父邮箱。

V0.4 不新增跨集群自动协作、集群嵌套或未纳管独立 Agent 间的自主通信。用户可以在不同内容页各自下达任务。共享底层目标不代表 Agent 已经互通。

### 6.2 消息与执行不同

- `send_message` 投递信息，不自动启动模型回合；明确委派/继续任务才启动或排队。
- `delegate_task` 明确任务、交付物、范围、预算、关联对话与来源；成员未启动可在既有纳管授权内按需启动。
- `wait_events` 等待有界事件，避免轮询；`cancel_task` 停止明确任务，不能用消息文本替代取消回执。
- 消息含稳定发送者/接收者、task/message ID、回复关系、membership revision 与协调启动代次。去重、过期、回执和队列上限由宿主维护。
- 收到的消息属于有来源的任务数据，不是系统规则或用户授权。一个会话 Agent 请求另一个执行操作，不因此获得对方的直接工具权限。
- 单个对话默认一个活动回合；多来源请求排队，不同时修改同一对话。用户直接输入可显式打断，不能由任意集群消息抢占。

### 6.3 可实现的消息、任务及事件协议

- `send_message` 的幂等域为 sender AgentId + generation + request_key；同 key 同规范化参数返回原 MessageId，异参拒绝。收件箱先持久化再回 accepted，状态为 `queued → delivered → acknowledged`，也可进入 `expired/rejected`；投递或确认不证明模型已处理，Task 输入按§6.3.3另记处理事实。重试不重发，消息数量/字节上限触发背压；离线接收者不启动模型。
- `delegate_task` 单独创建 TaskId，写入 initiator（user / cluster / direct_parent）、root_task_id、parent_task_id、来源集群及 membership/coordinator revision、接收 AgentId、交付物、scope、预算及§6.3.1的初始计划。对外状态为 `queued → running ↔ waiting_approval/waiting_events/blocked → succeeded/failed`；取消走 `cancelling → cancelled` 或 `cleanup_pending/outcome_unknown`，由§6.3.2的分离事实派生，不作为另一份权威状态。后两者不得计入成功/已停止；资源已安全释放时可按§7.1明确处置为 closed_unverified。终态与汇总条件见§6.6。
- 用户对话与集群委派分别使用 ConversationId/任务队列，成员的用户对话不被后台任务覆盖。用户可查看或明确接管任务，接管改变来源需要宿主记录新授权；不能靠把消息复制进用户历史伪装成用户请求。移除成员/停用集群按来源和任务祖先链取消，只影响对应 cluster 任务。
- 消息/任务创建、幂等回执与待发布事件一起进入§11.2的元数据事务；事件通过 outbox 发布，消费者以 event_id 去重。派发前重新验证成员/运行代次，失效消息返回 rejected 原因，不交给新集群或新启动代次。不能承诺网络副作用恰好一次，只承诺宿主接单去重与禁止未知结果重放。
- `wait_events(after_cursor, max_events, wait_ms, mode=bounded)` 只返回调用者有权读取的事件，wait_ms 范围为 0–30 秒；返回 next_cursor、has_more、timeout。bounded 模式超时后允许一次正常任务续行，dependency 模式须显式指定获准的依赖/事件条件，才可在单次窗口超时后持续等待。cursor 包含授权域和 stream_epoch，事件保留已过期返回 gap + 最新快照/续读位置，不以空数组掩盖缺失。超时不代表任务完成，快照不泄露子 Agent 私有邮箱/控制句柄。
- 每个 Agent 的收件箱有界，每个 ConversationId 只有一个运行回合；父等待孩子或等待事件时释放 Provider 并发槽，不持有资源短锁等待，长期租约按§8.2判定。父/子及成员协助形成的任务等待依赖都必须无环；等待自己的转换调用同样禁止。业务状态事件驱动 UI 和 wait，不用模型定时询问状态。

#### 6.3.1 任务计划、修订与授权依据

Task 持有原用户/直接父级请求和授权依据的不可变引用，以及单调 plan_revision。每个计划版本冻结目标槽位、工作项及负责人、必需/可选标记、依赖条件、交付物验收、失败策略和预算约束；依赖条件须区分“成功”“已结束”或明确证据条件，不从一条自然语言消息推导控制关系。初始计划允许先登记已知调查步骤，不要求在排障前穷举未来步骤。

- 宿主计划修订命令携带 TaskId、预期 plan_revision、修改原因/依据、受影响工作项及幂等键；原授权内追加调查可由有权执行者/直接父级提出并经宿主校验，不强制新建根任务。扩目标、扩能力或增加预算必须有对应的新授权；模型总结、外部内容和结果消息不能成为授权依据。
- 修订在同一事务登记新版本、受影响项和派发门禁，保留旧计划及执行事实。明确缩权先撤销受影响未派发调用/未消费批准，再处理正在执行的操作；不能等下一次模型请求才撤权。未受影响且目标、参数、授权均未变化的原 operation 可继续，不能借修订改参数复用批准。
- 调用、输入快照、汇报及验收记录计划版本。派发前检查工作项仍属于当前有效计划及授权；失效未派发 slot 返回 PlanChanged/ScopeRefreshRequired。迟到结果保留原版本事实，只有经宿主确认仍满足当前验收条件的证据才可复用；不能用旧计划完成当前任务，旧 usage 仍只向原账本结算一次。
- 已取消/已处置任务不因修订或新输入复活。已终结任务的新工作形成新的获准请求并引用原结果；未知尝试的门禁仍按§6.5、§7.1保留。明确用户意图已覆盖的相同范围不重复确认，关键歧义才请求补充。

#### 6.3.2 权威状态与展示状态

以下事实在 Task 中分别记录并由同一 owner 推进；不用单一 state 枚举覆盖所有维度，也不为每个维度增加独立运行主体。

| 维度 | 权威事实与约束 |
| --- | --- |
| 运行阶段 | queued/running/waiting/blocked/cancelling/ended；Provider 回合结束不直接改成 ended |
| 等待原因 | none、事件依赖、人工审批/输入、资源或预算，关联实际等待/待处理记录；人工计时规则见§6.4.1 |
| 业务结果 | pending/succeeded/failed/cancelled/unknown 及逐项证据；子项失败不等于根任务已终结 |
| 控制与资源 | active/cleanup_pending/released/transferred 及真实回执；本地释放不等于远端结果已知 |
| 恢复门禁 | open/suspended/recovery_required，预算不明另记 budget 阻塞原因；门禁关闭时不得新派发 |
| 明确处置 | 无处置或§7.1的 closed_unverified 事实；不改写原未知结果 |

对外 waiting_approval、blocked_budget、cleanup_pending、outcome_unknown、closed_unverified 及忙碌计数均由上述事实按统一谓词派生。succeeded/failed/cancelled 作为终态展示仍须满足§6.6的收尾条件；unknown 无处置且未核实不伪装成 ended。恢复门禁关闭时可叠加显示原业务/清理状态，不用“已暂停”掩盖仍在运行的外部操作。加载校验和 UI 使用同一组合法组合/转换规则。

#### 6.3.3 输入归属、事件分流与处理水位

需要模型处理的 TaskInput 登记稳定 input_id、任务/来源、单调输入序号、计划/执行归属版本及内容引用；与原 MessageId/event_id 关联去重。明确指向 Task/工作项/回复关系的补充交给唯一任务处理，话题相似不足以附加；超出范围由有权协调者形成计划修订或新请求，不复制为第二份工作。普通成员消息仍不自动启动模型，已满足获准等待条件时才按§6.4恢复。

- 区分 accepted、delivered、included(request_id) 与 handled：included 仅表示已进入持久化的真实请求上下文，不证明 Provider 已处理或业务已落实。请求发送前保存 input_id 集合、上下文引用/摘要、plan_revision、执行归属及配置版本；汇报/宿主动作提交后才记录逐输入处置和处理水位，不能把序号中间的空洞一并确认。
- 输入投递后、入请求前崩溃继续保留未纳入状态；已 included 但未 handled 的输入保留原请求/历史关联，明确恢复后按原账本处理，不再次追加相同消息。持久化失败不声称已读。任务收尾与接纳新输入同事务串行，不能在已接纳且未处理的任务指令仍悬空时报告交付完成；须处理、明确拒绝/转交，或保留可定位待处理项并保持未完成状态。终态后的新输入不自动重开旧任务。
- 工具/执行回执由宿主直接更新对应 attempt 和等待条件；普通进度只更新摘要，不逐条唤醒集群模型。只有新规划、授权范围内的协助或确需判断的结果进入模型回合。可合并尚未消费的进度投影，但保留事件 ID/顺序和原始证据；取消、撤权、审批决定、最终回执及用户指令不能合并丢弃。

### 6.4 协助请求、等待与恢复执行

成员之间的 `send_message` 只交换信息。需要对方启动工作时，成员调用逻辑命令 `request_assistance`，提交原协作 root_task_id、请求任务、候选成员、工作项、交付物、申请预算及幂等键；宿主记录请求并通知集群，不直接启动接收成员。纯用户任务须先在明确的集群协调授权下建立协作根任务，不能将本会话任务的授权直接用作跨成员授权。

集群收到请求后，在原授权范围决定委派或返回阻塞；请求本身不要求用户重复批准。实际委派的 initiator 仍为 cluster，调度父任务为集群的协作根任务，另记有界 requester_task_ids 及依赖边关联请求者；保留原 root_task_id、成员/协调代次及取消来源。预算从该根任务的剩余池预留，请求者与接收者不各获得一份新额度。接收成员的 scope 取协作根任务授权与自身绑定的交集，集群不能透传请求者的 scope；候选可见或已纳管都不能补足根任务缺少的目标授权。重复请求或重复事件不得产生第二个接收任务。

AgentRuntime 保存等待条件、依赖任务 ID、最后事件位置及预期代次，按以下规则推进：

- 明确委派使获准任务进入队列；普通消息只持久化和通知 UI，不唤醒空闲 Agent。协助请求可以唤醒其已获准的集群根任务处理调度。
- 任务等待时进入 waiting_events，释放模型槽和资源短锁，保留对话执行顺序；同一 Agent 的其他就绪任务仍可调度。单次 wait_events 最多等待 30 秒；bounded 超时返回后可执行备用决策，只有显式 dependency 模式才保留持续等待订阅。两者超时均不自动取消依赖任务或免除交付/收尾责任。
- 依赖结果、匹配显式等待条件的消息、审批回执或协助请求到达后，宿主按等待条件和事件 ID 去重，重验任务/权限/成员/协调代次，再将一次续行入队；不为同一对话开启并行回合。消息仅满足已有获准等待时才能恢复该任务，不能据此创建新任务。续行在原工具调用配对闭合后使用结果或受控通知进入下一轮。
- 新增等待边前检查所有任务依赖，自等待和 A 等 B、B 等 A 均返回 DependencyCycle，不让任务占槽互等。原任务取消、权限失效或依赖失败时按事实解除等待并返回相应状态。
- 等待注册与任务状态持久化；同一运行代次内，通知丢失可从权威任务状态补齐。进程重启按§11.3进入 recovery_required，不能借补投事件自动续跑旧任务。

#### 6.4.1 原子等待与工具循环挂起

在宿主工具结果之外增加内部运行控制结果 `continue | suspend(wait_id) | finish`；suspend 不序列化为模型可调用的授权或伪成功结果。Manager 收到 suspend 后将本任务的工具循环现场交还 AgentRuntime，不调用 nextRequest、不占用模型槽。每任务独立持有 ConversationId、turn/call、工具账本、wire history、累计 usage、剩余额度、时间预算/暂停账本及授权快照；其他任务不能通过 clear/reset 覆盖它。现场只保留拥有所有权的值或受控引用，不保留栈上 budget/CancelToken 或 UI 指针；异步服务仍借用的令牌/现场由 Runtime 持有到 join/解除借用，不能在挂起时提前销毁。恢复时重建受 Task 取消门禁和账本重算的有效 deadline 约束的运行令牌。

挂起现场覆盖整个 Provider 工具批次：保存原 assistant tool_calls、参数哈希/顺序、各 slot 的未派发/已派发/已闭合事实、当前索引及原请求表引用。同一批次按原顺序派发；遇到审批/用户输入时暂停当前 slot 和后续 slot，不能提前执行后面的副作用。决定到达后先复验原调用再推进；取消/撤权/范围变化按事实闭合当前及剩余未派发 slot，已派发项只按原 operation 对账。全部真实工具对闭合后才能发送下一 Provider 请求或刷新请求表；不重放前面已完成的调用，也不把它们改挂另一任务。

为避免显式等待阻塞同批的未派发工作，第一版 wait_events 与 cluster.enable 一样必须是唯一调用；完整批次预检在任何派发前发现混合等待即整批返回 ExclusiveToolCallRequired，每个 call 只补一份未派发结果。其他工具在执行中触发的人工等待使用上述批次现场，不承诺整批副作用原子性。Manager 新增接收 Task 现场/预算的续行入口，不调用会建立新预算的 resumeAnswer；人工等待也必须移交宿主待处理记录并释放不必要的工作线程，不能只释放逻辑模型槽却一直阻塞同步 Broker。

等待记录包含 TaskId、wait_id/revision、mode、条件及依赖 ID、stream_epoch/cursor、原工具调用引用、预期执行归属/运行/权限代次、单次等待到期时间和任务有效 deadline/timer revision。mode 为普通枚举字段，dependency 需要宿主校验明确条件，未指定则采用 bounded；不得在超时时静默改为 dependency。由进程级 owner 在同一元数据事务中检查授权、依赖环及当前任务结果/事件位置：条件已满足则直接记录就绪结果；否则登记等待。结果提交同样在该串行边界检查等待记录，消除“检查后、登记前结果已到达”的丢唤醒窗口。不能依靠再次通知或模型轮询补救这一竞态。

| 竞争/触发 | 唯一可提交的处理 |
| --- | --- |
| 单次 wait_ms 内条件满足 | 将原等待工具调用补齐一次 tool_result，持久化一次续行票据；恢复前再次复验权限及任务状态 |
| bounded 的 wait_ms 到期但任务仍有效 | 原调用只补齐一次 timeout 结果，关闭本次订阅并登记一次正常续行；预算允许时模型可执行原授权内的备用分支，不需要等待新事件。迟到事件不能再次恢复旧 wait_id，仍保留依赖任务及其收尾责任 |
| dependency 的 wait_ms 到期但任务仍有效 | 原调用只补齐一次 timeout 结果；保留明确条件的订阅并继续 waiting_events，不启动空模型回合。后续匹配事件通过已闭合工具对之后的受控通知恢复，不再为原 call 写第二份结果 |
| 结果已到但尚未消费，或 outbox 重投 | 以 `(TaskId, wait_id, wait_revision)` 原子设置/消费续行票据；消费后永久关闭该次等待，重复事件不能再建票据，新等待必须使用新 wait_id。任务状态可补齐通知丢失，但一次等待最多入队一次续行 |
| 当前 timer revision 对应的有效 deadline 到达、取消或授权失效 | 先关闭续行门禁，撤销等待/票据，并按实际原因补齐尚未闭合的工具对，再进入任务收尾；已排队的旧续行也不得调用 Provider |

进程级调度器维护单调时钟定时器，覆盖机器排队和机器依赖等待；宿主登记的有效用户审批／输入请求无等待到期时间，包括§8.3需人工决定的预算、恢复、验收或处置，不包括尚需机器清理的责任。按以下规则暂停自动执行时间预算，用户操作恢复后继续剩余预算，不依赖可见页面或 Provider 回调检查 deadline。自动续行继续消耗原模型/工具次数、token 和时间预算；恢复前若有效预算已耗尽，走取消/清理而不重置 Provider 默认超时。进程重启只恢复等待及账本的待核实投影，明确继续前先对账未闭合工具对和原操作，不以重发副作用修复记录。

- **等待原因由宿主判定**：持久记录直接人工等待、传递人工等待或机器等待及其有效依赖/请求引用，不能由模型声明 waiting_approval 或一条消息自行暂停预算。只有任务自身及其未决所属子树、有效协助依赖都被人工决定阻塞，且没有就绪/排队/运行的独立机器工作、机器等待或待执行的机器清理工作时，才是纯人工等待；否则其自动时间继续计费。
- **沿实际依赖逐级传播**：父任务或请求者处于 dependency 等待、其全部未决责任都已归为纯人工等待时，暂停该祖先自身的计时，并继续向上判定。只传播最小等待原因，不暴露成员子 Agent 私有对话或控制句柄。一个孩子等待批准不暂停整棵树；仍有另一个孩子运行/排队或机器依赖未完成时，祖先和相应机器分支继续计时，不能借人工分支延长其机器预算。bounded 等待仍有超时后的正常续行路径，不按纯人工等待传播暂停。
- **原因与计时一起提交**：登记/撤销人工请求、依赖变化及机器分支收尾时，同一 Agent state 事务按既有无环依赖关系重算受影响任务/祖先的等待原因、已消费时间、剩余时间及 timer revision；暂停时撤销原有效 deadline 定时器，恢复时只用原剩余时间，并取自身与仍有效的祖先时间约束中更小者重算。旧 timer 回调按 revision 拒绝，不能在暂停后误取消任务；暂停也不能复活已耗尽或已取消的任务。人工请求因任务取消、撤权或其他仍在计时的机器分支导致祖先预算耗尽而撤销时，仍走真实取消/收尾，不等价于人工等待自身过期。dependency 的 wait_ms 仅闭合单次工具窗口，不结束人工等待或启动模型。

宿主不自动重试空等待；连续无新事件、cursor 推进或业务进展的等价等待受原 round/tool 次数、有效 deadline 和调度约束。允许有界超时后的业务决策，不等于建立模型定时轮询。超时与取消/deadline 竞争以事务提交和派发前门禁复验为准，取消或过期后不得为超时备用分支调用 Provider；人工审批/输入等待仍沿用其独立暂停规则，不按 wait_ms 自动结束。

### 6.5 直接执行与成员分工

默认由已纳管成员承担其绑定范围内、需要局部上下文的工作，集群负责分解、跨成员协调和汇总。临时未纳管目标或用户明确要求集群直接执行的工作，经独立授权直接调用；成员暂不可用时报告阻塞，不静默改为集群代执行。用户授权允许改派时可采用直接执行，仍须完成原工作项交接和目标/审批复验。

宿主在根任务目标计划中分配稳定 target_slot_id，关联明确的逻辑 binding_id；组目标展开到获准的具体成员槽位。工作项按 `(root_task_id, work_item_id, target_slot_id)` 记录唯一执行负责人（AgentId/TaskId）和 routing_revision，不以运行期 SessionHandle 作为工作项身份。同配置的不同逻辑连接仍可对应不同槽位，不按主机名称或资产自动合并。

每次获准执行在派发意图事务中分配 attempt_id，同 key 幂等重试复用原 attempt_id，保存所属槽位、实际 SessionHandle/generation、ExecutionId/HostOperationId、routing_revision 及结果/清理证据。明确重连或重新关联同一逻辑目标时保留槽位，重签 scope 和审批；派发前检查该工作项全部历史尝试，旧尝试未知不能因 handle 改变而被绕开。替换为另一逻辑目标须明确修订目标计划，仍保留原槽位及未决尝试，不能自动新增槽位重试原副作用。

整体委派按同一工作项交接负责人；拆分为子步骤时分配各自 work_item_id、保留来源关联并冻结父项自身执行，不能由父项继续执行已分出的范围。直接执行、成员委派及其子任务均按该规则登记，避免集群与成员重复接管。重复提交返回现有任务/结果，不从自然语言或命令文本相同推断工作项相同。

改派先冻结旧负责人新派发，再确认原执行已停止且资源已释放，或已完成并直接复用结果，最后递增 routing_revision。cleanup_pending/outcome_unknown 时保持阻塞，不换 request_key 重试副作用；旧负责人的迟到回调仅补原记录。跨根任务的目标竞争仍走§8资源仲裁，工作项去重不代替目标锁或权限检查。

### 6.6 任务完成、依赖取消与预算结算

Provider 回复完成只结束一次回合。任务创建时登记交付物、必需/可选工作项及失败处理方式，每个计划版本冻结并按§6.3.1显式修订；默认采用 continue_collect。失败事实、处理中的状态与最终 failed 终态分别记录，不能在首个成员失败时直接终结根任务。未达交付物时可交付部分结果，但不能仅凭模型总结将任务标为成功。

- **成功**：自身交付物和必需依赖已满足，所属子任务/协助工作已收尾，没有未核实派发意图、活动审批或等待；资源已释放，或已有明确移交/保留回执。存在未知或 closed_unverified 工作时，父任务不得标为 succeeded，须继续待核实或按相应失败/用户处置结果收尾。
- **继续收集**：continue_collect 下先记录 pending_failure，根任务保持 running/waiting_events；其他独立且已授权的排队/运行工作继续派发和收集。需要前置项成功、但该前置项已失败而无合法输入的工作记录 DependencyFailed；原授权内的失败/超时备用分支按其条件继续执行。剩余工作及资源收尾后，必需项失败才将根任务置 failed；可选项失败按原交付物要求聚合。该路径不因“已观察到失败”冻结整棵任务树。
- **取消剩余工作**：采用 cancel_remaining 时，记录失败原因后立即冻结相应任务树的新派发，并沿直接拥有关系取消未决工作；根任务在收尾完成后进入 failed，不能因执行了取消过程就误记为用户取消。
- **用户取消/授权撤销/过期**：立即关闭相应派发门禁，覆盖 continue_collect，沿任务树及协助依赖规则推进取消，结案时记录 cancelled 及具体原因，同时保留此前失败事实。以上任一路径只有所属执行控制和资源收尾后才能进入 failed/cancelled；不确定项保留 cleanup_pending/outcome_unknown，或经§7.1明确处置。模型回复、取消请求已接收均不能充当收尾回执。
- **拥有关系与等待关系分开**：parent_task_id 决定子任务控制及预算归属，depends_on/requester_task_ids 只表示依赖。取消请求者 A 时，在同一事务解除其协助依赖；协助任务 B 已无有效请求者且根计划不再需要时，由集群这个直接任务拥有者发出取消。B 的成员父 Agent 负责其子任务，A 不取得控制 B 或其子 Agent 的权力。
- **共享协助**：第一版仅允许同一根任务内、明确引用相同工作项及兼容交付/授权范围的请求者共享结果，不按文本相似或跨根任务自动合并。仍有其他有效请求者则 B 继续，取消 A 不影响其结果；新增请求者与 B 进入 cancelling 的竞争按 revision 串行处理，已取消任务不自动复活。依赖边计入元数据/队列配额并参与环检测。
- **预算与聚合结果**：子任务的 token、模型请求和工具次数按§11.4只向所属父账本归集一次，父子经过时间不相加；未使用预留仅在实际收尾后返还。父任务保留对未决子任务的预算责任，不能因本回合结束提前返还。usage 无法核实时按预留保守计费而非退回可用额度。聚合结果逐项列出成功、失败、取消、未知及用户处置，不以“部分结果已返回”推断整棵任务树已结束。

### 6.7 结构化汇报、证据与交付验收

成员/子任务通过 TaskReport 汇报，至少携带 TaskId、executor_revision、plan_revision、单调 report_seq、已处理输入集合/水位、progress/ready/blocked/failed/waiting 类型、简短结论、证据引用及可选的具体人工请求。相同序号同载荷去重，异参拒绝；宿主只接受该执行者真实请求中已 included 的输入处置，不能让报告确认未纳入上下文的输入。旧执行归属或旧计划的报告只能补原事实，不能结束当前任务。子 Agent 仍只报给直接父级，父级审查后形成自己的获准汇报；报告不能代用户批准。

证据引用包含目标槽位/实际身份代次、原 attempt/操作/记录、观察时间及有序 revision（若原服务提供）、观察区间、完整性/截断及未知标记；模型推断与宿主执行事实分开。无共同可信时钟时不按不同主机时间戳武断排序或宣称一致快照；冲突或过时证据在聚合中明确列出，必要的重新观察也消耗原授权和预算。

每个交付物明确验收方式：工具/配置变更采用原服务回执与必要后置检查；诊断报告采用可追溯证据、覆盖范围和未核实项，不能声称宿主证明了任意语义结论。诊断能否以“不确定结论”交付取决于原计划，报告已交付不能覆盖未收尾执行的 outcome_unknown。ready 只是申请验收，宿主核对当前计划、输入处置、证据和§6.6收尾条件后才终结 Task。需要用户验收的工作保持明确待处理；新验收标准须修订计划，不能临时提高标准使任务无限延长。

依赖旧观察的操作由具体工具声明必要新鲜度或内容/版本前置条件，派发前及等待审批后重新检查；generation 不变、连接在线或模型重复原结论均不能替代这些检查。前置条件改变则返回 PreconditionChanged 并重新规划，不能用旧批准提交新的影响；不为所有工具发明统一时长的“可信有效期”。验收证据和读取入口复用§4.3、§11.2.2的有界引用。

## 7. 运行、退出与停止

集群成员关系持久化，协调运行状态独立管理。显式启用集群并打开内容页后启动协调域；空闲不持续调用模型，切 Tab/最小化不停止。停止当前回复只停止当前任务，停用集群或关闭其内容页才关闭协作门禁。

内容页关闭以§3.4的宿主命令为准，视图卸载和跨窗口重挂不触发停用；关闭后的清理回执不依赖页面继续存在。

停用时立即禁止新跨成员消息/委派，撤销当前协调代次；待执行的协作步骤取消，已执行请求按任务树向各直接父级发出取消。成员父 Agent 再停止自己的子任务，集群不直接调用子 Agent。取消失败/远端未知单独记录，不用父任务已取消推定所有进程已停止。

成员由用户直接发起的任务及其子任务不受其他集群任务停止影响。集群停止后会话 Agent 可单独工作和使用自己的子 Agent，但跨成员协作不可用。其他集群不受影响。

恢复集群时换新协调代次，重新验证成员、任务权限及目标；不自动重放旧消息、旧审批和未确认副作用。关闭底层连接时立即撤销该绑定的实时能力，保留 Agent 历史和成员信息，并显示连接关闭。重新打开获得新运行身份，必须明确重新关联，不能按主机名称继承旧批准。

子 Agent 完成后释放模型/工具运行资源，保留只读结果。未完成任务可由同一个直接父级在有效授权内继续；不能换父复活。父 Agent 被转换/销毁前完成或停止其子任务，禁止产生无主执行者。

### 7.1 清理证据、未知结果与明确处置

分别记录执行控制/本地资源证据与远端业务结果。前者包括旧执行入口及输入租约已撤销、本地 IO/引用已释放，或已有明确的用户接管/资源移交回执；后者保留原成功、失败或 remote_effect_unknown。用户接管和本地释放不能证明远端进程已退出。

| 控制/资源证据 | 远端业务结果 | 允许的推进 |
| --- | --- | --- |
| 尚未释放或清理未知 | 任意 | 保持 cleanup_pending；阻塞关联成员转移、父 Agent 转换/销毁及工作项改派，用户处置也不能替代资源释放证据 |
| 已安全释放/明确移交 | 已核实 | 按§6.6收尾及回收未使用额度；移交本身只有符合原交付物时才算任务成功 |
| 已安全释放/明确移交 | 未知 | 原工作项停在 outcome_unknown 并禁止自动重试；成员可退出及接受新的独立授权任务，不携带旧 scope/审批，原执行历史和未决结果继续保留 |

提供逻辑命令 `reconcile_task` 按原 ExecutionId/HostOperationId/记录读取新证据；使用宿主只读证据投影及当前获准的历史读取权限，不恢复旧成员关系或实时执行 scope，没有新证据仍返回未知，不重新执行原命令。对于控制资源已安全收尾但结果持续未知的任务，用户可明确选择“保留未知结果并放弃自动重试”，由宿主记录精确处置范围、用户来源、时间、证据引用及新 revision，将获准执行链关闭为 **closed_unverified**。该状态只表示控制生命周期已关闭，结果仍未知，不计入 succeeded/cancelled 或“远端全部停止”。父级或集群可请求对账/用户处置，不能替用户决定；已有明确用户意图时沿统一策略执行，不额外重复确认。

closed_unverified 前仍须清理所属任务树、撤销等待/审批并按§6.6解除协助依赖；usage 未知的预留按保守已消费记账，不能以处置退回额度。之后可回收不再需要的运行/收尾预留，但原未知回执、处置索引和禁止重放标记保持有效。后续用户如需再次执行，应形成明确的新任务/工作项并关联原未知尝试，经过新的目标授权与审批，不能恢复旧 key 自动续跑。迟到证据只补原记录及重新核实的结果，不复活已关闭任务或撤销用户处置。

### 7.2 正常退出、睡眠唤醒与离线

以下由进程级宿主推进，与页面是否可见无关；持久化 intent、账本及回执仍走§11.2。第一版不承诺应用退出后继续协调，也不新增云端控制面或独立 daemon。

| 事件 | 运行、计时及恢复契约 |
| --- | --- |
| 正常退出应用 | 先关闭全局新派发门禁，持久化退出意图及任务/输入/批次账本，再按原服务取消、释放或已有明确移交收尾；退出清理初值最多等待 5 秒，不无限阻塞 UI。超时保留各未决 operation 与真实未知状态，不声称远端进程退出；下次启动按明确恢复门禁。持久化失败报告失败并保留本地门禁，强退按异常恢复处理 |
| 系统即将睡眠 | 尽可用的系统通知窗口关闭新派发、保存睡眠边界和计时账本，暂停本地自动时间；不依赖睡前一定完成清理，也不假设远端任务随本机暂停 |
| 系统唤醒 | 在恢复派发前核实睡眠区间、目标/连接代次、租约、未决操作和 Provider 请求。可证明的睡眠区间不计入自动执行时间，重算有效 deadline；无法核实剩余预算则 blocked_budget。未决副作用先按原 ID 对账，不重发。宿主代次/权限未变且证据、预算可核实的任务可在原授权内续行；显式停用或 recovery_required 任务仍须明确恢复 |
| 网络断开/Provider 连接中断 | 区分尚未派发、请求结果未知与外部命令仍运行。机器断网/退避等待照常计时，人工等待仍按独立规则暂停；只在原预算内重试允许重试的模型请求/幂等投递，不能自动重连目标或重放命令。scope/目标失效立即关相应入口 |
| 进程崩溃/强退后启动 | 对账原 state、journal 和输入/请求水位，再进入 suspended/recovery_required；不能因网络恢复或迟到事件自动启动模型 |

睡眠计时采用宿主可核实的睡眠边界，不依赖各平台单调时钟是否包含睡眠；Provider/远端服务各自的超时事实不因此延长。5 秒退出清理值是待定向验证的内部初值，不是已测保证；未完成本地收尾也必须保留恢复证据，不用新请求代替缺失回执。

## 8. 权限与资源冲突

有效权限 = 用户授权 ∩ Agent 角色硬边界 ∩ 任务委派范围 ∩ 目标当前能力。状态可见、内容读取、消息、委派、资源执行分别授权。纳管不等于完整历史共享，也不等于任何命令免审批。

会话 Agent 的单集群约束由宿主原子登记，两个集群同时纳管只能一个成功。成员/权限撤销使未执行调用失效；正在执行的副作用按真实取消能力处理。

连接会话是最终资源仲裁对象：独立 Agent、集群直接调用、成员 Agent 及组 Agent可能访问同一目标。只读操作按服务能力并发；关闭/重连等生命周期操作与冲突写操作需排他或排队。锁定与权限复验发生在实际派发前，不能仅按不同 Agent ID 判断无冲突。外部操作者或不同连接访问同一远端资源仍可能竞争，不承诺宿主锁能覆盖外部进程。

审批绑定原始任务、执行者、目标代次、完整参数和权限 revision，父级转交不能洗掉原来源或升级权限。同一审批事实在授权位置展示并只处理一次；集群 Agent不能代用户批准成员操作。

子 Agent 的私人对话、控制句柄和收件地址不向集群暴露。集群可以读取会话父 Agent 发布的子任务总数、忙碌/阻塞摘要及获准交付结果，但这不是对子 Agent 的直接查询或交互。

### 8.1 后台审批票据与展示归属

审批由 AgentRuntime 按 TaskId/OperationId 持有稳定 ApprovalTicketId，绑定原调用、执行者/代次、授权 revision、精确目标及代次、完整参数哈希；用户决定无等待到期时间。每任务最多一个活动票据，其余需审批步骤沿原工具队列等待；总量纳入任务及元数据接纳配额。现有 Broker 的单一 live_context/entry 通过每任务隔离实例或等价多票据适配复用，配置/取消一个任务不得覆盖其他任务票据。

- 后台任务未打开助手时，审批投影仍可从全局待处理通知及任务详情定位。集群页面可显示数量和定位入口，用户进入原审批投影后查看完整命令/目标/影响；不自动重开已关闭的成员用户对话，不向集群模型暴露私有历史或批准句柄。
- 视图只订阅票据，关闭/重挂窗口不删除事实。任务取消、集群停用、成员撤权，或执行者/绑定/精确目标代次及授权 revision 改变，使相应未消费票据 revoked 并记录具体原因；用户决定不按时长置 expired，撤销／拒绝均生成一次等待结果，清理不依赖页面继续存在。纯人工等待按§6.4.1暂停自身及符合条件的祖先时间预算，不能用旧 deadline 撤销票据；其他机器分支导致的有效任务取消仍可撤销。进程重启后旧票据不恢复有效批准，必须重新预检。
- pending → approved/rejected/revoked 与票据 revision 的决策原子完成；多个窗口重复操作返回同一回执。批准后尚未派发的票据仍可因目标或授权变化而撤销；派发时原子消费有效批准并重验任务、权限和目标，副作用沿原 operation 幂等接单。已消费或失效票据不能批准新参数或新执行尝试。集群 Agent 没有代用户批准入口。

### 8.2 资源等待与任务等待的交叉约束

任务依赖无环不能替代资源仲裁。宿主记录等待资源及其实际 Task/用户持有者；建立任务等待或资源排队前检查已知拥有/等待路径。若父任务持有子任务/协助工作所需的排他资源，又要等待该工作完成，第一版返回 ResourceDependencyConflict，要求先安全释放或取得明确移交回执；不自动抢占、换负责人或向子 Agent 透传 lease。用户持有资源时显示精确冲突，不取消无关用户工作。

多目标短锁按稳定顺序尝试；一次申请不能满足时释放本次已取得的短锁再排队，不持部分短锁等待审批、子任务或其他目标。长期 PTY 输入租约由原执行服务持有，不能仅因 Provider 槽释放就认为已释放；仅当有真实等待路径冲突时阻止等待，不把正常长命令全部强制交还。租约/拥有者变化后重验排队项，取消/撤权先移除其资源等待，新负责人仍经过§6.5的原尝试门禁。

资源仲裁范围仍是宿主可识别目标；同远端资源经不同连接或外部进程发生的竞争，依赖具体工具前置条件及真实结果处理，不按名称猜测全局远端锁，不承诺覆盖宿主外部行为。

### 8.3 统一待人工处理投影

AgentRuntime 持有按 Task/原 operation 关联的有界待处理记录，kind 区分 approval、input、budget、recovery、disposition/review；记录具体问题/目标/影响、可选动作、依据引用及预期任务/计划/权限 revision。approval 继续引用原 ApprovalTicketId，其他种类不能伪装成批准票据。计划修订按受影响项复验，未受影响且授权/目标/参数均未变化的原 operation 不仅因全局计划版本增加而强迫重复决定；不能据此把旧批准搬到新影响。一个执行步骤只消费一个有效决定；重复或迟到决定返回原回执/明确失效原因，不能操作新参数或另一任务。

各类决定分别走现有批准、输入、预算追加、恢复、验收或§7.1处置命令并复验，统一列表不授予跨种类权限。用户无等待到期时间；关闭/重挂视图不等于回答、拒绝、取消或授权。任务终结/撤权使相关记录失效，不能留下可操作的旧入口；费用/预算、恢复证据或新目标不足时显示准确阻塞，不以统一“继续”按钮掩盖影响。已授权的独立工作可继续，不为一个问题冻结无关任务。

## 9. 简洁状态 UI 与详情浮层

主 AI 助手/页面只保留角色、关键状态和数量，不常驻完整成员树、完整任务日志或大量状态列。

| 位置 | 常驻摘要示例 | 点击后的详情 |
| --- | --- | --- |
| 独立 Agent | 独立 · 空闲；子任务 2 | 自己的子任务列表/状态；启用集群入口 |
| 集群 Agent | 集群 · 协作中；成员 4 · 忙碌 2 · 待处理 1 | 成员浮窗、增减成员、授权状态、任务摘要；成员子任务仅父级发布的摘要 |
| 会话 Agent | 所属会话/组；集群名称或“未加入”；子任务数量 | 所属集群是否启动、同级成员公开状态、自己的子 Agent 详情 |
| 子任务详情 | 任务状态、父 Agent、必要目标 | 结果、阻塞、权限与停止操作，仅直接父级或用户有权操作 |

任务详情同时展示控制资源状态和业务结果；closed_unverified 默认使用“已结束 · 结果未核实”，后续对账获得新证据时另列最新结果并保留“关闭时未核实”的事实，不能改写原任务为成功或远端已停止。后台待审批可从摘要/全局待处理定位§8.1的原审批投影，未知结果可进入§7.1的对账/用户处置入口。

全局待处理与任务详情统一投影§8.3的不同人工事项，优先显示用户现在能处理的决定，并显示原任务、精确目标、原因及决定后的影响。正常进度留在任务详情；通知仅用于可用交付、必要决定或无法继续的阻塞，相同事实去重，不逐成员重复播报。汇总不得隐藏未授权、失败和未知项；列表计数由同一宿主查询派生，与可定位记录一致，不要求打开成员助手才能处理后台事项。

摘要计数从宿主事件产生，不触发模型查询；忙碌、待审批、失败等精确语义在浮层展开。非颜色唯一编码，提供文字和键盘可访问入口。短说明用气泡；有按钮、列表和滚动内容的详情使用可聚焦浮窗，不能只放 hover tooltip。危险操作的目标/影响与审批仍常显在原审批区，不以精简状态为由隐藏。

显示全局应用导航供用户定位多个 AI Tab，不把所有 Agent 的详细状态注入每个 AI 页面。未加入集群的会话 Agent 不显示其他集群内部信息。

视觉实施复用已有组件与 tokens，以可编辑 HTML/CSS 制作必要状态基准，再通过 zenit-html-ui 实现；本文未定义猜测像素，不代表原型/原生 UI 已验收。

## 10. 插件设计：事实连接与附着功能组件

### 10.1 对第 13 条的结论

AI Agent 应作为正式的独立内容页连接接入；会话助手作为附着功能组件接入。这里“事实连接”指宿主真实管理的独立运行实例，不要求必须建立网络 socket。AI 运行实例无需创建假 SSH 或隐藏终端。

插件不宜简单分成互斥两种插件枚举；应允许**同一插件声明两类贡献**，分别是 `StandaloneContribution`（独立内容页）和 `FeatureContribution`（附着功能）。AI 插件同时提供二者，共享 Agent 核心和视图组件。

| 方面 | 独立内容页连接 | 附着功能组件 |
| --- | --- | --- |
| 创建入口 | 新建/连接标准动作 | 宿主对可附着对象提供入口 |
| 身份 | 自己的运行实例与 Tab；关联独立/集群 Agent | FeatureInstanceId + 明确宿主绑定；关联会话 Agent |
| 生命周期 | create/cancel/close、资源回执、恢复 | attach/update_binding/suspend/detach/dispose；对话关闭另行处理 |
| UI 槽 | 标准内容 renderer | 宿主分配的面板/浮层槽 |
| 服务 | 自身声明的运行服务与工具 | 从宿主受限借用所需 typed service，不自行克隆连接 |
| 存储 | 可选创建配置 + 运行状态 | 组件偏好 + owner 绑定状态，不伪造主机资产 |
| 权限 | 与任务目标分别授权 | 受宿主绑定硬限制，再与任务授权取交集 |

“连接插件的复用”是复用注册、服务、工具、配置事务、受限 UI、事件和生命周期基础设施，而非把功能组件包装成另一个实际连接。组附着由宿主组上下文提供成员能力投影，不要求每个连接插件实现自己的组助手。

### 10.2 已有基础与真实缺口

当前 `src/host/plugin_registry.zig` 的 API 为 2，已有 `connection`、`quick_create`、`session_factory`、typed services/tools、AI context 和 renderer 注册。`publish` 当前要求每个 manifest 都有 session factory 与匹配的内容 renderer；`src/host/plugin_ui_contract.zig` 的 ContentMount 绑定 SessionHandle。已有 AI context 是连接向助手提供上下文，不是可挂载功能组件的生命周期契约。

因此，不能声称 API 2 已完整支持功能组件。V0.4 必须补充能力：

1. 按贡献类型校验：独立贡献要求创建/运行工厂和 renderer，纯功能贡献要求 FeatureFactory 与受限面板 renderer，不要求伪造 session factory。
2. 提供 FeatureHost 和 `FeatureBinding = session(handle) | group(id, revision)`；支持资格、唯一性、服务需求及失效通知。连接/组具备附着资格时即登记轻量身份，登记不依赖打开面板，不启动模型。
3. 提供 FeatureMount：只含槽位、tokens/主题、功能实例身份、绑定快照、受限服务解析器和事件出口，不暴露全局 App/UI 根。
4. 服务借用显式携带目标 handle/generation/权限 revision；组件持有的是可撤销引用，不获得连接所有权。组按目标解析服务，缺能力成员如实禁用，不扩大或伪造共同能力。
5. UI unmount 只释放视图，不能等同销毁 Agent；suspend 撤销不可用的会话能力；detach 是明确解除功能绑定，完成任务清理后 dispose。×关闭对话不调用 detach/dispose。
6. 插件配置/工具/服务按稳定命名空间注册，依赖和 API 版本在发布前验证，卸载/移除能力不得留下悬空句柄。

目标契约示意（非已实现 Zig API）：

```text
PluginManifest
  metadata, dependencies, settings, service/tool definitions
  standalone?: { creation, runtime_factory, content_renderer }
  features[]: { id, supported_bindings, required_services,
                feature_factory, panel_renderer, attachment_policy }

AI plugin
  standalone: quick_create -> IndependentAgent; page renderer
  feature: eligible(session | group) -> registered SessionAgent
           authorized task -> lazy runtime; open panel -> assistant renderer
  shared: AgentRuntime, conversation/composer, attachments, approvals, results
```

本版采用 **宿主 API 3 + API 2 兼容消费**，具体顺序如下：

1. 引入版本化入口与归一化 manifest。保留 API 2 的原字段语义/默认值，将 session_factory、workspace_kind、renderer 归为 standalone；新 feature 只能经显式 API 3 声明。不能让共享默认常量变更把旧声明自动标成 API 3。
2. `plugin_registry.publish` 先按来源版本验证，再统一验证贡献/依赖/服务；纯 feature 路径跳过 standalone 工厂/renderer 要求，但必须验证 FeatureFactory、binding 类型及 panel renderer。混合贡献分别验证，任一失败均不发布。
3. 同步改造 `plugins/linked_plugins.registerAll` 的精确版本检查及 legacy descriptor/registration 默认值，保证 Local/SSH/SFTP 仍经 API 2 适配。新增版本协商函数供所有注册路径共用，未知版本拒绝。
4. `PluginHost.apis` 的 host 依赖解析按兼容表处理 major=2/3，不能在当前按 id 唯一的列表里直接塞两个 host 条目，也不能将依赖 major=2 强改为 3。非 host 服务及插件依赖继续精确匹配各自 major/type token。
5. API 2 的 ContentMount、renderer update/unmount、session factory、typed services/tools 通过适配保留行为；API 3 feature 使用另一个 mount 契约。持久配置 payload_version 与宿主 API 版本独立，升级宿主不触发无关配置迁移。
6. [V0.3 BMC iKVM](V0.3_BMC_IKVM.md) 和 [V0.5 网页连接](V0.5_WEB_CONNECTION.md) 的 API 2 声明继续作为合法输入由兼容层消费。不能要求它们为采用 V0.4 重写协议、frame sink、凭据或执行实现。

兼容验收必须实际走 builtin legacy/API 2 bundled/API 3 standalone/API 3 pure feature/API 3 mixed 五种发布路径，并覆盖 host major=2 依赖、无效版本/缺 factory/错误 service token、renderer 迁移窗口能力校验。只测试 manifest 常量或新 AI 插件注册不算兼容完成。

### 10.3 AI 插件的具体接入

- AI 内容页优先复用 `quick_create` 语义：新建独立实例无需强制保存连接资产。若以后提供可保存模板，只保存模型/偏好等配置，打开模板仍新建独立 Agent，不能保存“新建即集群”的捷径。
- 标准运行容器可以继续采用宿主 SessionHandle 管理插件实例；其含义是 AI 页面实例，并非被 Agent 附着/操控的连接会话。业务 `AgentBinding` 对独立/集群始终为空，AI 对话使用另一 ID 域。
- AI 页面自己不声明会话助手附着资格，避免“Agent 页面再附着 Agent”递归；也不作为远程终端/文件目标或集群会话成员。选择器依据能力与绑定类型排除，而非靠名字判断。
- 支持的连接插件提供上下文/工具服务和附着资格；宿主挂同一 AI feature，连接插件不各画一套 AI 助手。
- 不具备 exec 的文件连接或 KVM不因附着 AI 就获得 shell。功能可用范围取实际服务快照，不绑定到“连接在线”等单一布尔值。
- 转换只替换该 AI 页面关联的业务 Agent，保留同一插件内容容器/Tab；不重建网络连接，不影响被纳管的成员连接。
- 子 Agent 仅为 AgentRuntime 的任务实体，不创建连接资产、顶层 Tab 或附着组件。

## 11. 运行、存储与恢复的实现方案

### 11.1 模块职责及身份索引

应用进程持有一个 AgentRuntime；页面/feature 仅发命令和订阅投影，不各建调度器。至少分离 AgentId、ConversationId、ClusterId、TaskId、FeatureInstanceId、连接 SessionHandle 和 TabId。会话 Agent 的稳定键使用 Agent store 中持久的 binding_id，映射一个逻辑连接实例，不能按 AssetOwner/主机名称去重；同配置打开两次对应不同会话 Agent。在线 SessionHandle/generation 仅为当前能力，重启恢复不直接复用，重新打开后须明确重新关联。组 Agent 使用组身份，组 revision 单独递增；关闭的绑定记录仅保留历史。

Agent 记录包含 role、generation、state、binding（仅 session/group Agent）、唯一 parent_agent_id（仅 child）、successor_agent_id（仅 converted）；成员记录独立包含 cluster_id、member_agent_id、membership_revision、state。会话 Agent 同时最多一个有效成员记录，在宿主单写事务内校验唯一索引。附着 Agent 的初次登记由进程级 FeatureHost 监听连接/组资格建立事件并去重；启用功能时也对现有合格绑定补登记，不能等到用户首次打开助手。

身份登记、任务启动、视图挂载为三个独立时点：登记只创建轻量身份与资格投影，不创建空对话或调用 Provider；获准任务按需建立运行资源及任务对话；打开面板才挂载视图。未打开过助手的合格连接仍可出现在授权候选目录，纳管不会主动弹出面板。资格/服务失效时暂停相应能力，保留身份及历史；恢复服务仍按当前 generation/revision 复验，不能自动复用旧批准。

`assistant_store` 继续负责现有内容、草稿、附件、Provider wire history 等，不把连接 owner 当 AgentId。增加以 ConversationId 查询的对话元数据表，将 initial_owner/origin 与 current_owner/owner_agent_id 分开；现有附着历史按真实来源导入，未知字段保持 legacy/unknown，不猜测集群或任务来源。独立对话允许无连接 owner；这是对话存储模型的扩展，不放宽 attached Context。

Task 是工作及预算的权威记录，当前执行归属、Provider 回合、工具批次与单次 attempt 分开；继续使用现有模块，不另增一套工单/执行器框架。Store 至少索引当前 executor_revision/plan_revision、待处理输入和实际请求快照、批次 slot、TaskReport/证据引用、正交状态、人工事项及容量预留；归档与派发查询不能按当前可见页面筛选。任务生命周期由 AgentRuntime 推进，Manager 只推进所绑定 Task 的一次可挂起运行，controller/journal 保留原副作用事实来源。

### 11.2 具体持久化提交点

第一版采用**单个有界 Agent 元数据快照**（拟定 `ai/agents/state.json`），不新增数据库依赖。根包含独立于宿主 API 的 schema_version、稳定 store_id 和单调 store_revision；由一个进程级 IO owner + 排他文件锁持有，按§11.2.3校验加载，写入复验预期 revision 与磁盘摘要，禁止各窗口各存一份。快照包含 Agent/绑定/成员/任务/对话头、计划版本/修订差异、目标槽位/执行尝试、输入处理与请求/批次头、汇报/证据引用、等待/续行及人工事项、Tab→Agent 关联、转换/处置回执、任务执行归属与预算交接、等待原因/依赖引用及暂停账本/timer revision、退出/睡眠边界、容量预留、幂等索引和待发布 outbox；大请求现场/历史按§11.2.2保存有界内容引用。收件箱保存 MessageId、发送者/接收者及代次、任务/回复关系、状态、过期时间和不可变消息内容块的哈希引用。实际执行命令、凭据、终端输出仍留在现有受控服务/记录中。

`send_message` 先按§11.2.2登记内容容量/预写意图并持久化消息内容块，再将收件消息头、内容引用、发送幂等回执及 outbox 事件在同一次 state 快照提交中发布，完成后才返回 accepted。崩溃恢复从收件箱记录恢复投递状态，outbox 只负责通知；不能仅持久化 outbox 就声称消息已入箱。内容块预写后提交失败仅留下受准备意图保护或可回收的未引用块，恢复不得产生第二条 MessageId。

事务具体执行：

1. controller 解析命令并准备不借用 UI 指针的计划；规范化参数哈希与 `(actor_id, generation, command, request_key)` 一起保存。相同 key 异参拒绝，相同请求返回原 operation/后继 ID；旧主体 converted 后仍能查询其原转换回执，但不能执行新命令。
2. 在锁内校验身份、成员唯一性、revision 及预算，形成 converting 意图并持久化；释放锁，完成获准的旧任务/子任务清理。初始成员不提前对外显示已加入；并发纳管者可先成功，转换提交时若冲突则整体失败，不留下空集群。不得持锁等待 Provider、审批、子任务或宿主 IO 回调。
3. 对话必要历史按§11.2.2预留并写成不可变内容块，写完并持久化后得到哈希引用；对话头和引用在最终快照内提交。预写后失败保留准备引用，意图安全终结后才回收未引用块，不能出现已发布的新对话引用未落盘历史。当前草稿、已完成工具结果和完整 tool_call/tool_result 配对按显式续接边界整理，不复制待执行调用或审批。当前唯一转换 call 的成功回执可按待提交计划预写为完整工具对，但只有最终提交成功才能发布；提交前失败/取消则在旧对话写真实结果，预写成功块不成为可见历史。
4. 在锁内重验计划，构造完整 next 快照；写同目录临时文件，sync 文件，原子替换唯一 state 文件，再同步父目录（采用项目实际 Zig/平台 IO API）。成功后更新内存 revision，再发布 outbox/UI。**旧主体终结、新主体/对话、初始成员、Tab 关联、当前转换任务执行归属/同一预算及转换回执处于同一个文件的一次替换**，不是多个 rename 的“事务”。
5. 文件落盘/替换前失败保留上次快照；替换已发生但目录同步/结果回传失败则进入 commit_unknown，停止旧主体入口并按原 key 读取恢复，不以“返回错误”回滚成独立 Agent。平台持久化保证必须通过故障测试确认，不能沿用现有原子写函数就声称断电安全。

工程初始硬限制为 state 快照序列化后最多 8 MiB、各元数据表合计最多 8,192 条记录，其中待发布 outbox 最多 2,048 条。接纳判断同时计算已用量和§11.2.1的收尾预留，任一维度不足即背压新增工作；不能把硬上限当作可用尽的新任务额度。回收策略只归档已终结且无引用的历史。converted 墓碑、有效幂等回执和未清理任务不能因队列清理被删除。该方案用于本版本地有界协作，不要求同时改造全部应用配置存储。

现有 `lifecycle_journal` 仍是执行/生命周期副作用的事实来源，它当前的单文件原子替换不能与 Agent state 合并成跨文件事务。Agent state 只关联 HostOperationId/ExecutionId；先保存派发意图，再调用现有幂等服务，再记录回执。两次写之间崩溃按原 operation 对账；副作用已派发但无可靠回执时使用 outcome_unknown，禁止换 request_key 再执行。§2.4的建组交接走这一恢复边界，不冒称与 metadata 同事务。

#### 11.2.1 接纳、收尾容量与回收

- 新建任务、消息、成员关系、转换及副作用派发前，在同一事务预留其最坏收尾所需的元数据条目/字节、阶段 outbox 及必要内容块额度，包括取消、撤权、清理未知及最终回执。记录及回执字段必须有大小上限，大内容写不可变块后保存有界引用；不能只预留 Task 一条记录而忽略后续事件。
- 始终满足 `已用 + 尚未使用的收尾预留 ≤ 各硬上限`。额度不足时拒绝新增工作，不占用已有对象的收尾额度；接纳检查与预留提交原子完成。取消、停用、成员退出、回执对账和 outbox 确认使用所属预留推进，不因普通工作队列满而排在新任务之后。
- 收尾按有界状态阶段推进，同阶段重复回执在原记录中幂等更新，不无限追加事件；更细执行证据保留在现有 journal/recording 中。每个阶段事件及其重投复用稳定 event_id，已发布载荷不可改写。控制资源未清理的未知任务持续占用必要预留；按§7.1核实收尾或处置为 closed_unverified 后，可在通知已处理且无运行引用时释放不再需要的预留，但保留未知/处置及禁止重放索引。
- 幂等回执在原主体 generation 仍可接单、操作未核实或仍被引用时保持有效。旧 generation 永久失去接单资格后，仅已终结且无引用的回执可归档/压缩；旧 key 查询返回原回执/历史引用或明确的已归档拒绝，不能因详细回执回收重新接受请求。converted 墓碑及唯一后继索引始终保留；永久记录接近容量时继续背压新建，不能通过复活旧身份腾空间。
- 容量保证针对逻辑配额。磁盘满、锁失效或持久化失败时立即阻止新派发，保留本地取消门禁和现有服务的清理能力，报告 persistence_failed/commit_unknown 并按原 operation 对账；不得报告已持久化成功。验收分别覆盖逻辑满额下可收尾和物理 IO 失败下不误派发。

接近接纳阈值时，定向测量快照提交延迟、outbox 积压及收尾推进；IO 仍由进程级 owner 承担，UI/controller 不持锁等待磁盘。只有测量表明需要时才调整内部常量或存储实现，不预先引入数据库或额外设置。

#### 11.2.2 内容块配额、引用与回收

Agent store 自有的消息、历史续接、交付物及恢复内容块与预写临时文件共享磁盘配额，工程初值合计最多 **256 MiB**、单块最多 **8 MiB**；实际已占空间加未兑现写入预留不得超过总额。历史超过单块限制时按完整消息/工具对分块，仍受总配额约束，不静默截断或发布缺失内容。该配额不改变现有终端记录/附件服务各自的保留策略，初值须定向测量后校准。

1. 写入前在准备意图内登记 operation、内容哈希/长度、容量预留及保护引用；写完并校验/同步后，最终 state 提交将准备引用转为已发布引用并结算容量。同哈希复用须验证现有块完整性。未提交收件头不等于消息 accepted，回收器也不能删除尚有效的准备块。
2. 引用根为权威 state 中的对话/消息/任务内容、历史及归档清单、转换/恢复准备意图及其传递引用；正在读取的块另持有进程级读取租约。归档清单引用在安全提交后才替换原引用。现有 journal/recording 只保留原服务所有权，Agent 回收器不删除其文件。
3. 删除或过期消息、任务归档、交接失败后安全撤销准备、启动恢复及空间不足时触发分批回收。消息 acknowledged 本身不解除仍被任务/历史持有的引用；进程重启先恢复权威 state 和准备意图，未核实意图继续保护其块。
4. 回收与提交由同一 IO owner 串行协调；删除前按最新 state/准备意图及读取租约复验候选无引用。不能只按旧快照或文件年龄删除；新增引用提交前须再次验证块存在且完整。未引用失败预写和临时文件清理后归还实际容量，不产生用户消息或执行重试。
5. 配额不足先回收无引用块，仍不足则拒绝新增内容并返回 StorageFull；已接单收尾使用其预留。不得为接收新工作自动删除仍被引用或用户保留的历史。物理磁盘失败仍走§11.2.1的持久化失败门禁。

#### 11.2.3 格式校验、初始化与异常加载

加载按“持有单写锁 → 受限读取/解析 → 版本识别 → 结构与引用校验 → 发布只读投影/运行门禁”推进，校验完成前不启动模型、工具派发、成员变更或内容回收。除 JSON/大小上限外，至少校验身份/代次、有效成员唯一性、converted 唯一后继、任务执行归属/预算一致性、计划/正交状态合法组合、输入水位与请求/批次/汇报引用、有效人工事项、幂等与禁止重放索引，以及关键内容引用的存在性与哈希/长度；不能默认补空、静默去重或丢弃异常记录来取得可运行状态。

- **首次初始化**：仅由唯一 IO owner 在首次创建专用 Agent 存储目录、且无既有 Agent 引用或关联宿主操作证据时初始化空快照；新 store_id 在首次持久提交后才可发布。已有目录中 state.json 缺失，包括初始化中断，进入 store_missing 诊断/恢复流程，不能仅凭文件不存在判断为新安装。
- **格式/版本异常**：损坏 JSON、非法字段/关系分别报告 store_corrupt/store_inconsistent；不支持的 schema_version 报 unsupported_schema，不能按当前默认值降格解析。受支持旧版本若需迁移，只在副本上执行显式迁移和完整校验，保留原证据后沿单一提交点发布；宿主 API 升级不自动改变该格式版本。
- **引用异常**：关键历史/恢复块缺失或校验失败时报告具体引用及 content_unavailable，并保持恢复门禁；不能用空消息、空工具结果或新身份替代缺失内容。消息尚未发布的准备块不完整则保留准备意图，先按原 operation 核实，不能伪装为已入箱。
- **关闭运行门禁**：异常时保留原文件及可读取证据，提供明确标记的只读诊断，阻止新 AI 工作和自动 GC；现有受控服务的取消/释放能力继续可用。不能因解析失败重置 store、重建旧 Agent、删除墓碑或放宽授权。
- **恢复旧记录**：不自动回退到旧备份并恢复执行。恢复须核对 store_id、已知提交点、转换/幂等回执和关联宿主操作；无法证明转换及未决副作用状态时继续 recovery_required，不能让缺失最新墓碑的旧独立实例重新执行。用户确认本身不替代执行证据核验；核验后仍按§11.3明确恢复，不重放旧批准或未知副作用。

### 11.3 崩溃、旧回调与恢复矩阵

| 断点/竞态 | 必须恢复出的状态与行为 |
| --- | --- |
| converting 已保存，旧任务还未清完 | 旧 Agent 可显示但入口冻结；原任务先查现有回执，清理未知继续阻塞，不自动提交/重放 |
| 历史块准备完，最终 state 尚未替换 | 权威 state 仍为 converting；可按原意图继续或在安全清理后解除冻结，未引用历史不成为新对话 |
| 最终 state 已持久化，UI/工具回执未显示 | 只恢复新集群；旧 Agent 墓碑定位同一 successor，outbox 重投由事件 ID 去重 |
| 两个窗口同时转换或纳管同成员 | 事务 revision/唯一索引保证至多一个成功；失败者取得明确冲突/原幂等回执 |
| 同一 Provider 响应包含 cluster.enable 及其他调用 | 本批任何派发前整批拒绝，每个原 call 仅有一份未派发结果；零查询/副作用/审批/转换意图，不按转换所在位置改变结果。下一轮可单独转换，不能把兄弟调用带到新主体 |
| 转换前预算已部分消耗、提交回执丢失或旧 usage 迟到 | 同一 TaskId/根任务/账本只交接一次，执行归属 revision 拒绝旧控制回调；消费、预留及有效时间预算不因转换重置 |
| session→group 的宿主组已提交，Agent/Task 投影尚未发布 | 保持交接冻结，按原 HostOperationId 核实；旧批次闭合后一次提交对话承接关系与当前 Task 执行归属/递增 revision，同一预算不重置，不重复建组。集群来源任务仍 blocked，明确纳管及重新授权前不能续行 |
| session→group 时当前 Task 的孩子或受影响执行仍未收尾 | §2.4先冻结并由原父级收尾，触发 call 不自等待；清理未知不派发建组，不转移孩子身份。恢复只采信原收尾证据，旧孩子结果不越过新执行归属门禁 |
| 重启后原协调域/子任务仍显示 running | 恢复为 suspended/recovery_required；新启动代次重验后由明确继续动作启动，不自动调用模型或工具 |
| 旧审批/Provider/文件选择器/执行结果回调晚到 | callback 携带 Agent generation、ConversationId、TaskId/executor_revision、binding/grant/membership revision，工作项调用另带 routing_revision；只更新原记录或丢弃失效展示，不能写入后继对话、关闭已交接任务或派发新操作 |
| 计划修订、缩权与派发/旧 ready 报告竞争 | §6.3.1原子登记修订及受影响门禁，旧调用/批准失效按原 slot收尾；结果保留原版本，只复用仍满足当前验收的证据，旧报告不能终结新计划 |
| 输入已投递但未纳入请求，或请求已保存而汇报未提交 | §6.3.3保留 input_id、真实上下文快照与处理空洞；明确恢复后处理同一输入，不把投递记成处理、不在历史重复追加；收尾不能吞掉已接纳指令 |
| 多工具批次中途等审批，后续 slot 尚未派发 | §6.4.1保存整批现场并挂起，恢复/取消逐 slot 闭合，不重放前序调用；混合 wait_events 批次则在任何派发前整批拒绝 |
| 成员移除与队列派发竞争 | 撤销先落盘；派发复验归属/协调代次，控制资源清理未知保留退出中；仅业务结果未知且资源已释放按§7.1退出，不迁移旧任务/批准 |
| 等待结果/协助请求重复投递或通知丢失 | 同代次按任务状态补齐，一次等待最多入队一次续行；重启后的补投不能绕过明确恢复 |
| 结果在检查与登记等待之间到达，或超时/取消同时到达 | 同一事务判定条件/登记等待；原工具对只闭合一次，失效续行票据不触发模型，等待中的有效 deadline 由宿主推进 |
| 有界等待超时且没有后续事件 | bounded 闭合 timeout 后可正常续行到原授权的备用分支；仅显式 dependency 保留持续订阅，旧 wait_id 不被迟到事件再次唤醒 |
| 子任务等待用户决定超过祖先原剩余时长，或旧 deadline 回调晚到 | 宿主按§6.4.1将纯人工等待原因逐级传递，原子暂停符合条件的祖先并使旧 timer revision 失效；决定到达后按原剩余时间恢复一次，不能因旧 deadline 取消人工等待 |
| 一个分支等待用户，另一独立分支运行/排队或机器等待 | 机器分支及祖先继续计时；机器责任完成且只剩人工依赖才暂停祖先。机器预算有效耗尽可取消任务树并按任务取消撤销票据，不能把整树暂停或记成审批等待过期 |
| 父子/兄弟并行区间与预算结算重叠 | §11.4按量纲结算，原请求/call 去重归集；父经过时间不再加子时长，并发槽只按真实占用释放，不因更换执行者/模型重置 |
| 父任务持 PTY lease 等待需要同资源的孩子 | §8.2拒绝已知资源依赖冲突，先安全释放/明确移交再等待；不只检查 Task 环，不自动抢占用户资源或透传 lease |
| 成员失败而其他独立工作尚未派发 | continue_collect 记录失败后继续获准工作并最终聚合；cancel_remaining 才冻结/取消剩余工作，用户取消和授权撤销可覆盖继续收集 |
| 元数据/outbox 达到新工作接纳阈值 | 拒绝新增工作，已有任务仍能使用预留取消、撤权、记录未知/最终回执并回收额度 |
| 改派时原执行结果未知 | 保留旧负责人及原操作关联，阻塞新执行；迟到结果只更新原记录，不以新 key 再派发 |
| 重连/重新关联目标后继续原工作项 | 保留 target_slot_id 和历史尝试门禁；新 handle/审批不能绕过旧未知执行 |
| 请求者取消与新增协助依赖竞争 | 同事务更新 requester 集合；无需求时由拥有者取消，仍有有效需求则继续，cancelling 不自动复活 |
| 多任务/多窗口同时审批或审批视图关闭 | 票据按任务隔离，一张票据只消费一次；关闭视图不覆盖其他票据，长时间 pending 不按时长失效；任务取消/集群停用/成员撤权或执行者、绑定、目标代次及授权变化由宿主撤销一次并记录原因，迟到批准不续行 |
| 证据过时/截断/互相矛盾，或前置条件在批准后改变 | §6.7保留来源和不确定性，按当前验收检查；必要条件不足则阻塞/重新观察，PreconditionChanged 不派发改变后的影响，不能仅凭 ready/exit=0 报业务成功 |
| 引用或汇报请求超出交付范围，配置切到另一 Provider | §4.3/§11.5在读取、交付及请求边界复验数据范围和能力；不发送越权原文，不将外部内容当授权，原结果和预算不改挂 |
| 人工等待/后台执行占满任务、内存或服务容量 | §11.4背压新工作，已接单等待不按时长过期；可落盘现场按引用保留，取消/释放/对账走预留，不只限制模型槽或 ready 队列 |
| 同一 Provider 被限流，多任务同时准备重试 | §11.5共享冷却/在途约束，重试计原请求/时间/usage；取消无需等冷却，未知副作用只查原 operation，不集体重发命令 |
| 正常退出未清完、睡眠通知缺失、唤醒或断网 | §7.2保留原操作与计时证据；可核实唤醒按原授权续行，无法核实预算/执行仍受门禁；正常退出不承诺远端全停，下次启动明确恢复 |
| 统一待处理决定晚到，或健康检查发现无进展 | §8.3按事项种类及原 revision 消费/拒绝，不把补输入当批准；§11.5只补通知/投影/获准对账，合法人工等待不误报，不越权自动修复 |
| 资源已释放但远端结果永久未知 | 保留未知及禁止重放证据；用户明确处置可 closed_unverified，不误报成功/进程退出，不阻塞新的独立授权工作 |
| 内容回收与预写/新引用提交竞争 | 有效准备和读取租约保护块，删除前重验最新引用；提交失败块可回收，已发布内容不丢失 |
| 权威文件损坏/缺失、不支持版本或关键引用缺失 | 按§11.2.3关闭新工作/GC门禁并保留证据，不初始化空 store、不降格解析、不恢复缺少最新转换事实的旧备份 |
| 跨窗口重挂与显式关闭竞争 | unmount 不停用；关闭命令按 revision 提交，全窗口同步；旧挂载回调不能恢复已关闭协调域 |

转换工具使用宿主控制结果收尾：提交成功后旧对话写入终结事件，新对话写入引用同 operation 的交接事件；这些事件随权威 state/outbox 可恢复。Provider 后续 completion 只能关闭旧请求，不能重新启动旧 Agent 或终结已交接给新执行者的当前任务。模型故障、窗口关闭都不能决定 converted 是否回滚。

### 11.4 调度、预算与资源回收

每个 Task 显式保存子任务数量、模型请求/token、工具调用、并发及自动时间上限；继承现有任务/Provider 限制并与父剩余额度取更小值，不另增设置 UI。按以下不同量纲记账，不能把所有“子任务消费”按一个求和规则处理：

| 资源 | 计量与归属 |
| --- | --- |
| token/模型请求/工具次数 | 原请求/call 唯一记账，根任务归集自身及后代原条目，不再次累加已含后代的父级汇总。模型传输重试计入实际请求次数及已知/保守 usage；拒绝的工具 call 仍消耗工具循环次数，实际副作用另记 attempt |
| 子任务可用额度 | 派生前原子预留，子可花额度不得与父可花额度重叠；真实收尾后才返还未用预留，未知 usage 按预留保守消费，不因失败/处置假设零使用 |
| 自动执行经过时间 | 各 Task 按自己的单调时钟/暂停账本计时，父等待孩子的区间已在父计时中，不再加子时长；两孩子并行 30 秒不使父扣成 90 秒。有效截止由自身剩余时间与有效祖先约束取小，计时变化见§6.4.1、§7.2 |
| 模型/工具及资源并发 | 按真实占用原子申请和释放，不按已结束的模型回合推断后台执行已停止；资源清理仍使用所属预留 |

计数/token 耗尽进入 blocked_budget，不自动扩额；续预算须来自用户或仍有额度的直接父任务，并保留原消费和授权依据。有效自动时间耗尽按§6.6取消/清理；增加新时间预算也不能复活已取消任务。未返回准确 usage 时先保守计入预留，不按零消费继续派生。

自动执行时间预算从接纳起计入机器排队、模型/工具执行和机器依赖等待；直接用户审批/输入等待及由其独占阻塞的祖先按§6.4.1暂停，存在独立机器工作、bounded 续行路径或机器清理责任时不暂停祖先。等待原因变化与计时账本/timer revision 同事务更新，恢复时沿已记录的剩余时间重算有效 deadline，自动续行不补满预算；父任务暂停不授予其他机器分支额外时间。子预算追加不能超过父剩余额度及有效 deadline。运行代次内以单调时钟执行，持久记录原预算、已消费量、暂停/恢复账本及所需截止信息；重启后先对账有效人工请求/依赖并重算等待原因，不能沿用暂停前的墙钟 deadline 或自动调用模型；不能证明剩余时间/额度时保持 blocked_budget，明确恢复也不能自动重置成 Provider 默认预算，需获得明确的新预算授权。等待和恢复期间的资源/额度归属按§6.6推进。

队列按 Agent/任务来源做轮转并设置等待老化，防单个集群塞满所有 Provider 槽；用户交互优先但不无限饿死后台已授权任务。工程初始上限为宿主同时 4 个模型请求、每 Agent 同时 1 个、每来源集群同时 2 个（合计协调 Agent、成员任务及全部后代）、每直接父任务最多 4 个未终结子任务；未收尾 Task 每 Agent 最多 32 个、全局最多 128 个，包含排队、人工/依赖/预算等待、运行及清理未知任务，不仅计算 ready 队列。已安全处置终结的历史不占运行名额，但仍占必要存储索引。来源按 root_cluster_id/任务祖先链计算，不按当前成员或窗口计算；无关用户任务不计入该集群。多级限额原子占用，实际请求释放才归还，等待不占模型槽；用户交互也不能增加“额外一槽”突破硬上限。取消先关派发门禁，再沿拥有/依赖关系传播。

新 Agent 工作持有运行/清理引用的执行或生命周期操作初值全局最多 32 项、单 Task 最多 4 项，仍取原服务更低限制；这不是从 Driver 队列大小推断的并发能力。AgentRuntime 自有及由其独占保留的运行现场/缓存初值最多 256 MiB；借用记录/图像等服务继续遵守原服务配额并核算保留引用，不能把引用当零成本。挂起现场在容量允许时落内容块，仅保留有界头；恢复加载前重新预留内存。任务、字节、待处理记录、服务容量与§11.2收尾预留必须同时满足，不足即拒绝新接单/新派发，不能靠人工等待过期腾空间。取消、撤权、释放和对账使用保留通道或优先队列，不排在普通新工作之后；物理 IO 失败仍不能承诺成功收尾。这些数值均为待测内部初值，不能据此宣称应用整体内存或吞吐已达标。

独立→集群按§2.2.1交接同一任务账本，不作为预算追加或新的默认计时起点；人工等待已记录的暂停/恢复状态随账本保留。任何有效时间预算的变化都须能由原计时规则或明确的新预算授权解释。

收件箱初始限制为每 Agent 最多 128 条未确认消息且内容总量不超过 1 MiB，单条消息内容最多 16 KiB，全局未确认消息最多 1,024 条；任一超限均返回 QueueFull/MessageTooLarge，不静默丢弃。以上数值及§11.2存储上限是保守工程初值，未经过性能实测，先作为内部常量实施；必要调优须以定向测量为依据，不增加设置产品。

执行资源复用现有 SessionHandle/目标 generation、PTY Lease、ownership_revision 与录制屏障。持有执行 lease 才能输入，用户接管撤销 Agent 输入；Agent 完成不能自动关闭 borrowed_user 或 handed_to_user 终端，created_task 资源按保留策略清理。组 Agent/单会话 Agent/多个集群对同一目标使用同一仲裁入口，按稳定目标顺序申请多目标短锁，不在持锁时等待用户批准；派发前再次复验。只读与写入的并发规则由具体服务决定。

保留 exec 与 PTY 不同完成证据、Local private_protocol 与 SSH shell_reported 的区别、session_interval 输出归属及 recording_degraded/outcome_unknown。聚合结果须逐项显示 local_released、remote_effect_unknown 和资源所有权，任务取消、预算耗尽或集群停止都不能把未知远端效果变成“全部已停止”。

### 11.5 Provider、健康检查与诊断

Task 创建时从既有对话/父任务设置取得模型配置快照；每次请求记录实际 Provider/端点身份、模型、能力、配置 revision 和输入/计划版本，不持久化秘密。配置更新在完整工具对之后的请求边界应用；切换目的地须仍满足§4.3的数据交付授权、能力及剩余预算，不静默降为无工具模式、不因换模型增加额度。未实现所需能力则明确阻塞；原调用/审批/回执不随配置改挂。

按 Provider 配置身份/规范化端点及非秘密凭据引用区分共享限流域，调度器统一观察 Retry-After、在途请求和有限退避，避免各 Manager 同时重试放大故障。队列/退避计入原机器时间，实际重试计入请求和 usage；取消不等待冷却，恢复不能重置冷却或预算。只重试原策略允许的模型请求和可去重投递；未派发意图复验后才可派发，已派发副作用结果未知则只按原 ID 对账，禁止把一次“模型重试”扩展成命令重发。

健康检查由宿主读取权威事实，覆盖就绪却未续行的等待、持续投递失败、非法执行归属/状态、资源互等和未完成清理；与各服务的真实 deadline/心跳区分，合法人工等待、正常长命令和已知冷却不报成故障。自动修复限于去重补通知、重建投影及获准只读对账；不自动恢复已停用任务、重连目标、迁移孩子或执行命令。长任务确需方向复核时，可复用有权直接父级的既有回合并计入原预算，不默认增加模型回合或常驻 Watchdog Agent。

诊断按 TaskId/plan_revision/executor_revision、输入/请求、call/attempt、operation、store_revision 和原因码串联，可回答“为何排队/等待、是否已派发、缺什么证据、由谁决定”；只导出获准的最小元数据，秘密和完整日志沿原读取权限处理。状态迁移时记事实，不为每个流式 token 或进度投影做快照 fsync。容量验收测提交延迟、写入量、队列/内存及恢复成本；测量不足时先背压并定位瓶颈，确需改变存储实现再单独评审迁移，保留既有事务与恢复契约。

### 11.6 本版采用与保留的外部设计思路

采用工作与执行现场分离、事件分流、紧凑上下文/原始引用、结构化汇报和低打扰人工入口；均落到现有 Task/attempt/宿主服务，不复制完整 Source/Thread/工单框架。用户已授权的独立检查或准备可按计划提前并行，不以“投机”为由扩目标或开始新工作。未来明确需要主动巡检时再设计有目标/数据/动作/预算边界的规则，先记录 would-run 再验证执行；本版不默认监听环境接单。应用退出后常驻、云端控制和后台 daemon 留待明确需求，不能用持久化记录冒充持续执行。

A–E 为 V0.4.1 非 UI 能力，F 为 V0.4.2。连接管理缺口逐动作接入现有宿主命令，不在本版顺带重写 Local/SSH/SFTP/KVM；KVM/网页连接是否可附着或执行完全按其已发布 typed service 能力，不由 Agent 角色推导 shell 或 KVM 写操作权限。

在 A–E 集成时通过内部测试入口完成一次纵向验收，再交付 F 的正式页面；测试入口不得成为绕过授权的产品入口。闭环覆盖：

1. 创建无连接绑定的独立 Agent，授权选择一个真实 Local/SSH 目标，走完整请求/执行/回执/下一轮刷新；在同一绑定上接纳两个独立任务，一个等人工时另一个可推进，停止其中一个不串改另一个现场、输入和预算；越界附着入口仍拒绝相同调用。
2. 将独立 Agent 转换为集群并纳管两个会话 Agent，其中至少一个从未打开过助手；各成员获得独立任务对话，用户面板不被自动打开。
3. 分别委派工作；成员协助经集群形成接收任务，继承同一根预算；结果事件恢复等待并汇总。覆盖登记前已完成、bounded 超时后的备用决策、dependency 超时后的持续订阅及迟到结果、结果/取消/有效 deadline 竞争，以及纯人工依赖向祖先传递暂停、混合机器分支继续计时和旧 timer 失效；不丢唤醒、不重复闭合工具对、不重置预算，互相等待被拒绝。
4. 集群尝试直接接管相同工作项时取得现有任务/冲突；重连更换 handle 也保留原槽位/未知门禁。取消唯一请求者时由拥有者取消无用协助，存在另一有效请求者时继续；根任务不能先于所属任务树收尾，且不影响成员无关用户任务。
5. 填满新工作接纳额度，拒绝新增任务/消息，已有任务仍可取消、退出成员、写入清理未知及最终回执；outbox 排空后释放相应额度。
6. 通过同一宿主命令关闭集群内容页，验证全窗口停用和后台清理；重挂视图不关闭。模拟崩溃后，仅明确恢复才启动新协调代次，旧事件/审批不重放副作用。
7. 两个从未打开助手的成员同时等待审批，用户能从全局待处理定位各自精确目标；跨窗口重复批准只消费一次，关闭视图不覆盖票据。长期无用户决定仍为 pending；任务取消、集群停用、成员撤权、执行者/绑定/精确目标代次或授权 revision 变化时只撤销一次，拒绝迟到批准及旧续行，不使用审批等待到期机制。
8. 分别模拟控制资源未知、资源已释放但业务未知；前者阻塞转移/处置，后者可退出成员及接受新任务。用户明确关闭未核实任务后，原结果仍未知、旧 key 不重放，迟到回执不复活任务。
9. 内容配额接近满额时，预写失败块可回收，有效准备/历史/读取租约引用不丢失；仍无空间则拒绝新增内容。协调 Agent、成员及子 Agent 合计遵守同一来源集群模型槽上限，等待不占槽。
