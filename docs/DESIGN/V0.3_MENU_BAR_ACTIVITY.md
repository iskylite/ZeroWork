## 1. 用户确认的规则

- macOS 顶部菜单栏使用透明背景 **App LOGO**。
- 数字叠在 LOGO **右上角**，以白色数字、透明背景呈现，仅数字带细深灰描边；不在 LOGO 旁平排数字。
- 按**有后台新活动的会话数**计数。同一会话内容区和 AI 助手任意一方有新活动均标记该会话，两者合并只计 1；连续输出或多次完成不叠加。
- **App 回到前台全部清空**，不要求逐项查看。再次进入后台时只计算后续新活动。
- **左键**点击显示 App；**右键**点击打开原生菜单。
- 右键菜单包含活动会话列表和「退出 ZeroWork」。点击会话后激活所属窗口并定位到对应会话；AI 来源优先打开对应助手对话。
- 会话列表与 Tab 保持一致：相同图标、显示名称、连接/运行状态，以及同一窗口内的排列顺序。重命名、状态改变和 Tab 重排后同步更新。

“按后台事件次数累计”和“逐个查看后扣数”是已被用户替换的方案，不作为本版行为。

## 3. 活动、去重与清空

| 条件 | 计数行为 |
| --- | --- |
| App 在前台发生新输出或 AI 完成 | 不累积角标 |
| App 在后台，会话首次出现新输出 | 该会话标记活动，总数 +1 |
| 同一会话后续继续输出、命令结束或 AI 回合完成 | 保留一项，总数不再增加 |
| 另一会话发生新活动 | 另一会话标记活动，总数 +1 |
| 会话结束，但没有新的输出批次 | 通过终端结束事实标记活动 |
| 进入前台，包括左键显示 App 或点击会话定位 | 全部清空 |
| 再次退到后台，只有旧输出或重复完成回执 | 不重计 |
| 已关闭来源被清理 | 删除其活动标记，旧菜单标识不能跳到新会话 |

当前终端来源为宿主确认的输出序号与结束事实；Shell 命令结束标记也会推进输出序号。AI 来源复用真实回合完成发布，不从 UI 重绘推断完成；主动取消不额外产生完成活动。不能以一段时间没有输出推断任务已结束。

计数独立于系统通知权限、系统完成提醒开关与全局重要提醒列表。菜单栏活动只提供低打扰提示，不因此新增系统通知、声音或应用内横幅。

## 4. 右键列表与 Tab 一致性

列表采用原生菜单行，复用 Tab 的展示信息：

| 信息 | 目标行为 | 当前原生状态 |
| --- | --- | --- |
| 会话名称 | 与 Tab 显示名称一致；重命名后同步 | 已复用模型显示名称；真实 Local 重命名同步已验证 |
| 会话图标 | 与该 Tab 的 OS/协议/历史图标使用同一选择结果和资源 | 已复用 Tab 的 SVG 资源，原生 14pt 图标 |
| 状态 | 复用 Tab 的连接/运行状态及图标颜色，不另造一套在线判定 | 已读取 Tab 实际图标颜色和同一状态标签，真实进程退出已验证 |
| 排列 | 同一窗口内按 Tab 顺序；拖拽重排后同步，而非活动到达顺序 | 已按窗口及模型 Tab 顺序排序；真实拖拽重排已验证 |
| 当前会话 | 使用原生勾选标记，保留图标与名称 | 已实现并核验原生 NSMenuItem 状态 |
| 来源与跳转 | 稳定 owner/generation 与菜单 token；不按名称查找 | 已实现并有路由测试 |
| 内容区与 AI | 同一会话一行，不额外列一个同名 AI 活动项 | 已实现合并计数 |

列表只显示有后台新活动的会话；不把所有 Tab 都塞入活动列表。没有活动时显示不可操作的「没有新活动的会话」，保留退出项。重名、Tab 重排和多窗口不改变来源身份。标题、图标、状态和排序来自 `Workspace.tabPresentation()`：读取模型名称与顺序、实际 Tab 节点的图标颜色及同一 SVG 资源。多个来源归于同一可见组 Tab 时合并一行。

### 左键、定位和退出

左键激活并显示已有主窗口，必要时恢复最小化窗口；不打开右键菜单。

右键本身只展开菜单，不请求激活主窗口、不主动清零。点击会话行后激活所属窗口并选中来源；AI 活动优先恢复原助手对话。如果来源已失效，不跳转到同名新会话。App 真正进入前台后统一清空活动标记。

定位时保留现有设置保存/放弃确认。有未保存设置时先处理原确认，不静默丢弃草稿；这一情况下不能将“已选菜单项”冒充“会话已呈现”。

「退出 ZeroWork」调用现有应用退出/关闭请求，继续执行运行工作和资源收尾的确认，不绕过关闭流程强退进程。

## 7. 前台恢复延迟分析（2026-11-02）

用户实测主要是“点击后完整 App 显示前台很慢”。先进行正式版采样，再实施本节末尾的局部维护；区分空闲成本与实际点击耗时。

在正式安装版、启动空白工作区状态下进行 3 秒主线程采样（19:10:57，PID 19604），随后进程 CPU 持续约 59–60%。主线程共 1391 次采样，1255 次位于 `runtime.App.frameAfterChromeSync`，约 90%；此比例是采样栈分布，不是单次点击耗时。UI 帧中包含通知避让树扫描、隐藏子树布局/渲染索引/辅助功能投影，以及 RemoteEditor/BMC 编辑器的样式遍历。采样文件：`/tmp/zw-menu-foreground-latency.sample.txt`。

当前优先判断：窗口恢复与 UI 绘制共用主线程，持续的全树维护工作会推迟原生事件处理及激活后的首帧；需要对隐藏界面进行有效可见性门禁和按变更处理。维护前 `RemoteEditor.isVisible()` 只看根节点自身的 `display`，不核验被隐藏的祖先，解释了空白界面采样中仍出现编辑器处理的现象。

维护前菜单选择还存在确定的额外等待路径：原生只写入动作 token，Zig 在下一轮循环开始才消费；当前 `windows.tick()` 仍会先执行一次帧处理，因此会话定位可能先等一帧旧界面再切换。左键直接调用 AppKit 激活，不走该 token 队列，但完整界面显示仍要等待同一主线程的帧处理。

另一个次要风险是菜单投影每轮遍历活动 Tab，`tabIcon()` 在 OS 尚未知时可能进入同步 OS 缓存读取；本次采样未证明它是主要耗时。现有 16ms 事件轮询参数本身不足以解释明显停顿；也尚未测得某次点击中系统激活、CPU 首帧和 Metal 呈现各占多少时间。应以点击时间戳、窗口成为 key/active、首帧完成三段记录复测，而不是先归咎网络或单纯修改轮询间隔。


### 本次维护与隔离验证

只调整影响恢复路径的维护工作，不改变活动计数、列表展示和退出确认规则：

- `RemoteEditor.isVisible()` 检查祖先显示状态；AI composer 在隐藏时先退出布局/样式维护，重开时再应用待更新投影，撤销的快照仍及时释放。
- 通知计时与宿主更新继续执行；仅在有可呈现横幅时收集避让矩形，并跳过隐藏子树。
- 原生会话选项在主线程菜单回调中直接定位，避免先渲染旧会话再消费队列；左键激活和会话定位后请求立即重绘。
- 菜单读取 Tab 已选定的图标资源，图标变更时同步缓存，避免投影期间重复读取 OS 缓存。

已通过针对性的隐藏/重开投影回归、通知倒计时和 Tab 元数据检查；AppKit 动作检查确认会话 token 同步交付，不再留在下一轮队列。独立 Debug/test-mode 构建完成，真实双 Local 会话再次验证合并计数、改名、图标/状态/勾选、拖拽排序及进程退出状态；已查看原生窗口截图。
