# V0.3 PATCH：AI 会话绑定、独立执行与排队／引导

> 2026-11-04 用户裁决后的设计补丁，属于 **0.3**，不新增功能版本号，不修改构建版本或插件 API 2。状态：**非 UI 核心、AiHost 接线与界面集成已实施，已完成针对性验证**；§19 全部交叉场景仍按各自证据验收，不以局部通过代替全量验收。
>
> **绑定只有两个状态：已绑定、未绑定。** 停止是任务行为，结束并解绑是一个操作；操作未完成时仍为已绑定，不增加“结束中”绑定状态。每个现有连接会话／会话组的附着 Agent 应能独立执行；这与另一个拟移除的“独立 Agent 连接插件及其内容卡片”无关。

## 1. 范围、术语与规范优先级

本 PATCH 完整定义现有附着 Agent 的执行隔离、AI 会话独占绑定、查看／定位／结束／恢复／复制、历史环境失效、消息接收与排队／引导。普通 UI 切换不改变执行归属；历史选择不能直接接管会话。不新增连接插件、独立 AI 内容卡片、集群、子 Agent、任务迁移平台或会话同步功能。

| 术语 | 本文唯一含义 |
| --- | --- |
| 连接会话／会话组 | 当前真实业务工作对象；单会话以完整 SessionHandle 标识，组以稳定组身份及有效 revision 标识。名称、Tab 序号、布局位置不是身份。 |
| 附着 Agent | 用户从该连接会话／组打开的既有 AI 助手；拥有独立执行域，同一时刻最多绑定一个可写 AI 会话。不是新连接插件。 |
| AI 会话 | 由 ConversationId 标识的消息、历史、附件、草稿和上下文记录；可结束、恢复或复制，不等于连接生命周期。 |
| Turn／任务 | 一次初始提交及后续模型／工具循环；可接收多条引导。同一 Agent 同时最多一个活动主 Turn。 |
| worker | 执行模型请求及工具循环的后台执行单元；有工作时启动，空闲时可回收。不是模型、子 Agent 或每个组成员各一个线程。 |
| 结束并解绑 | 关闭该会话执行输入，停止推进并收敛任务／资源，保存后撤销绑定的操作；不删除历史，也不默认关闭业务连接。 |
| 恢复／切换 AI 会话 | 保留 ConversationId，把已结束且未绑定的原会话独占绑定到目标 Agent。 |
| 复制 AI 会话 | 从稳定历史快照生成新的 ConversationId，来源保持不变；不复制执行权。 |
| 历史终端记录 | V0.2.6 的录制／归档与只读回看，和本 PATCH 的 AI 会话列表是不同实体，不能混用 HistoryId／ConversationId。 |

本文在上述范围内覆盖 [V0.1.7 AI 助手](V0.1.7_AI_ASSISTANT.md)和 [V0.2.6 会话执行](V0.2.6_AI_SESSION_EXECUTION.md)中“忙时拒绝所有新消息”“选择历史直接激活旧 owner”“关闭后隐式恢复原会话”等旧行为。原权限域、真实执行回执、录制、输入租约、未知效果和合法 session→group handoff 继续有效。既有停止／只读核验／回答恢复规则不得借引导绕过。V0.4 未来插件或集群结构不是本 PATCH 的前置。

### 1.1 从用户要求推导出的不变量

1. 多个连接／组的 Agent 必须独立工作，所以不能共用一个活动 Manager、请求槽或取消令牌。
2. 一个 AI 会话只能有一个可写归属，所以历史查看、恢复和复制必须是不同命令；跨窗口也不能各自成为写入者。
3. 任务空闲不等于已解绑，所以恢复条件不能只判断 running=false；停止完成也不自动解绑。
4. 解绑只能在旧执行失去派发／控制能力后提交，所以异步结束期间保持原绑定，并用操作门禁拒绝执行输入；无需第三种绑定状态。
5. 恢复保留身份而环境可能变化，所以 ConversationId 不能单独作为授权依据；还须检查绑定版本和实际资源代次。
6. 引导属于当前 Turn，排队属于后续 Turn，所以两者分开调度，但统一使用输入身份、接收确认和绑定校验。
7. 历史数据可以复用，历史能力不能复活，所以恢复／复制必须重建当前环境；队列、审批、工具调用和旧句柄不能自动执行。
8. “无感”表示正常发送一次完成、状态自然衔接；不表示隐藏真实等待、自动接管、假装生效或在不确定时重发操作。

| --- | --- |

| turn/steer 携 threadId、expectedTurnId、clientUserMessageId；前端有 optimistic 消息与 accepted 更新 | 引导绑定精确 Turn；先显示待处理消息，分开记录接收与消费。 |

| 消费前复验队列项及状态；运行中不自动 start 队首 | 编辑／移除与派发按版本协调，消费确认后才移除可执行项。 |

| 手动压缩不可引导时可回到排队；活动轮已结束有可识别的 start 回退 | 暂存等待压缩；只有同一有效绑定内才允许旧轮结束后的新轮回退。 |

协议依据：[OpenAI Docs：App Server](https://learn.chatgpt.com/docs/app-server)的 turn/steer、thread/read、thread/resume、thread/fork。读取不恢复运行，resume 保留原线程身份，fork 产生新线程身份并支持已完成 Turn 截点。本 PATCH 额外要求附着环境的唯一绑定和恢复前解绑，这是项目规则，不宣称为 Codex 的同名内部规则。

[Responses API steering](https://developers.openai.com/api/docs/guides/steering)是另一层模型能力，不能由 Desktop 的 turn/steer 推断所有 Provider 都支持。当前项目 HTTP 流式 Provider 采用本地执行边界消费；不默认取消模型生成后重发，不新增原生 WebSocket Provider。模型侧 steering 也不撤销已经发生的实际操作。工具派发屏障、历史环境隔离和资源释放条件是本项目适配。

## 3. 身份、绑定与操作记录

### 3.1 唯一绑定与两个状态

持有权由应用级权威存储统一管理，不由各窗口的 selected 或可见节点决定。可以使用现有应用控制循环＋事务存储，不要求新增常驻服务。

```text
ConversationRecord:
  conversation_id, content_revision, initial_origin, history, draft, draft_revision
  binding_revision                  // 单调递增，解绑后仍保留
  binding: null | { agent_id, current_owner }
  last_closed_binding_revision?     // 上次结束提交的证据，首次使用可为空

AgentRuntime:
  agent_id, attachment_identity      // 真实会话／组，不依赖显示位置
  current_conversation_id: null | ConversationId
  active_turn: null | TurnState
  environment_revision              // 当前资源映射／能力快照的版本
```

binding 非空为**已绑定**，为空为**未绑定**，没有 ending／releasing／reserved 绑定枚举。为恢复而做的预分配不产生执行权，也不向 UI 发布第三状态。删除标记、存储不可用和历史完整性是记录属性，不是新增绑定状态。

新建或尚未使用的副本也可以未绑定，不要求它先经历一次虚假的“结束”。首次绑定走新建／复制提交；恢复原会话则必须能证明上次使用已经结束并解绑。已经结束的历史不因只读查看而清除结束事实；成功恢复建立新的绑定区间，保留前一区间的结束记录。

任意已提交版本同时满足：一个 Agent 至多一个 current_conversation_id；一个 ConversationId 至多一个 binding；双方索引互为对应。绑定为 null 时不能有有效派发权。初始来源和历史调用 owner 永久保存为历史事实，不以 current_owner 的空值丢失来源。

同一真实会话／组在应用内只对应一个逻辑附着 Agent。多个窗口展示它时共用该 agent_id 和权威 runtime，不能因为重新挂载面板或新开窗口分配第二个可执行 Agent。agent_id 不随 worker 重启改变；业务对象关闭后再创建，即使名称相同也属于新附着身份。

attachment_identity／current_owner表达经宿主确认的业务对象归属，当前可操作SessionHandle、传输代次与组成员快照另放环境表并完整校验。不得仅因“绑定仍在”放行旧generation；也不得把每次传输重建都解释为新Agent。宿主若无法证明业务对象存续关系，按对象关闭处理，不能由模型补认。

### 3.2 与绑定状态正交的执行／操作状态

- Turn 可为 starting、running、waiting_user、finalizing、stopping 或终态；这些不改变绑定二元关系。
- 生命周期操作可记录 operation_id、kind、预期两端版本、进行进度和成功／失败结果；结束操作未完成时，binding 仍非空。
- 接受结束操作即关闭执行输入 admission 并暂停自动消费。UI 可显示“正在停止任务”，不能把绑定状态显示为“已解绑”。
- 结束失败保留原绑定、禁用自动续跑并显示具体原因；显式继续必须重新校验原环境，不能以失败处理偷偷清空绑定。

同一会话及目标 Agent 同时最多一个修改归属的生命周期操作；重复请求复用原 operation，冲突的新建／恢复／复制并使用／handoff／删除直接拒绝，不排成可能作用于未来绑定的隐式操作队列。只读查看和固定截点复制可以并行。生命周期操作先登记预期两端版本再异步推进，提交时复验操作仍有效；不通过增加 binding 第三状态实现互斥。

取消组合切换只取消尚未提交的后续步骤。若 End 已经接受，任务可能已停止或资源已释放，不能声称撤销了这些事实；先让原 End 幂等收敛。只有在该 End 明确失败／终结、无后续解绑回调可能提交且旧工作已收敛时，才可由显式继续重新打开原绑定的执行 admission。用户新消息本身不能取消一个仍有效的 End。

### 3.3 必须携带的校验身份

新输入携 agent_id、ConversationId、binding_revision、environment_revision、submission_id；引导另带 expected_turn_id。工具调用／审批继续携 TaskId、原 Turn/call 身份、grant revision、真实 SessionHandle/generation 和组成员 revision。纯消息排队不固定永不变化的资源权限；实际模型请求、预检和派发各自按当前合法范围校验。

binding_revision 在成功绑定、解绑和合法 owner handoff 时推进，禁止回绕或复用；同一会话在同一 Agent 上恢复也必须推进。资源 generation／membership_revision 与绑定版本分别管理：重连、增删组成员不一定重绑 AI 会话，但必须使过时资源能力／审批失效。窗口变化、重命名、Tab 排序不推进绑定版本。

environment_revision 只随资源身份映射、成员授权范围或关键能力失效而推进，不随普通终端输出／RTT／无影响的状态刷新推进。旧环境下尚未消费的输入先暂停；仅在宿主能够证明其捕获的全部资源引用及授权范围未改变时可重新准入，否则要求用户在当前环境重新提交。不能靠解析自然语言或“同名主机”证明目标相同。权限收紧立即作用于实际派发，不把旧输入版本当作永久授权。

这里的 agent_id 是本 PATCH 内部运行身份，不要求先交付 V0.4 的公开 Agent 实体或插件 API。可以由宿主为现有附着实例分配稳定 runtime ID；不得用内存地址／数组下标作跨异步回调身份。所有非零 revision 的推进均使用有溢出检查的现有 identity.advance，耗尽时报错并保留原状态。

## 4. 每个附着 Agent 的独立 worker

连接 A、连接 B、组 G 的 Agent 各自运行，不因另一 Agent 正在生成、审批、压缩或执行工具而禁用发送。组 G 一个主循环可以调度多个目标，不能机械地按成员数启动 N 个 Agent worker。

现有 AiHost 只保留面板、输入、展示绑定、命令路由；执行可变状态进入稳定地址的 AgentRuntime。每个 runtime 持有 Manager、worker／私有 I/O、Provider binding／native context、请求快照、取消 token、工具 Bridge／执行桥、审批 Broker、引导邮箱、事件通道、重试与压缩。历史／草稿由 ConversationRecord 拥有，runtime 通过唯一绑定取得写入权；切换界面不搬移 worker 正在使用的历史对象。

共享模型目录、不可变配置、现有连接／文件／通知服务；共享服务必须沿原控制器／mailbox入口，不能把 libssh2、终端 SPSC 输入或可变网络 context 暴露给多个 worker 并发直写。不同 Agent 操作同一终端／KVM 时按资源租约与 fence 仲裁；只等待冲突的操作，不能把资源锁扩大成全局 AI 锁。权限撤销、人工接管和连接关闭优先于后续派发。

UI 事件携 runtime／conversation／binding／Turn／event sequence；按 runtime 有界轮转消费，后台大输出不能饿死前台。worker 不持 UI Node／Scope 指针。窗口关闭不释放仍被 worker 持有的数据；先关闭 admission、收敛并 join，再释放 runtime。join 只能在已发布终态后由安全控制点执行，不在工具回调／Bridge 锁／审批 handler 内等待自身。应用退出、更新关闭协调器必须遍历所有 runtime，不再只检查 AiHost 的一个 thread_state。

## 5. 查看、定位、新建、结束、恢复、复制与导入

### 5.1 命令语义

| 操作 | 身份／内容 | 绑定与执行效果 |
| --- | --- | --- |
| 查看 | 读取原记录，不改变 ConversationId | 只读，不绑定、不连接、不请求模型；不把历史窗口变成第二写入者。 |
| 定位 | 跳到仍持有该会话的原 Agent／窗口 | 使用实时绑定索引，不能按历史 owner、名称或 Tab 序号定位替代对象。 |
| 新建 | 新 ConversationId，空历史 | 目标无绑定才可直接绑定；已有会话先显式结束并解绑。仅打开欢迎页不必创建可写会话。 |
| 停止 | 保留当前 ConversationId | 停止当前任务并暂停自动队列，继续保持绑定。不是结束、删除或断开连接。 |
| 结束并解绑 | 保存原历史、草稿和暂停输入 | 完成 §6 后撤销绑定，不默认关闭业务连接。 |
| 恢复／切换 | 保留原 ConversationId | 来源必须已结束未绑定；目标必须无当前绑定；推进绑定版本并重建环境。 |
| 复制 | 新 ConversationId，记录来源 ID／revision／截止 Turn | 来源不变；只复制 §8 的稳定内容，无任务和执行资格。 |
| 导入 | 首版入口“复制到当前 Agent”承载上下文复用 | 导入按复制语义创建新 ID；没有任意文件格式导入器。本地原会话继续使用必须走恢复，不能借“导入”绕过绑定。 |

收起面板、切换连接／组、打开设置或只读历史均不停止任务、不解绑。AI 面板关闭／新建／切换若实际表达结束，必须调用统一结束操作，不能保留旧“隐藏即收起”和“×立即换空会话”两套含混实现；收起与结束在菜单、a11y 和 Tooltip 中明确区分。

### 5.2 来源与目标条件矩阵

| 来源 AI 会话 | 目标 Agent | 允许行为 |
| --- | --- | --- |
| 已结束未绑定 | 无当前绑定、来源内容可读 | 可恢复，也可复制后绑定。 |
| 未使用的新会话／副本、未绑定 | 无当前绑定、记录完整 | 可首次使用并绑定，不要求伪造结束回执；这不是恢复旧运行。 |
| 已结束未绑定 | 绑定另一个空闲会话 | 不直接替换；明确“结束当前会话并恢复／使用副本”。 |
| 已结束未绑定 | 当前任务／审批／清理尚未结束 | 不接管；显式结束操作完成后才可进行组合操作下一步。 |
| 已绑定、空闲 | 就是原持有者 | 返回当前会话；另行复制不隐含激活副本。 |
| 已绑定、空闲 | 其他 Agent | 查看／定位／复制；不允许恢复原会话。 |
| 已绑定、运行中 | 任意目标 | 查看／定位；复制只到最后稳定截点，不能接管活动会话。 |
| 已绑定、结束操作未完成 | 任意目标 | 查看；不能恢复；复制仍只读稳定截点。 |
| 已删除、正文缺失或损坏 | 任意目标 | 不恢复、不伪造空会话成功；已有可读部分可查看，复制须明确可用截点。 |

源绑定空闲也不能被别的 Agent“借用”；来源运行完毕不自动变成未绑定。目标有已暂停队列、草稿或失败恢复时也算已有会话，不能因没有 worker 而覆盖。活跃来源复制到另一个空闲 Agent 后，两边是不同 ConversationId，可各自运行。“复制、不使用”发布未绑定副本；“复制并使用”先准备不可见快照，结束目标原会话后才发布并绑定副本，两种命令不混为一次隐式激活。

## 6. 结束并解绑的提交条件

```text
接受 EndConversation（核对原绑定版本，建立幂等操作）
  → 关闭新执行输入与自动消费，保存后续编辑为草稿
  → 请求停止模型／工具循环，撤销未使用审批和输入授权
  → 收敛派发、控制租约、后台读取／压缩和本地资源
  → 保存真实历史、暂停输入、资源处理回执
  → 原子撤销两端绑定并推进 binding_revision
```

1. 空闲且无待释放资源时可以同步完成，没有强制等待阶段。
2. 有 worker 时，请求取消后仍保持绑定，直到不再有新的派发生产者／有效控制入口。不能先清 owner 再让旧 worker 后台收尾。
3. 已提交的 PTY／其他持续 execution 必须完成既有 stop、人工接管或 Supervisor ownership 交接，并持有可核对回执；worker 结束不证明 execution 已退出。
4. 远端结果 unknown 不要求永久等待业务完成，但必须先撤销旧派发／输入能力并释放或明确转交本地 ownership；unknown 原样写入历史。无法确认本地失权时保留绑定并报告阻塞。
5. 附件读取、压缩、标题／图像任务要么停止并收敛，要么变为仅写旧快照的无执行能力操作；它们不能在恢复后覆盖新草稿、模型历史或绑定。
6. 保存失败不宣布解绑成功；保留原绑定及停止门禁，允许重试同 operation_id。超时不强制清空绑定，用户退出沿既有应用强退／恢复边界。
7. 相同 operation_id 返回相同进度／结果。成功后重复结束不再停止新绑定；旧结束票据不得命中恢复后的同 ConversationId。
8. 结束将 queue／未消费 steer 的调度资格设为 paused，保留原交付状态，尤其不能把 outcome_unknown 改成“确定未消费”；不自动删除或重放。删除会话是另一个显式操作，需先满足无绑定及未决提交的核对条件。

解绑提交前还须设置最后的内容／草稿保存屏障：核对 content_revision、draft_revision 和待处理输入版本，使 End 受理前已接收的输入、已产生的工具结果以及承诺保存的草稿均有落点。后续编辑若未赶上该屏障，保留为原票据关联的 UI 恢复草稿并提示未保存，不能落到恢复后的新绑定或清空输入。绑定索引、结束回执和 last_closed_binding_revision 同提交发布；任何提交前错误保持已绑定。

Stop／失败／End共用中断Turn封口：已经进入规范历史的合法工具调用，对确定未派发的slot写真实cancelled_unsent，对已经派发而结果不明的slot记录unknown及原operation引用；未形成合法call_id／完整参数的流式片段只保留在原始展示／审计，不伪造可执行工具对。若旧记录损坏而无法重建合法transcript，可保存可证明的稳定前缀、原始中断尾部和“不可完整恢复”标记；在控制已失权、所有承诺保存事实确已保存后仍可结束解绑，后续按§7限制恢复。历史可恢复性与当前控制权分别判断，不能因半截模型历史永久占住绑定；实际存储失败仍按第6条保留绑定重试。

## 7. 恢复与组合切换事务

预检先校验来源有上次结束提交证据、binding=null、规范历史可读、目标无绑定且无冲突生命周期操作、目标会话／组对象身份有效；预分配请求所需对象并验证环境重建可完成。完整但为空的历史、只有草稿或已知暂停输入，不等于正文缺失，仍可恢复。提交时在唯一权威入口再次比较来源 content/binding revision、结束证据和目标占用版本，**同时发布 Conversation.binding 与 Agent.current_conversation_id，并推进绑定版本**。只有提交成功的 runtime 可写入／派发。失败释放暂存，不改变来源或目标；两个 Agent 竞争只允许一个成功。

结束时标记不可完整恢复的记录不因binding=null就自动可恢复：能重建完整规范历史才继续原会话；只能读取稳定前缀时提供明确截点复制及原尾部只读查看，没有可恢复前缀时仅查看／新建。不能静默丢掉尾部再以原ID宣称完整恢复。该限制不把已完成解绑的记录改回已绑定。

业务对象有效不等于网络已连接。对象仍存在但离线时允许恢复为已绑定的非执行环境，只读查看与草稿可用；不能自动重连或授予远端能力。新发送沿实际可用工具／明确目标准入，不把离线连接的写入请求静默降级为其他主机或本机执行。目标对象已关闭或代次不可核对时拒绝绑定。

恢复同一 ID不延续旧 TaskId／活动 Turn。保留历史 Turn 的原 ID，新任务使用新身份，不能从历史计数倒退并碰撞。恢复只建立可用会话，不立即向模型发送，也不重放“请继续”、旧工具或旧队列。

原草稿可以恢复到输入框，但正文／附件保留历史来源，已失效的连接、选区或远程引用标为需重新选择，发送前复验；绝不因草稿恢复而自动发送。只有草稿的空会话按同一规则处理。旧回答重试／继续工具执行的票据不随恢复复活；历史问题如需再做，只能明确复制为新输入，使用新任务身份与当前权限。

“结束当前会话并恢复 X”分两段：先预检 X 和目标环境，再执行当前会话结束；结束完成后复验并绑定 X。用户取消／目标关闭／X被另一 Agent 抢先恢复时停止组合操作。若结束已经成功、后续恢复失败，原会话仍作为未绑定历史保留，显示目标未恢复；不把旧任务自动复活作为回滚。

查看历史不生成恢复命令。当前 UI 选中项／focused Agent 改变后，尚未提交的原恢复票据必须失效；不能把 X 绑定到后来切到的 Y Agent。已经提交成功的恢复不因随后切换界面而撤销，只按原目标报告结果。跨窗口只改变展示投影，不增加持有者。来源原连接仍存在并不影响未绑定会话恢复到另一 Agent；恢复不自动跳回原 owner。

## 8. 复制与跨 Agent 上下文复用

### 8.1 快照与目标

复制在源的 content_revision 上取得不可变快照，截止最后一个已终结、工具调用／结果完全闭合且历史已提交的 Turn；成功、失败和停止的 Turn 均可作为截点，但必须保留其真实终态和 unknown／中断标记。仅工具对闭合而 Turn 仍运行不算稳定截点。运行中回答、半截工具批次、未确认输入及压缩中间产物不进入副本；尚无稳定 Turn 时拒绝复制，空会话改用新建，草稿如需复用通过明确文字复制，不把草稿伪造成完成历史。不能为复制要求停止来源，也不能让复制过程中后来追加的消息混入原截点。

快照必须持有截止点的规范历史，而不只复制一个压缩摘要。若当前 wire_history 已被压缩，使用能证明仅覆盖该截止点的历史／摘要；摘要已混入截止点之后内容且原文不可重建时拒绝该截点，不能把后来的信息倒灌进副本。复制期间 pin 住选定正文／不可变附件及来源元信息，源删除或新输出不会改变快照；临时 pin 不授予源会话写入权，也不修改其 content_revision。

新记录生成新 ConversationId，存 parent_conversation_id、source_content_revision、fork_turn_id、来源标签。历史 Turn/call 身份作为不可执行的来源引用保留；新任务／派发账本使用新会话和新 TaskId，不把来源调用重新登记为可重试执行。共享不可变文本／图片块须引用计数，删除来源不能损坏副本。

“复制并使用”先完成截点、正文／附件可读性和目标条件预检，再原子发布副本及其初始绑定；目标占用变化时不生成用户不可见的已绑定副本。“复制、不使用”不要求选择目标Agent，也不受目标占用影响，只校验来源快照并明确发布为未绑定记录；首次使用时再取目标配置与新绑定。“复制并使用”在来源自身需先结束的情况下，预备副本不提前获得执行权，失败／取消清理未发布临时数据。

来源正在执行时允许显式复制到另一个无绑定 Agent，适用于跨主机复用排障背景；不是共享会话或跨 Agent 消息工具。目标有当前会话时先明确结束；同 Agent“复制并使用”同样执行结束＋绑定副本。没有自动同步、合并或从来源继续拉取的关系。

### 8.2 复制内容白名单

| 可复制的稳定历史 | 不复制／不恢复的运行内容 |
| --- | --- |
| 用户／助手正文、原时间线、已闭合工具结果及原来源标签 | worker、活动 Turn、Task、执行／重试账本、Supervisor控制入口 |
| 已保存且可复用的文件正文／选区／图片快照 | 远端文件句柄、临时 URL、过期图片服务引用、终端输入队列 |
| 有来源范围的摘要及历史事实，按 §9 标历史 | 待发送队列、待引导输入、未确认提交、未完成问答、草稿 |
| 只读记录引用，前提是引用可访问且保留策略允许 | 密码／密钥、审批票据、允许一次授权、权限／执行路由 grant |
| 来源信息与分支关系 | 来源的实时模型／权限 override、当前目标与实时目录快照 |

副本的模型／effort取目标当前配置；来源模型仅保留为历史元信息。恢复原会话可保留原生成偏好，但必须验证配置存在；无效时要求选择，不静默替换。两种操作的执行权限、运行方式和目标能力均取目标 Agent 当前有效策略，不从历史 Controls 导入 auto／full_control。现有显式实时权限修改继续按原审批规则生效。

正文完整性和附件可用性分别判断：规范消息及必要工具对损坏时拒绝该截点；历史外部附件失效可以按 §9 保留“不可用”占位及原来源，不能伪造内容、发送坏图片引用，或静默删掉整条工具结果。副本还原模型上下文时使用合法的缺失内容说明；展示的原始历史事实不改写为新生成结果。

## 9. 历史环境失效与上下文重建

恢复／复制到相同名字、相同资产或相同 Agent，都不能证明旧句柄仍有效。必须分别维护：不可修改的历史记录、按来源／绑定代次标记的历史模型上下文、由当前宿主生成的实时环境与能力表。

| 历史项 | 新绑定后的处理 |
| --- | --- |
| SessionHandle、GroupRef、成员索引、Tab序号、operation／execution ref | 默认仅历史，不按数字、名称、主机IP映射当前对象；工具解析同时校验会话授权与完整代次。 |
| 命令与执行结果 | 保留当时真实目标和结果；命令文本不形成重放请求，历史成功不形成新执行成功。 |
| cwd、目录、连接状态、组成员清单、系统事实 | 新请求按当前能力重新查询；旧值标记“历史环境”，不得作为实时初始目标。 |
| 文件／图片／录制 | 可读不可变快照保留来源；外部引用失效显示不可用，不自动在新主机读取同路径或请求新授权。 |
| 压缩摘要／host notice／先前 system 环境片段 | 保留可核对的历史来源，清除其实时能力语义；新 system 与当前绑定 notice由宿主重新构建。 |
| 未知结果／尚未证实的业务效果 | 原样保留；不能恢复为 pending execution 或自动重试，不把历史观察结论推广到当前环境。 |

模型历史投影按绑定区间标注旧工具输入／输出，保持角色和 tool pair合法；不把整个旧工具历史改写成新的成功结果。当前身份／范围说明在新绑定的首个模型请求前就位，不等模型先拿旧ID调用工具后再纠正。复制／恢复不重新获得绑定外既有连接的查询权；模型猜出旧ID也不能通过后端校验。快照中包含相同文件路径时，文件写／读工具仍必须由当前明确来源解析，禁止回退 activeTab。

### 9.1 连接变化与既有 handoff

普通断线／重连：只有宿主确认仍是同一个逻辑连接对象的重连，AI binding才保持已绑定；agent_id属于该业务对象的存续期，传输重建不是创建第二个Agent。推进实际发生变化的资源generation／grant与environment_revision，撤销旧输入权，按§3.3处理旧环境输入并重建能力。若原SessionHandle确已销毁、无法证明同对象重连，走业务关闭及新对象路径，不能按相同session_id／名字自动修补current_owner。断线本身不自动结束／重绑AI会话。

会话关闭／组关闭：沿既有关闭协调器对所附 Agent 发起结束；真实资源失权并收敛后解绑。资源已消失也不直接把旧 Agent 绑定到新建同名连接。零成员组若业务组对象仍有效，可以保持绑定并沿 V0.2.6 查询／管理能力工作，不因成员为空伪造解绑。

合法 handoff 必须区分两种既有业务，不笼统停止“来源Agent”：

- **当前对话从单会话提升为组：** 同一ConversationId与Task由唯一承接runtime继续，current_owner从session原子改为group，推进binding_revision和environment_revision。该runtime不是待结束的无关来源，不能调用End把自己停掉；原session附着写入入口在同一提交中失权。若使用不同承接runtime，必须在原写入者已移交失权后唯一接续，不允许两个worker同时推进该Task。保持V0.2.6调用参与者的旧批次屏障，再刷新新范围。
- **把另一个会话拖入已有／新建目标组：** 目标Agent及其当前ConversationId按原规则继续，成员变化推进environment_revision；若目标会话自身提升为组，再同时推进其binding_revision。被并入的另一来源Agent若有独立AI会话，则按§6结束并解绑自己的会话，保留历史；不把它的历史、队列或任务拼入目标。来源停止与资源成员关系提交沿原入组事务协调，不能把独立worker的停止误写成停止目标承接任务。

两种情况都保持绑定二元关系，原子提交前后各只有一个owner。非本次调用参与者不能借handoff抢占会话；与End／恢复冲突时按§3.2串行裁决。旧计划未用批准失效，已派发请求只按原身份补账；唯一承接Task在合法刷新边界继续，普通旧worker无权续行。旧绑定／旧环境下未消费的队列和引导按§3.3暂停并保留，不自动扩展到新成员；已经consumed的输入留在原历史，不改成新队列。资源租约与历史调用身份不改写。

## 10. 跟进行为设置与输入记录

AI 设置 → 对话 → **跟进行为**：`steer`“引导”（默认：在 AI 工作时发送的消息将补充到当前任务）；`queue`“排队”（当前任务完成后依次处理新消息）。一个应用级持久设置，无连接／组覆盖；缺省／旧版本无字段使用 steer，非法持久值按配置校验失败处理，不默默启用第三种行为。保存失败保留旧有效值和用户选择，沿设置事务显示失败。

设置改变只影响之后新提交；每条输入记录 resolved_mode，旧队列不批量转引导。Cmd/Ctrl+Shift+Enter 为单条反向行为，优先识别且不破坏原发送／换行配置；IME组合输入不触发。其他快捷键不改。按钮、键盘、`@ai <问题>` 等显式发送走同一协调器；选区／附件入口原本只填草稿的继续不自动发送。

```text
Submission:
  submission_id, agent_id, conversation_id, binding_revision
  admitted_environment_revision
  kind: follow_up | interaction_response
  resolved_mode: queue | steer       // 仅follow_up适用
  effective_route: start | queue | steer
  expected_turn_id?, expected_interaction_ticket?
  sequence, message_revision, payload_snapshot, attachment_refs
  delivery_attempt_id?               // 实际投递尝试的回调身份
  generation_config_snapshot?, delivery_state, paused, pause_reason?
  resulting_turn_id?, consumed_request_sequence?, original_submission_id?
```

payload在 admission前完成自有副本、附件保留／scope检查和容量预留；接收失败不得清草稿。清空仅消费提交时那一版草稿，用户在异步接收期间新输入的文字／附件不能被回调清掉。生成配置记录非秘密ID与配置revision；不把密钥写进消息。引导继承活动轮生成配置，UI中为下一轮选择的模型不能偷偷替换当前轮；显式权限撤销仍实时生效。

草稿清空依据协调器可靠持有正文的“受理收据”，queued也可以具有该收据；delivery_state=accepted专指输入已交给Turn。两者不是同一个标志，不能让排队消息一直留在输入框，也不能用乐观显示代替可靠受理。

输入同时记录提交时的下一轮生成配置；实际accepted为steer时使用目标Turn原配置，实际queue／start或受控回退新轮时使用记录的下一轮配置，并更新effective_route。后续设置改变不改这两个已确定的来源；失效配置阻止启动并保留输入，不临时改用活动模型或另一个Provider。

交付状态与是否允许推进正交，不能用一个suspended枚举覆盖交付事实：

| delivery_state | 确切含义与允许的后续 |
| --- | --- |
| queued | 正文已由协调器可靠持有，尚未交给某个Turn；可在未claim且版本有效时编辑／移除。 |
| submitting | 已唯一claim、正在把输入交给确定的Turn；仅同一投递尝试推进。 |
| accepted | 该Turn的输入邮箱已持有输入，但尚无consumed提交证据；不能同时回队列或创建另一投递。 |
| consumed | 用户输入已经一次性提交进该Turn规范transcript，并关联请求序号；模型是否收到、是否遵循另记请求事实。此状态不回退为queued。 |
| failed | 已证明该尝试没有被目标Turn接受；保留错误，可按原输入身份发起受控重试。 |
| cancelled | 已证明没有consumed且不再可能被原尝试消费；保留去重回执，不等于撤销已发生的效果。 |
| outcome_unknown | 不能证明原尝试被接收／消费与否；只允许对账，不自动重发。 |

paused是独立调度门禁，End／Stop／环境变化只设paused及原因，不改变accepted、consumed或outcome_unknown。普通start／steer可从新受理直接进入submitting，queue从queued经claim进入；明确失败的排队转引导可以释放claim返回queued。accepted要撤回，必须在同一邮箱消费锁下证明未消费并提交cancelled，不能仅凭界面显示待处理撤回。保留按ID查询的终态回执，不以从列表移除代替去重记录。

consumed提交同时确定规范用户消息和consumed_request_sequence；模型HTTP开始前失败也不再追加相同用户消息。请求重试复用已提交transcript；实际网络送达不确定时记录request状态，不倒退消息交付状态。预算／持久化预检在该提交前失败则输入仍accepted且paused，不显示成已经进入请求。乐观UI消息不是第二份规范历史，后续以submission_id更新同一项。

同一submission受控重试仍有不同delivery_attempt_id，回调须同时匹配消息／绑定／Turn和尝试身份；旧尝试的late failure不能把新尝试的accepted降回queued。仅已证明原尝试未接收时才允许新尝试，outcome_unknown只查询原尝试，不生成第二个并行投递。

## 11. 发送判定与启动／收尾协调

所有判定在复验唯一绑定和 admission后执行；普通前台显示目标不替代命令票据捕获的 Agent／会话。

| 当前条件 | 普通排队模式 | 普通引导模式 |
| --- | --- | --- |
| 已绑定，空闲且无更早可消费消息 | 开始新 Turn | 开始新 Turn |
| 已绑定，活动轮运行／等待用户 | 入队 | 提交当前轮引导，等待／审批见 §13 |
| 首轮启动尚未提交完成 | 入队 | 暂存队列，防止双启动；普通发送不抢首轮 |
| 当前轮已发布最终回答、仅剩本地收尾 | 入队 | 转后续输入，不强改已发布终态 |
| 手动压缩操作占用会话写入 | 入队等待 | 暂存队列，压缩完成再判断；不强行引导压缩任务 |
| 更早可消费队列项尚未claim | 追加队尾 | 活动轮存在时可引导；空闲时普通发送不能绕过旧队首，指定队列项的立即处理见§12 |
| 停止／失败／unknown导致自动推进暂停 | 保留暂停输入 | 保留；通过明确的继续／新请求恢复，不自动重放旧输入 |
| EndConversation已接受，绑定仍非空 | 不接受执行，保留草稿 | 同左，不能在旧任务收尾间隙插入新一轮 |
| 空白欢迎页且Agent无当前会话 | 原子新建并绑定，再受理首条输入 | 同左；空闲时跟进行为不影响首条启动 |
| 未绑定历史／只读历史／绑定版本不符 | 先恢复／首次使用副本／复制，旧提交不执行 | 同左，不回退到当前Agent另一会话 |

针对已进入引导提交且目标轮已确定、但启动回执ID尚在途的情况，协调器等待该轮身份，不再次启动。对每个 Agent的启动／结束和输入接收使用同一短同步入口；不持锁等待网络、用户或工具。只有当前运行对象能发布活动轮终态。

空白欢迎页的首次发送携带Agent及欢迎页代次票据；完成模型／payload／容量预检后，原子发布新ConversationId、双向绑定和首条输入，再允许worker启动。同一欢迎页并发发送只创建一个会话，后续输入通过该票据已提交的新会话映射有序接收；不能把票据转投给后来另建或恢复的会话。新建／接收提交前失败保留欢迎页草稿；提交后启动失败保留新会话及已受理输入，不能伪装成未接收而重新建会话。只读历史没有这个隐式新建入口。

首轮启动失败保留后续队列，不越过失败首条自动执行后面的命令；spawn失败、OOM和预检查失败都必须有明确未开始回执，不把草稿丢在既非历史也非队列的状态。

表中队首先后约束针对仍具有自动消费资格的queued项；paused项不被隐式重新启用。新发送可成为用户明确的新处理请求，但须等旧停止完成、活动Turn退出和资源复验后再启动；停止进行中接收的输入保持paused，停止完成不自行启动它，须显式继续／再次发送。当前绑定的outcome_unknown投递须先核对；工具效果unknown则沿现有observation-only／资源门禁，只开放已允许的观察及收敛操作，不能靠解析新文字判断“不是同一效果”后放行写入。旧绑定的归档unknown按§14.1处理，不一律阻塞新环境。

首轮或收尾期间暂存为queue的输入不因用户选择默认steer而在后台变成另一轮的引导。resolved_mode保留用户选择，另记录effective_route及暂存原因；它后续按队列开启新轮，除非用户明确执行“引导”转换。

转为queue／start时，原steer尝试的expected_turn_id保留在尝试回执中作来源，不能成为未来自动改投新Turn的许可；只有已证明旧尝试未accepted的路径才可移除当前投递的旧轮约束，后续由queue claim或受控start确定新resulting_turn_id。新一轮启动槽必须等旧worker退出／join及必要ownership收敛后释放，不能只因已经发出终态事件就并发重用同一runtime的请求字段。

## 12. 队列、编辑、顺序与转引导

队列属于 ConversationId，执行资格属于提交时的绑定版本。每个Agent没有全局跨会话抢槽的问题；其当前会话之外只能查看／定位／恢复／复制，不能创建多个可写历史分支塞入同一个runtime。

普通自动消费：上一轮成功终态→落定真实wire history与资源交接→复验队首ID／版本、绑定、环境、能力、预算→原子claim→开始新轮→确认accepted后移除可执行队列项并保留回执。输入仍可能accepted且paused，移出队列不等于已经consumed。queued不预先进入上一轮模型上下文；新轮使用上轮最终历史。已受理且由Supervisor持有的持续execution不要求业务完成才消费下一轮，但必须满足已有ownership／输入规则，不把“进程还在跑”误判成本地资源未释放。

编辑／移除／重排仅作用于未claim的queued项，携预期message_revision和queue_revision。提交中、accepted或outcome_unknown不允许直接改正文／删除去重证据；失败刷新真实状态并保留编辑草稿。拖排序不改变submission_id。编辑后再次做附件／scope／容量校验，取消编辑恢复原位置和正文。记录顺序由宿主sequence决定，不用wall clock排序。

“引导”操作：claim原队列项→检查绑定／Turn→运行时提交steer、空闲时按用户明确选择启动该项→确认accepted后移出可执行队列，保留后续consumed／paused记录。全程使用同一submission_id且协调器持唯一处理权，不先删除再提交。明确未accepted的失败才可恢复queued，已有paused门禁不因此清除；未知结果转outcome_unknown并阻止自动队列再次发送；原队列项被编辑则旧按钮失败，不发送缓存正文。手动压缩时保留队列。已accepted的引导不提供假“撤回到队列”；只能在确定未消费且本地原子撤回成功时取消。

空闲时点击非队首的指定项表示用户明确要求先处理它，可以越过其他未claim的queued项；只移动／claim这一项，其他项相对顺序不变，不覆盖已claim输入，也不越过outcome_unknown门禁。普通发送和自动消费仍严格取队首。“继续队列”是独立明确动作，只重新准入用户选定、仍为queued且未消费的paused项；不是把所有待处理状态统一改回queued。

用户停止、任务失败、历史保存失败、资源效果不确定均暂停自动队列；同一会话有未决提交时不越过它派发依赖后续输入。显式重试使用原提交去重语义，仅在确定未接收时重发；新建任务／重新执行是另一个明确动作，不复用已派发工具账本冒充重试。

## 13. 当前 Provider 的引导消费与工具屏障

### 13.1 当前轮内继续

UI／控制线程只向线程安全邮箱写已拥有的输入，worker拥有活动模型历史。原TurnId／TaskId／工具账本不变；引导不调用会resetForRun的普通submit／run入口。即便tools为空也有可继续的真实transcript；不能把引导实现依附于tool_host是否存在。

消费前复验当前绑定、环境准入、活动Turn、End／Stop门禁；accepted不免除这些检查。绑定或目标已失效时设paused并保留原交付事实，不能为了清空邮箱改投新Turn。普通新引导推进计划input_revision，审批／派发读取同一revision；不能由UI直接修改worker正在使用的请求数组。

| 到达阶段 | 消费规则 |
| --- | --- |
| 模型请求尚未发出 | 将当前邮箱快照按sequence加入下一请求，后来的输入留下一边界。 |
| HTTP流式响应中 | 立即确认接收、显示待处理；响应返回后的派发／完成屏障消费，不取消HTTP、不重放生成。等待受原网络／idle timeout约束。 |
| 模型返回工具计划、尚未派发 | 先处理待引导输入，旧计划未派发部分用真实本地拒绝结果闭合后重新规划。 |
| 工具已执行 | 不伪造取消；等待真实回执／既有有界等待结果，保持原结果归属。尚未执行兄弟调用逐个检查。 |
| 没有工具，准备完成 | 在关闭本Turn输入前检查邮箱；有已接收输入则保留本次assistant输出并继续当前Turn；预算／错误不允许继续时明确暂停保存。 |
| 当前Turn最终发布已提交 | 仅同一绑定内走 §14的新轮回退，不改写已完成轮。 |

连续输入逐条存储，一个边界可在预算内一次纳入多条。一次收到无限引导不能重置原Task的时间／工具／轮次预算；达到预算先保留未消费输入并暂停，不丢消息也不无界续行。用户明确等待仍沿既有budget.userWait暂停自动预算；网络、工具和传输超时保持各自规则。

模型说明要求保留原任务中仍有效的目标；新输入为补充／纠正／追加，只有用户明确替换／取消才改变目标。仅输入“现在怎样”也不丢原目标。多条引导不自动摘要、去重或用后一条覆盖前一条。

流式文本已经出现“完成”或Provider的done不等于应用Turn已提交终态。唯一的完成边界是协调器在同一短同步入口检查无待处理accepted引导／有效等待后，关闭本Turn输入并提交turn_completion；已关闭后新输入只能进后续队列，finalizing还没释放worker也不能开第二轮。错误、停止或预算耗尽可以在有未消费输入时终结Turn，但必须同时暂停并关联这些输入的原目标，不能以“邮箱非空”阻止停止，也不能丢弃消息。

已经明确进入后续队列的输入不再由“引导回退”路径直接启动，必须等待本轮收尾并与其他队列项统一claim。未受理的旧轮steer只有在证明该尝试未accepted／未consumed、同绑定有效、无更早可消费项且无别的新轮已经启动时，才可保留submission_id准备一次新轮请求；其他情况保留为queued或paused，不能产生第二投递。

### 13.2 尚未派发工具与审批

每次工具派发前检查活动输入revision及终止门禁。新引导已经被接收时，不继续派发旧输入版本的计划；检查与取得本地派发资格在同一控制边界线性化。已经取得并提交派发的调用保持真实回执，不能在事后标记未执行。

一个assistant工具批次已经进入历史时，对所有未派发slot补 `not_dispatched_due_to_new_input`（或现有等义错误），保原call_id和工具角色；这是宿主拒绝事实，不是模拟远端输出。派发中／unknown沿原账本结算。所有必要call/result闭合后才插入用户引导并发下一请求，不拆tool pair、不把未知写成失败后自动重试。

等待用户审批的工具尚未派发时，引导必须能唤醒Broker等待。关闭该旧计划的未用票据并按上述结果闭合、重新规划；新计划按当前有效权限重新决定是否审批。旧弹层／按钮携审批ID与计划revision，过期点击不能批准新命令。已运行的独立execution不会因普通引导被无条件停止。权限切换、scope刷新和用户接管继续独立执行其现有校验，steer不提升授权。

### 13.3 与原位审批／问答共用 composer

Composer 原位交互：普通输入／附件保持挂载，审批和问答使用明确interaction ticket。“批准／拒绝／提交答案”是专用交互命令，不能由跟进行为设置排入下一轮，也不能把自然语言“同意”自动当作权限批准。

“稍后处理”不回答、不批准，恢复普通草稿；此时普通发送可以按设置排队或引导。排队输入不改变当前审批／问答，继续等待其专用动作。accepted引导则在协调器中明确supersede本Turn尚未完成的审批／问答票据、唤醒等待，并提交“被新输入中断、未批准／未回答”的真实结果后消费引导；不依赖模型或关键词判断新文字是否与旧问题相关。若仍需要答案，模型重新提问并取得新ticket，不能让旧等待挡住引导形成死锁。引导不是该问题的专用答案，更不是批准。

答案／批准与引导在同一ticket／计划revision入口决定先后：专用动作先提交则保留真实结果，已派发操作按原身份结算；引导先提交则旧ticket点击明确失效。停止／结束可随时取消等待，不要求先回答。手动压缩不能在尚未闭合的工具／问答边界抢写transcript。专用interaction_response不使用resolved_mode、不占普通follow_up队列条数，并采用现有有界答案／票据容量，队列满不能阻止回答、拒绝、停止或结束。

## 14. 竞态、停止与未知结果

| 并发场景 | 必须得到的唯一结果 |
| --- | --- |
| 引导接收与Turn完成 | 同一入口决定先后：输入关闭前accepted则消费／暂停保留；关闭后按后续队列处理，满足受控回退条件才准备新轮。没有终态轮内悬挂输入。 |
| 引导回退新轮时用户已结束／恢复 | binding revision不符，禁止回退，内容保留为暂停记录／草稿；不能跟随同ID的新绑定。 |
| 旧轮结束后另一轮已开始 | 不把面向旧轮的引导自动改投新轮；普通输入可保留后续队列，用户显式重投才改变目标。 |
| 排队消费与编辑／移除／引导按钮 | 同ID／版本只允许一个claim；失败方刷新，不重复执行。 |
| Stop与模型成功同时完成 | Stop关闭后续派发，最终状态沿现有取消优先；真实已发生结果保留，不能被late success置为自动续跑。 |
| End与新发送 | End先接受则新执行输入不接收；Send先接受则被结束流程消费／暂停保存，不能丢失。 |
| 旧结束完成与新恢复 | 新绑定只能在旧解绑提交后建立；旧票据／回调不得清掉新绑定。 |
| 两窗口恢复／重复组合操作 | 权威绑定CAS及operation去重只允许一个持有者；失败不销毁另一端。 |
| 引导已接收但下一请求失败 | 尚未提交规范历史的保持accepted＋paused；已提交的保持consumed并关联请求失败，不重复追加同一用户消息或重执行旧工具。 |
| 网络超时／落盘前后崩溃使投递结果未知 | 先按submission／request／operation核对；unknown不能自动转failed再发送。 |

停止仅停止当前任务并暂停自动队列，AI会话仍绑定。停止完成后显式新发送可建立新Turn，但先核对当前运行的unknown／历史完整性，旧暂停队列不跟随启动；明确“继续队列”才重新准入可恢复的queued项。自然语言“继续”是普通新输入，不是授权恢复所有队列、工具或审批的控制命令。结束并解绑后，旧输入均没有新绑定执行资格；复制完全不带可执行输入。

### 14.1 暂停输入的恢复与重发

| 原输入事实 | 允许的处理 |
| --- | --- |
| queued＋paused，仍在同一绑定／环境且内容有效 | 用户明确继续队列后，可保留submission_id／原顺序重新准入；不创建第二份用户输入。 |
| accepted但未consumed，原Turn仍可继续 | 仅同一Turn、同一有效绑定且已解除暂停原因时恢复原邮箱；旧计划仍按新input_revision重新规划。 |
| accepted但未consumed，原Turn已终结，或绑定／目标环境失效且无法原样重新准入 | 核对原尝试不会再消费后，原子取消原资格，用户明确重发生成新submission_id并记录original_submission_id；不能把原accepted无声改成queued。 |
| consumed，随后Turn失败／停止 | 保留在规范历史；可用原绑定内受限的回答恢复机制，或明确生成新的后续输入，不重发原submission、不重演已派发工具。 |
| outcome_unknown | 先对账，不能通过暂停／解绑／换ID把它变成明确未消费。证明未消费后才进入上述恢复／重发；证明已消费则转consumed并保留原关联。 |
| 结束并解绑前的旧输入 | 展示为原绑定的只读待处理记录；已知未消费且已失去原执行资格者可由用户明确重发，仍不确定者先核对。新绑定不继承旧队列启用状态。 |

重发中的“取消旧资格＋发布新输入”按original_submission_id／重发operation去重；同一恢复动作重复点击不能生成多个新ID。已明确归档到旧绑定且不会再推进的历史unknown不是新绑定的活动邮箱项，不全局阻塞无关Agent／资源；但其对应原效果／原输入仍不能盲目重放，实际资源门禁由可核对的ownership与效果事实决定。

旧runtime事件只补其原绑定区间的执行事实／审计，不能更新新Turn终态、草稿、当前工具表或重新发起模型请求。历史会话页面若展示旧事实更新，应标原运行来源，不把它当成当前环境最新状态。

## 15. 保存、崩溃恢复、容量与删除

### 15.1 持久化边界

运行内的完整恢复／复制为本PATCH必须验收。跨重启能否完整恢复历史沿现有存储能力，不借本补丁重做全量AI历史数据库；不能因持久化了一个绑定／queue ID就声称正文已恢复。最小可靠存储必须覆盖绑定版本／结束操作回执、输入去重／状态和已承诺保存的payload／附件引用，可复用现有journal＋原子文件写入。无法保存的接收不清草稿，不能显示“已保存到历史”。

队列受理、claim／start关联与消费回执须有可恢复的顺序：先持有正文／附件，再发布接收；执行前记录submission→Turn／operation关联；终态后保留去重证据。无法在同事务提交网络与本地写入时使用outbox／inbox对账，不承诺远端exactly-once。恢复发现不完整tool pair／缺少历史时禁自动执行，保留可读输入并显示具体恢复能力。

进程崩溃后不得根据磁盘binding直接恢复控制权。先对原operation、Supervisor ownership和输入fence进行核对／撤销，确认旧派发者不存在且本地控制已失效，再提交一次带崩溃原因的结束回执、last_closed_binding_revision和未绑定状态并推进版本；这样后续恢复具有结束证据，不靠手工清空binding。无法确认则保留为已绑定的待核对记录、不可接管。远端命令可能仍在运行，只保留历史unknown，不自动重连、重复停止、重放命令或续跑队列。应用正常退出／更新沿全部runtime的关闭屏障，不能只停可见Agent。

权威写入者还须通过应用现有单实例／存储写锁及进程实例身份确认；另一个仍存活窗口／进程拥有的绑定不是崩溃孤儿，不得“启动时全量解绑”。最小日志记录原进程实例与操作关联，操作回放只补原版本状态，不重新执行外部副作用。已结束记录中的历史unknown与当前绑定的未决投递分开索引，查看／恢复不把它重新注册成活任务。

### 15.2 有界保留

首版常量作为非UI契约：每个AI会话最多32条尚在活动调度器中的未终结follow_up输入（包括queued／submitting／accepted但未消费／outcome_unknown，以及其中paused的项）；应用总计最多256条；每会话待处理正文上限512 KiB，应用总计8 MiB。正文与附加文本按实际UTF-8字节计，编辑按替换差额计；草稿／正式历史仍沿已有上限，不通过这里提高wire_history的512条／512 KiB限制。超限拒绝新受理并保留草稿，不淘汰旧输入冒充成功。审批／问答、Stop／End等有界控制通道独立预留，不能被follow_up配额占满。

文件／图片使用现有单项／单次附件上限；本次非 UI 实施将 AI 不可变图片的全应用保留预算定为 **512 MiB（编码字节＋解码像素）**，与每个工具结果库原有 128 MiB 上限分别执行。排队保留引用并计入全应用实际占用，不能靠引用共享漏算不同图片；同一不可变块只按物理一次计费。达到附件预算时拒绝新受理，不延迟到执行时才发现正文已丢。已归档暂停输入可在显式结束后落盘退出热内存，但仍不能无界生成或恢复到可执行队列。列表分页／虚拟化，打开列表不预加载所有会话正文或启动worker。

上述输入条数／正文预算是本 PATCH 新增的首版默认常量，不是当前源码已有值，不新增设置调优页。转成不可执行历史待处理记录后按既有历史保留策略计费；再次启用队列须重新通过32／256条与正文／附件准入，不允许“落盘后重新载入”绕过上限。只读历史、绑定索引和最小去重回执不因此全量常驻正文。

### 15.3 删除和保留

来源与副本各自引用历史／快照，删除来源只减少自身引用，不删除副本仍持有内容。正文复制权限、保留策略、附件不可访问均在复制前校验。处于绑定或提交unknown的会话不得直接删除去重和ownership证据；先结束／核对，再按现有明确删除操作清理。不新增长期保存秘密、跨Agent凭据传递或自动导出格式。

## 16. UI、低打扰与设计基准

### 16.1 普通发送与队列

运行中保持输入和发送能力；有内容时发送可用，停止保持独立入口，无内容时可突出停止。沿既有尺寸／tokens预留按钮区域，状态切换不跳动，不为解释worker添加产品文案。Tooltip分别为“引导当前任务”“加入队列”，包含单条反向快捷键。

引导消息立即进入时间线，等待接入时附轻量“待处理”；进入请求后去掉等待，失败／待确认有消息级状态。整个消息队列使用一张无描边紧凑卡片，内部每条消息单行显示，序号／状态、正文摘要与图标快捷操作同行。默认常驻向上直箭头与更多，hover／键盘聚焦时显示编辑／移除，位置和高度不跳动；调整顺序进入更多菜单。操作通过 Tooltip 和 a11y 标签解释，只有编辑时展开输入区。卡片作为 composer 正上方正常列布局的占位区域，显示顺序、必要附件与编辑／移除／引导操作；不使用悬浮定位或 portal，不遮挡步骤和消息。消息区高度扣除队列实际占位高度。头部固定、卡片区域有界内部滚动，不挤出输入框；被消费后进入正式历史，使用同 submission 关联去重。用户阅读历史不强滚到底。正常接收、接入和消费不弹 Toast，不抢焦点、不增加声音或系统通知。

### 16.2 AI会话列表与结束

| 列表事实 | 主要动作 |
| --- | --- |
| 当前Agent已绑定 | 返回当前会话、查看、复制；结束是明确操作。 |
| 其他Agent已绑定 | 查看、定位、复制；无恢复按钮。定位失败保留事实，不自动接管。 |
| 已绑定且有结束操作进行 | 查看并显示操作进度；绑定标签仍为已绑定，恢复不可用。 |
| 已结束未绑定且内容可读 | 查看、恢复到当前Agent、复制到当前Agent。 |
| 未使用副本／新会话且未绑定 | 查看、首次使用到当前Agent；不显示不存在的原运行恢复。 |
| 删除／内容不可用 | 如实显示可查看范围，不给假恢复入口。 |

目标已有会话时动作明确为“结束当前会话并恢复”或“结束当前会话并使用副本”，显示当前任务／暂停输入影响，复用现有关闭确认，不增加每条消息的确认。空闲无资源直接完成；需停止时展示真实进度，失败保留重试／定位。隐藏面板使用“收起”，不能与“结束会话”同义。历史只读页面没有能直接执行的普通发送按钮。

现有审批／问答原位交互、稍后处理胶囊和队列是不同集合，可同时投影但不混计；不要把用户待批命令拖到普通队列或将队列编辑覆盖问答草稿。原位输入恢复、附件、焦点、滚动、IME和Esc优先级沿既有交互契约；选中历史对象的命令票据不追随之后切换的Agent。

### 16.3 原型与原生验收边界

上述状态使用 zenit-html-ui 与仓库实际 ui.widgets API 实现原生交互；未新开第二套独立助手页面。针对性验证包括三主题布局与旧事件校验，以及真实主程序上的排队、同轮引导、只读查看、跨 Agent 复制／定位、确认取消、恢复／解绑和设置保存。真实外部模型、远端 SSH、真实输入法和 VoiceOver 尚不由该本地确定性验证覆盖。仅编译通过或静态文档不能算 UI 完成。

迁移旧数据时：selected／ended不能直接决定绑定。读取真实存活任务、当前附着对象与权威持有者：每个Agent只保留一个可证明的当前绑定，其他旧记录在完成必要收敛后转未绑定。若同一ConversationId多份数据／多持有者，先冻结执行并核对content revision／operation，不能“最后写入者获胜”覆盖历史；必要时保留冲突快照供只读，不自动合并。旧owner只做来源，不可恢复为当前连接句柄。迁移失败停止启用新调度，保留旧记录与诊断，不双轨运行两个发送器。

迁移转未绑定也须提交可核对的结束／迁移回执和last_closed_binding_revision；不能迁完后因缺少结束证据无法恢复。只有可证明从未使用的空记录／副本才走首次绑定例外。运行中草稿与规范历史不同写入域，draft_revision由控制线程管理；worker提交模型历史不能覆盖新草稿，只读复制只pin已提交content_revision。
